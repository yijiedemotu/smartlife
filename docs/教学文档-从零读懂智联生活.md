# 第 1 章 · 业务全貌：三端一体在做什么

## 1.1 三个端与角色

| 端 | 角色 | 入口 | 核心能力 |
|---|---|---|---|
| 👤 用户端 | `role=1` | 用户端页面 | 逛店、附近(GEO)、购物车、下单支付、订单追踪、秒杀抢券、券包、饭搭子匹配、私信、签到、资料 |
| 🏪 商家端 | `role=2` | `/merchant/**` | 入驻申请、店铺资料与营业开关、**单店经营看板**、订单履约（接单→配送→完成/取消）、商品管理、优惠券管理（秒杀时间窗）、**到店券核销** |
| 🛡️ 管理端 | `role=3` | `/admin/**` | **入驻审核**（通过即自动开店）、店铺治理（停业/恢复/删除）、全平台订单巡检与兜底、商品与券违规治理、账号封禁/解封、类目字典、平台看板、**操作审计日志** |

三端不是"三个页面"，而是**账号体系 + 接口鉴权 + 数据隔离 + 消息隔离 + 治理流程**五层都分开（详见第 3 章）。

## 1.2 平台治理闭环（本项目最有"真实业务味"的部分）

```
商家注册(role=2) ──► 提交入驻申请单(tb_merchant_apply, status=待审)
        │                       │
        │            管理端【入驻审核】通过
        │                       ▼
        │            自动创建店铺：merchant_id 绑定、audit_status=通过、open_status=营业
        │            （幂等：同一申请单重复审核被拒）
        ▼                       ▼
   商家可经营：维护资料/上下架商品/发券/接单/核销 ──► 关键动作写 tb_audit_log
                                │
                     平台治理：停业整顿 / 恢复 / 删除店铺、下架违规商品与券、封禁账号
```

## 1.3 一条完整业务主线（读懂它≈读懂 80% 代码）

```
① 逛店：/shop/list、/shop/nearby(GEO)、/shop/{id}(多级缓存，仅展示审核通过且营业中的店)
② 加购：/cart（Redis Hash）
③ 下单：/order/create（校验+服务端算钱+写订单与快照+条件扣库存+清购物车）
④ 支付：/order/{id}/pay（状态→2；WebSocket 只推给【该店铺的商家】）
⑤ 履约：商家 /merchant/order/{id}/accept|deliver|finish（每步 WS 推给下单用户）
⑥ 秒杀：/voucher/seckill/list、/voucher/{id}/seckill（Lua 预扣 → MQ 异步落库 → WS 通知）
⑦ 社交：/mate/recommend（编辑距离+堆）→ /chat/send 与 /chat/history 轮询收发
⑧ 运营：签到 BitMap、UV HyperLogLog、券核销（商家端 Redeem 页）
⑨ 治理：入驻审核、店铺停复业、订单巡检、账号封禁、审计日志
```

## 1.4 藏在业务里的关键设计（读代码前先记住）

1. **用户端只看得见"审核通过且营业中"的店铺**（`RoleConstants.visibleToUser`），商家端/管理端不受限
2. **一个商家绑定一个店铺**（`tb_shop.merchant_id` 唯一索引）；商家端所有查询强制带自己的 shopId，**服务端强制重写 shopId**，前端伪造无效
3. 订单金额**服务端重算**；"我的xx"接口的用户 id 一律来自登录态，绝不接受前端传参
4. 秒杀券**一人一单**；订单只有 1/2 状态可取消，取消要回补库存
5. 金额一律**分**（整数）；关键动作必须**留痕**（审计日志）

# 第 2 章 · 代码分层与"请求的一生"

## 2.1 分层地图（按三端看）

```
Vue3 单应用（同一工程，三套布局 + 路由守卫）
  ├─ layout/UserLayout.vue
  ├─ layout/MerchantLayout.vue   /merchant/**
  └─ layout/AdminLayout.vue      /admin/**
        │  utils/request.js（自动带 token、解包 Result、X-Auth-Refresh 续期）
        ▼  HTTP + Authorization: Bearer <JWT>
Spring Boot (context-path=/api)
  ① 拦截器链：AuthInterceptor(路径前缀鉴权) → TokenRefreshInterceptor(滑动续期)
  ② Controller：/auth · 用户端(/shop /cart /order /voucher /mate /chat /sign /user)
                · 商家端(/merchant/**) · 管理端(/admin/**)
  ③ Service：业务规则 + 端侧守卫(RoleGuard) + 归属校验(MerchantService) + 缓存/锁/MQ 编排
  ④ Mapper：MyBatis-Plus CRUD + 手写聚合 SQL
  ⑤ 中间件：Redis（缓存/Lua/GEO/BitMap/HLL/锁）· RabbitMQ（削峰+死信）· WebSocket（按角色分桶）
```

## 2.2 一次请求的生命周期（以"商家接单"为例）

```
商家端订单页 → request.post('/merchant/order/8/accept')
  ▼
AuthInterceptor.preHandle
   ├─ 解析 JWT → LoginUser{id, role, nickname}
   ├─ path=/merchant/... → user.canOperateShop()? 否则 403「仅商家账号可访问」
   └─ UserContext.set(user)                      ← ThreadLocal
  ▼
TokenRefreshInterceptor：剩余 <30min → 响应头 X-Auth-Refresh
  ▼
MerchantController.accept(orderId)
   ├─ RoleGuard.requireShopOperator()            ← Service 层二次校验
   ├─ merchantService.requireActiveShop(me)      ← 必须已过审且营业中
   └─ orderService.accept(orderId, shopId)       ← 归属校验：订单必须属于我的店
        ├─ 状态机 2→3
        └─ MessagePusher.orderStatus(order.userId, ...)  ← WS 推给下单用户
  ▼
Result{code:1,...} → 前端响应拦截器（顺带续期）→ 页面刷新
  ▼
afterCompletion → UserContext.clear()
```

**读代码顺序**：Controller（接口与入参）→ Service（业务与并发）→ Mapper（数据）→ 前端页面（交互与守卫）。

## 2.3 统一约定（少踩坑）

| 约定 | 位置 | 说明 |
|---|---|---|
| 响应体 | `common/Result` | `code`：1 成功 / 401 未登录 / 403 端侧越权 / 0 业务失败 |
| 业务异常 | `BusinessException` + `GlobalExceptionHandler` | Service 直接抛，统一转 JSON |
| 用户上下文 | `common/UserContext` | ThreadLocal，请求结束必须 clear |
| 角色/状态常量 | `common/RoleConstants`、`LoginUser` | 角色 1/2/3、店铺审核 0~3、申请单 0~2 |
| Redis Key | `common/RedisConstants` | 集中管理，禁止散写字符串 |
| 消息常量 | `MQConstants`、`ws/MessagePusher` | 交换机/队列/WS 消息类型 |

# 第 3 章 · 三端鉴权与数据隔离（本版本核心新章）★

> 面试最爱问："普通用户/商家会不会越权看到别人数据？"——本章就是答案，共 **5 道防线**。

## 3.1 权限矩阵（`security/AuthInterceptor`）

| 路径前缀 | 允许角色 | 说明 |
|---|---|---|
| `/auth/**` | 免登录 | 登录 / 用户注册 / **商家入驻注册** |
| `/merchant/**` | 商家(2) + 管理员(3) | 管理员具备平台代管能力 |
| `/admin/**` | 仅管理员(3) | 平台治理专属 |
| `/cart/ /mate/ /chat/ /sign/` | 仅普通用户(1) | 购物车/社交/签到是用户端语义，商家与管理员账号被拒 |
| 其余（`/shop /order /voucher /user ...`） | 登录即可 | 用户端业务 |

实现要点（`AuthInterceptor`）：
```java
String path = request.getRequestURI().substring(request.getContextPath().length()); // 剥离 /api
if (path.startsWith("/merchant/") && !user.canOperateShop()) → 403
if (path.startsWith("/admin/")   && !user.isAdmin())         → 403
if (isUserOnlyPath(path) && user.isAdmin())                  → 403
UserContext.set(user);
```
> 为什么要剥离 contextPath：`getRequestURI()` 带 `/api` 前缀，不剥离就永远匹配不到 `/admin/`。

## 3.2 第二道防线：`security/RoleGuard`（Service 层显式校验）

```java
RoleGuard.requireMerchant();      // 必须是商家本人（管理员也不通过，用于"仅商家自己"的敏感写）
RoleGuard.requireShopOperator();  // 商家或管理员
RoleGuard.requireAdmin();         // 仅管理员
```
拦截器管"路径"，RoleGuard 管"业务方法调用者的身份"，对定时任务/内部调用也能给出清晰报错。

## 3.3 第三道防线：店铺归属校验（`service/MerchantService`）

```java
shopOfMerchant(merchantId)      // 商家→店铺 解析（进程内缓存 60s，吸收高频请求）
requireShop(id)                 // 没店铺 → "请先提交入驻申请"
requireActiveShop(id)           // 未过审/停业 → 明确的业务提示
assertShopOwnership(shopId, merchantId)  // 目标店铺必须属于该商家（管理员传 null 跳过）
resolveOperateShop(user, shopId, mustActive) // 商家=取自己的店；管理员=必须显式选店
resolveQueryShop(user, shopId)  // 商家只能查自己的店，管理员可查任意店
```

## 3.4 第四道防线：服务端强制重写 shopId（防前端伪造）

商家端写商品/券/订单操作时，**不信任请求体里的 shopId**：
```java
Shop shop = merchantService.resolveOperateShop(currentUser, dto.getShopId(), true);
dto.setShopId(shop.getId());   // 服务端强制覆盖为"当前登录者有权操作的店铺"
```
即使前端篡改成别家店铺 id，也会被纠正为自己的店。

## 3.5 第五道防线：WebSocket 消息按角色/店铺分桶（`ws/WsSessionManager`）

```java
userSessions    : userId     → sessions   // 用户端（多端登录保留多会话）
merchantSessions: merchantId → sessions   // 商家端：新订单只推给"订单所属店铺"的商家
adminSessions   : Set<Session>            // 平台广播（如异常告警）
```
支付成功时：`MessagePusher.newOrderToMerchant(order.getShopId(), ...)` —— **A 店的新单不会打扰 B 店商家**；用户侧状态变更只推下单本人。

## 3.6 端到端验证（自己动手）
1. 用商家 `13700000001` 登录，调 `/admin/order/page` → 期望 **403 仅平台管理员**；
2. 用商家 A 的 token 提交别家店铺的商品（把 shopId 改成 B 店）→ 期望"无权操作他人店铺"或被强制重写；
3. 用管理员登录调 `/cart` → 期望 **403 平台管理员账号不支持用户端操作**；
4. 用 `13700000002`（待审核商家）登录商家端 → 提示"店铺当前状态为「待审核」"；管理员审核通过后刷新 → 可正常经营。

# 第 4 章 · 认证与账号（JWT + 拦截器 + ThreadLocal）

## 4.1 三个注册/登录入口
| 接口 | 说明 |
|---|---|
| `POST /auth/login` | 三端统一登录，返回 `role` 与 **`homePath`**（前端据此落到用户端/商家端/管理端首页） |
| `POST /auth/register` | 用户端注册（role=1） |
| `POST /auth/register/merchant` | 商家注册（role=2）**并自动提交入驻申请单**（等待平台审核） |

## 4.2 代码流程（登录）
```
AuthController.login → UserService.login:
   ① selectOne(phone)                    ② PasswordUtil.matches(raw, salt:sha256)
   ③ 校验 status（0 封禁 → 拒绝）         ④ JwtUtil.createToken(LoginUser{id,role,nick})
   ⑤ 返回 {token, role, nickname, avatar, homePath}
前端：store.setLogin() 持久化 → router 按 homePath 跳转
```

## 4.3 设计要点
- 口令 `salt:sha256(pwd+salt)`，随机盐；生产可换 BCrypt（见手册④）
- JWT 无状态换来多实例零共享；代价是无法主动踢人 → 需要时引 Redis 黑名单
- **滑动续期**：`TokenRefreshInterceptor` 剩余 <30min 自动签发新 token 走 `X-Auth-Refresh`，前端 axios 自动替换
- **账户状态**：管理员可封禁/解封（`/admin/user/{id}/status`），登录与接口都会校验 `status`
- **改密/角色接口**：`/user/me/password`、`/user/me/role`

**练习**：把 `expire-minutes` 改成 1 分钟观察续期；再封禁一个账号，看登录与已登录请求的差异。

# 第 5 章 · 用户读链路：多级缓存治理（技术：Caffeine + Redis + 布隆 + 互斥锁）

## 5.1 业务需求
首页/详情/附近都是"高频读、低频写"。要求：热点别打 DB、不存在的 id 别打 DB、缓存过期别把 DB 打穿、**审核未过/休息中的店铺对用户端等价于不存在**。

## 5.2 接口与代码位置
```
GET /shop/list      → ShopService.pageShops（热点排序）
GET /shop/hot       → ShopService.hotShops（定时预热缓存）
GET /shop/nearby    → ShopService.nearby（Redis GEO）
GET /shop/{id}      → ShopService.queryById（★多级缓存 + 可见性校验）
GET /shop/{id}/products → ProductService.listByShop
GET /shop/type/list → ShopService.listTypes（Redis 12h）
```

## 5.3 queryById 教学式拆解（本项目最该读懂的方法）

```java
// ① L1 本地缓存（Caffeine 5s）：同实例瞬时热点
Shop shop = localCache.getIfPresent(id);
if (shop != null) return shop;

// ② 布隆过滤器：不存在的 id 直接拒掉 → 防「穿透」
if (!bloom.mightContain(id)) return null;

// ③ L2 Redis：EMPTY=曾查过但不存在（空值缓存 5min）；JSON=正常缓存
String json = redis.opsForValue().get(cacheKey);
if (json != null) {
    if (MARKER.equals(json)) return null;
    shop = JsonUtils.fromJson(json, Shop.class);
    localCache.put(id, shop);
    return shop;                 // ★注意：用户端读取后还要判断 visibleToUser
}

// ④ 都未命中 → 互斥锁重建（防「击穿」）：仅一个线程查库回填
return rebuildByMutex(id, cacheKey);
```

**关键补充**：用户端读取后通过 `RoleConstants.visibleToUser(shop)` 过滤——`audit_status=通过 && open_status=营业` 才可见；否则等价于"店铺不存在"。这样"平台停业整顿"立刻对用户端生效，而不需要遍历清理缓存。

## 5.4 四道防线（教学对照表）
| 问题 | 不解决的后果 | 本项目对策 | 代价 |
|---|---|---|---|
| 穿透 | 恶意/错误 id 打穿 DB | 布隆 + 空值缓存 | 布隆不可删，靠启动重建 |
| 击穿 | 热点 key 过期瞬间全打 DB | 互斥锁单飞 + L1 兜底 + 自旋 | 热点期毫秒级等待 |
| 雪崩 | 大量 key 同时过期 | TTL 随机化 20~40min | —— |
| 一致性 | 商家改了、用户看旧值 | 写后重建缓存 + 启动全量重建 + 审核状态实时过滤 | 短暂窗口 |

## 5.5 写链路（多份索引一致性）
`ShopService.saveShop`：`INSERT/UPDATE DB → writeDetail(重建缓存) → GEOADD → bloom.put → 删热点列表缓存`；
`removeShop`：删库 → 删缓存 → 移除 GEO 成员（布隆删不掉，靠启动重建）。
商家改资料/平台停业都走 `ShopService`，保证缓存/GEO/热点三份索引口径一致（`MerchantService` 里统一调用）。

**动手**：连续请求 `/shop/1` 100 次看 SQL 日志次数；`redis-cli FLUSHDB` 后再请求一次，观察只有 1 次 DB 查询（互斥锁）；请求 `/shop/999999` 确认无 SQL（布隆）。

# 第 6 章 · 位置与运营：GEO / HyperLogLog / BitMap

## 6.1 附近店铺（Redis GEO）
```
写：ShopService.addToGeo → GEOADD shop:geo:{typeId} lon lat shopId（同时写 typeId=0 全量与具体类型）
读：ShopService.nearby → GEORADIUS key lon lat 10km ASC COUNT 20 → 按 id 复用多级缓存补详情
```
- 为什么：GEO 底层是 **ZSet + GeoHash(52bit)**，半径过滤+排序在 Redis 内存完成，毫秒级
- 一致性：店铺增删改同步维护；`DataInitRunner` 启动全量重建
- 只返回可见店铺（同上 `visibleToUser`）

## 6.2 UV 统计（HyperLogLog）
`PFADD uv:{date}:{page} visitorId` 埋点；看板 `PFCOUNT` 汇总。固定 ~12KB、误差 0.81%，用极小内存统计海量去重 UV。

## 6.3 每日签到（BitMap）
```
sign:{userId}:{yyyyMM}  第 N 位=当月第 N 天
签到：SETBIT (day-1) 1      月统计：遍历 GETBIT 收集已签天
连续天数：从今天往前数        内存：一年 365bit ≈ 46 字节/人
```

**动手**：`redis-cli GEOPOS shop:geo:0 1`、`GEODIST ... 1 4 km`、`GETBIT sign:<uid>:<yyyyMM> <day-1>`、`PFCOUNT uv:<今天>:shop:1`。

# 第 7 章 · 交易链路：购物车 → 下单 → 支付 → 履约（技术：Redis Hash + 事务 + 状态机 + WS）

## 7.1 购物车（Redis Hash）
```
cart:{userId}  field=productId  value=数量
HINCRBY 加 / HSET 改 / HDEL 删 / HGETALL 取 → 回表拿商品实时价与店名 → CartItemVO
```
为什么存 Redis：读写高频、无强持久需求；**价格永远以 DB 为准**（回表）。

## 7.2 下单：一个事务里的五件事（`OrderService.create`）
```
① 校验：店铺存在（且可见）+ 商品属于该店且在售
② 服务端重算金额：amount = Σ(price × count)          ← 不信前端
③ 写 tb_orders(status=1) + 逐条 tb_order_item（名称/图/单价快照）
④ 逐条 reduceStock：UPDATE tb_product SET stock=stock-n, sales=sales+n
                    WHERE id=? AND stock>=n AND status=1   ← 原子条件更新防超卖
   返回 0 行 → 抛 BusinessException → @Transactional 整体回滚
⑤ 清理购物车对应项（HDEL）
```
为什么要快照：商品改名/改价/下架不影响历史订单；为什么要条件更新：并发下"查-改"有窗口会超卖。

## 7.3 支付 → 只推给该店商家（WS 课堂重点）
```
OrderService.pay: 校验归属与状态(必须1) → status=2+payTime
   → 组装 {orderId,number,shopName,amount,userName,address}
   → MessagePusher.newOrderToMerchant(order.getShopId(), map)
        → WsSessionManager.sendToMerchant(merchantId, json)   // 只推该店商家
商家端 MerchantLayout/Orders.vue：收到 NEW_ORDER → 弹窗响铃 + 刷新
```
用户侧：商家 accept/deliver/finish 时 `MessagePusher.orderStatus(order.userId, ...)` → 用户端 toast + 订单页刷新。

## 7.4 履约状态机（`OrderService`）
```
1 待支付 ─pay→ 2 已支付/待接单 ─accept→ 3 制作中 ─deliver→ 4 配送中 ─finish→ 5 已完成
   │                 │
   └─cancel(用户/商家)┴→ 6 已取消（回补库存）
```
`transit(orderId, from, to, msg)` 先校验当前状态==from，否则拒绝——状态机挡住跳级/重复操作。

## 7.5 超时未支付自动取消（`OrderTimeoutTask`）
```
@Scheduled(cron="0/30 * * * * ?")
 ① Redisson tryLock("smartlife:task:timeout-order")  ← 多实例只让一台执行
 ② SELECT status=1 AND create_time < now-15min LIMIT 200
 ③ 逐单置 6 + 按明细 addStock 回补
```

**动手**：双浏览器演示"用户支付 → 商家响铃 → 接单/配送/完成 → 用户实时进度"；再把 `TIMEOUT` 临时改小，观察超时取消与库存回补。

# 第 8 章 · 秒杀（技术：Redis Lua + Redisson + RabbitMQ + 死信）★

## 8.1 需求拆成 4 个问题
① 不超卖 ② 一人一单 ③ 别把 DB 打爆 ④ 用户要"秒回"

## 8.2 方案演进
```
v1 同步查库存再插入     → 并发超卖
v2 DB 乐观条件更新      → 防超卖但 DB 成瓶颈、一人一单要两步
v3 Redis Lua 预扣 + MQ 异步落库 + DB 兜底 + 唯一索引   ← 本项目（另有 Redisson 锁版可切换对比）
```

## 8.3 完整流程（`VoucherService.grabSeckill`）
```
POST /voucher/{id}/seckill
 ① 预校验（一次 DB 读）：券存在/上架/type=2/在[begin,end]
 ② ensureStockCache：Redis 库存 key 缺失 → 按 DB 剩余回填
 ③ 主方案 Lua（SECKILL_LUA_ENABLED=false 时切 Redisson 锁）：
      execute(seckill.lua, [seckill:stock:{id}, seckill:user:{id}], userId)
      0=成功 1=库存不足 2=重复下单
 ④ 成功 → MQ 发送 {userId,voucherId} → 立即返回"已受理"
 ⑤ 消费者 SeckillOrderConsumer（手动 ACK + @Transactional）：
      a. 再校验时间窗  b. DB 条件更新 stock-1,sold+1 WHERE stock>0
      c. INSERT tb_voucher_order（唯一索引 user_id+voucher_id）
      成功→ACK+WS 通知；重复→ACK(幂等)；业务失败→回补 Redis+ACK+通知失败；未知异常→NACK→死信
 ⑥ 死信消费者 SeckillDeadConsumer：回补库存 + 通知"可重试"
```

## 8.4 Lua 逐行（`resources/lua/seckill.lua`）
```lua
if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then return 2 end  -- 一人一单
local stock = tonumber(redis.call('get', KEYS[1]) or '-1')
if stock <= 0 then return 1 end                                       -- 库存不足
redis.call('decr', KEYS[1])                                           -- 扣减
redis.call('sadd', KEYS[2], ARGV[1])                                  -- 标记用户
return 0
```
Redis 单线程执行整段脚本 → "判重+扣减"不可被打断 → 原子。

## 8.5 为什么"两把锁 + 一条约束"层层都要
| 层 | 防什么 |
|---|---|
| Redis Lua / Redisson 锁 | 扛 99% 流量，防 Redis 侧超卖与一人一单 |
| DB 条件更新 stock>0 | Redis 与 DB 万一不一致，DB 仍不超卖（权威兜底） |
| 唯一索引 | 一人一单最终防线 + MQ 消费天然幂等 |
| 失败回补 | 任何"预扣成功未落库"都还库存，最终一致 |

**动手**：stock=100、2000 并发压测核对订单行数=100；同账号连点两次验证限购；切锁方案对比吞吐；RabbitMQ 控制台看积压与归零。

# 第 9 章 · 社交：饭搭子匹配 + 私信（技术：编辑距离 + 堆 + REST 轮询）

## 9.1 匹配（`MateService.recommend`）
```
① 读 mate:recommend:{userId} 缓存(10min) ② 取我的标签，空则提示完善
③ 候选池 = role=1 且 id≠我 且 tags 非空
④ 打分：对"我的每个标签"取它与对方标签集合的最小编辑距离并累加 = distance
⑤ 容量 N 的堆保留 distance 最小的 N 个（内存 O(N)）   ⑥ matchRate = max(0,100-distance*10)
⑦ 写回 Redis 10min
```
`JSON_CONTAINS(tags, JSON_QUOTE(?))` 用于按标签精确找人（比 LIKE 准）。

## 9.2 私信（REST + 轮询，刻意不用 WebSocket）
```
发送 POST /chat/send {toId,content}        → 校验 → INSERT tb_message
增量 GET /chat/history/{peer}?afterId=N    → WHERE id>afterId ORDER BY id  （前端 2.5s 轮询）
初次 GET /chat/history/{peer}?size=50      → 最近 50 条（正序）
会话 GET /chat/contacts                    → LEAST/GREATEST 归组 + MAX(id) 取末条 + 未读聚合
已读 POST /chat/read/{peer}                → read_flag=1
导航角标：每 6s 轮询 contacts 求和
```
为什么不用 WS：私信弱实时、轮询零连接态；订单强实时才用长连接——同一平台两种实时方案并存，是"按场景选型"的最佳素材。

**动手**：DevTools 看 `afterId` 递增；把轮询间隔改 10s 体验延迟；`redis-cli` 观察缓存/库存变化。

## 10.2 单店隔离是怎么落地的（教学重点）
```
① AuthInterceptor：/merchant/** → canOperateShop()（商家或管理员）
② MerchantController 每个方法先取 currentUser
③ MerchantService.resolveOperateShop / resolveQueryShop：
      商家 → 解析自己的店铺（可要求 mustActive 已过审营业）
      管理员 → 必须显式指定 shopId（平台代管），未指定则报错引导
④ Service 内所有查询都强制 eq(shopId, 自己的店铺)
```
**效果**：请求里传 `shopId=别家` 也不会越权；管理员"代管"是显式能力而非漏洞。

## 11.2 审核闭环教学（最值得画图的一段）
```
商家注册(role=2) ──► /merchant/apply/submit（生成申请单，status=0 待审）
        │
管理端 /admin/apply/page 看到待审 ──► /admin/apply/{id}/audit {approved:true, remark}
        │
MerchantService.auditApply（@Transactional）：
   ① 校验申请单存在且 status=待审（防重复审核：幂等）
   ② 更新申请单（状态/审核人/时间/备注）
   ③ approved 且首次入驻 → 新建 Shop：merchant_id 绑定、audit_status=1、open_status=1
                    → shopService.saveShop（联动缓存/GEO/热点）
   ④ approved 且资料变更 → 同步店铺字段并复营业
   ⑤ evictCache(merchantId)（清 60s 归属缓存，让商家端立刻看到新状态）
   ⑥ writeAuditLog(adminId, "APPLY_APPROVE"/"APPLY_REJECT", ...)
```
**可讲的设计点**：①审核通过才"产生"店铺（而不是先建店再改状态）；②申请单状态机保证幂等；③归属缓存主动失效；④审计日志失败不影响主流程（`try/catch` 只告警）。

# 第 14 章 · 调试技巧与排错手册

## 14.1 调试技巧
- **后端日志**：`SPRING_PROFILES_ACTIVE=dev`（或 `application.yml` 的 MyBatis log-impl）打开 SQL 打印，用来验证"缓存是否命中"

- **命令行**：`redis-cli monitor`（真实命令流）、`ttl/get/smembers/pfcount/getbit`、RabbitMQ 15672 看队列
- **前端**：Network（请求/响应/WS）、Console、Application→localStorage(`sl_user`)、Vue Devtools 看 Pinia

## 14.2 排错手册
| 现象 | 定位/解决 |
|---|---|
| 登录后落到错误的端 | 看登录响应 `role` 与 `homePath`；前端路由守卫按 role 分流 |
| 商家端提示"店铺尚未通过审核" | 设计如此：先在管理端「入驻审核」通过其申请 |
| 用户端看不到某家店 | `audit_status != 1` 或 `open_status != 1`（平台停业/商家休息），用户端等价于不存在 |
| 商家改商品提示"无权操作他人店铺" | 归属校验生效；确认 shopId 是否被篡改，或改用管理员代管（显式传 shopId） |
| 普通商家调 `/admin/**` 返回 403 | 正常鉴权，换管理员账号 |
| 用户端接口 401 | token 缺失/过期；Knife4j 里记得配全局 Header `Authorization: Bearer xxx` |
| JS 端登录"没反应" | 看 Network 是否 200 → localStorage 是否有 token（曾因 Pinia state 未声明字段导致） |
| 秒杀提示"手慢了" | Redis 库存与 DB 不同步 → 重启后端触发回填，或商家端重存该券 |
| 秒杀券不显示 | 时间窗过期 / `status=0` / `audit_status` 被平台下架 |
| WS 不推送 | 后端在否；Network→WS 是否 101；token；是否看错端（新单只推该店商家） |
| 冒烟测试 FAIL | 按脚本输出定位是哪条断言；常见是种子数据未重建 / 服务未起 / 端口占用 |
| 控制台中文乱码 | 多为终端 GBK 解码显示问题，数据本身 UTF-8；用浏览器或文件确认 |

# 第 15 章 · 教学改造任务（从"会读"到"会写"）

## 15.1 入门
1. 给 **商家端看板**新增一个指标：本店"今日新客数"（首次在本店下单的用户数）。
2. 给 **用户端店铺详情**加"收藏"（Redis Set，含我的收藏列表页）。
3. 管理端审计日志支持按 `action` 过滤。

## 15.2 进阶
4. **入驻审核驳回通知商家**：审核后站内私信/WS 通知（复用 Chat 或 WS）。
5. **店铺评分**：订单完成后可评分，聚合到 `tb_shop.score` 并同步缓存。
6. **秒杀限流**：同用户 3 秒内只能点一次（SETNX+TTL），前端按钮倒计时。
7. **订单超时改延迟消息**：RabbitMQ 死信 TTL / 延迟插件替代定时扫描，对比精度与压力。

## 15.3 挑战
8. **新增第四端"骑手"**：接单配送（订单状态 3→4 由骑手端操作），复习整套权限矩阵与隔离。

11. **审计日志异步化**：改为 MQ 异步落库 + 分区表，讨论"审计可靠性 vs 主流程性能"。

# 第 16 章 · 自测题库与结语

## 16.1 每章自问
1. 三端是怎么"真的分开"的？五道防线分别在哪、（用代码位置回答）。
2. 用户端为什么看不到被停业的店铺？这个判断在哪个方法里？
3. 商家 A 如何被阻止查商家 B 的数据？如果我伪造 shopId 会发生什么？
4. 店铺详情的四道防线各防什么？写路径如何保证缓存/GEO/布隆一致？
5. 下单为什么要"服务端重算金额"+"条件扣库存"+"明细快照"？
6. 支付后为什么只有该店商家收到新单提醒？WS 会话是怎么分桶的？
7. 秒杀的三层一致性防线分别防什么？死信什么时候触发？
8. 匹配为什么用编辑距离+堆？私信为什么不用 WebSocket？
9. 入驻审核闭环有哪几步？怎么做幂等？归属缓存什么时候失效？
10. 冒烟测试覆盖了什么？你自己新增功能后会补哪些断言？

## 16.2 结语：什么叫"真正读懂这个项目"
- **能画**：业务闭环图 + 三条核心时序（缓存读 / 秒杀 / 订单履约）+ 权限矩阵
- **能指**：每个结论落到类/方法/一行配置（本文档已给位置）
- **能证**：跑出缓存命中、压测不超卖、双端 WS 推送的真实现象
- **能改**：完成第 15 章至少一个任务并通过冒烟测试
- 之后再用《项目学习手册》①~⑤ 做纵深、《面试题档案 56 条》做输出训练，这个项目就真正属于你了。
