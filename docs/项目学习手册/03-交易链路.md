## 模块一：秒杀系统（Redis Lua + Redisson + RabbitMQ）——第二面试重点

### 1.1 需求拆解：秒杀到底难在哪

| 难题 | 如果不处理会怎样 |
|---|---|
| **超卖** | 100 张券卖出 300 张，平台要赔钱 |
| **一人一单** | 一个用户脚本刷光库存，其他人陪跑 |
| **DB 打崩** | 瞬时并发全打到 MySQL，连接池 + 行锁雪崩 |
| **下单慢** | 同步落库 = 单线程排队，QPS 上不去，前端超时 |
| **失败丢库存** | 预扣成功但下单失败 → 券"消失"，用户投诉 |
| **三端边界** | 商家 B 能不能给自己的券设库存？平台能不能下架违规券？ |

前五个是经典秒杀问题，第六个是三端改造**新增**的问题——本模块都会覆盖。

### 1.2 方案总览：两条链路，一个开关

```yaml
smartlife:
  seckill:
    lua-enabled: true    # true=Lua 原子预扣（默认）；false=Redisson 分布式锁（对照组）
```

```
【Lua 方案：lua-enabled=true】
用户点击抢购 POST /voucher/{id}/seckill
   │
   ├─ 前置校验（DB，低频）：券存在/已上架/平台未下架/是秒杀券/在时间窗内
   │
   ├─ ensureStockCache：Redis 无库存键则从 DB 回填 seckill:stock:{id}
   │
   ├─ Redis Lua 原子执行（lua/seckill.lua）：
   │     ① 库存 == null      → 返回 -1（未预热，前置已兜底）
   │     ② 库存 <= 0         → 返回 1（售罄）
   │     ③ SISMEMBER 已购集合 → 返回 2（一人一单）
   │     ④ DECR 库存 + SADD 用户 → 返回 0（预扣成功）
   │     ★ 整个脚本在 Redis 单线程内原子执行，不存在"检查与扣减之间的空隙"
   │
   ├─ code=1 → 抛"手慢了，已被抢光"；code=2 → 抛"每人限购一单"
   │
   └─ code=0 → RabbitMQ 发消息（削峰）
                 → 消费者 SeckillOrderConsumer 异步落库：
                       @Transactional createVoucherOrderTx()
                         ① 校验券状态与时间窗
                         ② voucherMapper.cutStock(id)  ← UPDATE ... SET stock=stock-1 WHERE id=? AND stock>0
                         ③ INSERT tb_voucher_order（user_id+voucher_id 唯一索引兜底）
                 → 成功：WebSocket 推 SECKILL_RESULT 给用户
                 → 失败/异常：消息进死信队列 → SeckillDeadConsumer 回补 Redis 库存 + 移除已购标记
```

```
【Redisson 对照组：lua-enabled=false】
   RLock lock = redisson.getLock("smartlife:seckill:lock:" + voucherId);
   lock.lock();                                  ← 看门狗自动续期 30s
   try {
       if (已购) return 2;
       if (Redis 库存 <= 0) return 1;
       DECR 库存 + SADD 用户;
       return 0;
   } finally { lock.unlock(); }
   → 后续同样走 MQ 异步落库
```

**为什么要保留两套？** 压测对比才是面试里最硬的数据：Lua 方案把"检查+扣减"压进一次 Redis 往返，Redisson 方案每次抢购都要抢锁 + 网络往返 + 锁续期开销，吞吐差距可量化。用 `.env.prod` 里一个开关就能切换（`SECKILL_LUA_ENABLED`），`deploy.sh` 之外无需改代码。

### 1.3 四层防超卖（从外到内）

| 层 | 位置 | 作用 |
|---|---|---|
| ① Lua 原子预扣 | Redis | 在内存里挡住 99% 的并发，保证"不超发" |
| ② Redis 一人一单集合 | `seckill:user:{voucherId}` Set | 挡住同用户重复抢（脚本内 SISMEMBER） |
| ③ DB 条件扣减 | `UPDATE tb_voucher SET stock=stock-1 WHERE id=? AND stock>0` | 即使 Redis 被清/重启，DB 也不会卖超 |
| ④ DB 唯一索引 | `uk_user_voucher (user_id, voucher_id)` | 一人一单的**最终防线**，并发重复插入直接被拒 |

> 面试这样答："Redis 是性能层，DB 是正确性层。任何一层失效都不能导致资损。"

### 1.4 三端改造给秒杀带来的新逻辑

#### ① 平台可以强制下架券（治理权）

```java
// VerifyService/OrderService 的读取路径都加了 audit_status 过滤
.eq(Voucher::getStatus, 1)        // 商家自主上架
.eq(Voucher::getAuditStatus, 1)   // 平台未强制下架 ★ 新增
```

```java
// grabSeckill 前置校验（VoucherService）
if (voucher.getAuditStatus() != null && voucher.getAuditStatus() != 1) {
    throw new BusinessException("该券已被平台下架");

```

管理端 `POST /admin/voucher/{id}/audit?auditStatus=0` → `VoucherService.changeAuditStatus()` → 立即 `evictCache(shopId)` 清掉店铺券列表缓存，用户端秒级不可见。

#### ② 秒杀券只能由"自己店铺"的商家创建

```java
@PostMapping("/merchant/voucher/save")
public Result<Void> voucherSave(@RequestBody Voucher voucher) {
    LoginUser user = RoleGuard.requireShopOperator();
    Shop shop = merchantService.resolveOperateShop(user, voucher.getShopId(), true);  // 必须已过审
    voucher.setShopId(shop.getId());          // ★ 强制归属，防伪造
    if (voucher.getId() != null) {
        Voucher exists = voucherService.getById(voucher.getId());
        merchantService.assertShopOwnership(exists.getShopId(), user.isAdmin() ? null : user.getId());
        voucher.setSold(exists.getSold());    // 防前端篡改已售数量
    }
    voucherService.adminSave(voucher);
    return Result.ok();
}
```

注意最后那行：`sold` 由服务端从库里读出来回填，**不允许前端传**。否则商家可以把 `sold` 改成 0 来"重置销量"，甚至影响库存对账。

#### ③ 秒杀库存缓存与 DB 的同步责任

`VoucherService.adminSave()`（商家端保存券）会：
```java
if (voucher.getType() == Voucher.TYPE_SECOND_KILL) {
    redis.delete(seckillStockKey(voucher.getId()));                       // 先删
    if (voucher.getStock() != null && voucher.getStock() > 0)
        redis.opsForValue().set(stockKey, String.valueOf(voucher.getStock()));  // 再按新库存写入
}
evictCache(voucher.getShopId());    // 店铺券列表缓存 + 秒杀场次列表缓存
```

所以商家在商家端"改一下时间窗/库存"，用户端秒杀立刻按新值走——这就是 README 里"改秒杀时间：商家端→优惠券管理→编辑券→保存即同步 Redis"的实现。

### 1.5 代价与坑

| 坑 | 表现 | 处理 |
|---|---|---|
| Redis 库存与 DB 不一致 | 提示"手慢了"但 DB 还有库存 | `DataInitRunner` 启动回填 + 商家重存券；生产应加对账任务 |
| MQ 不可用 | 预扣成功但下单失败（券被"吃掉"） | 死信队列回补；生产建议本地消息表 / 事务消息 |
| 消费失败重复投递 | 重复下单 | 唯一索引 + `countByUserAndVoucher` 幂等判断 |
| 消费者并发过大 | DB 压力反弹 | `prefetch=1` + `concurrency=2~8` 限流，这正是"削峰"的本意 |
| Lua 脚本写错 | 库存扣了但标记没写（或反之） | Lua 脚本内所有分支必须同时处理"库存"和"已购集合"；本项目脚本见 `resources/lua/seckill.lua` |

## 模块二：订单履约链路（三端协作）

### 2.1 状态机

```
                    ┌──────────────── 用户取消 / 超时自动取消（回补库存） ──────────┐
                    ▼                                                        │
   1 待支付 ──支付──► 2 已支付/待接单 ──商家接单──► 3 已接单 ──商家配送──► 4 配送中 ──商家完成──► 5 已完成
        │                    │                                                                    
        │                    └── 商家/平台取消（回补库存）──► 6 已取消                              
        └── 15 分钟未支付，OrderTimeoutTask 自动取消 ──► 6 已取消（回补库存）
```

| 流转 | 触发方 | 代码 |
|---|---|---|
| 1→2 | 用户支付 | `OrderService.pay()` |
| 2→3 | **商家接单** | `OrderService.accept(orderId, merchantId)` |
| 3→4 | **商家发货** | `OrderService.deliver(orderId, merchantId)` |
| 4→5 | **商家完成** | `OrderService.finish(orderId, merchantId)` |
| 1→6 | 用户取消 | `cancelByUser()` |
| 2→6 / 1→6 | **商家/平台取消** | `cancelByMerchant(orderId, merchantId)` |
| 1→6 | 定时任务 | `autoCancel(order)` |

所有流转都过一个私有方法：

```java
private void transit(Long orderId, Long merchantId, int from, int to, String msg) {
    Orders order = ordersMapper.selectById(orderId);
    if (order == null) throw new BusinessException("订单不存在");
    assertOwnership(order, merchantId);        // ★ 三端隔离：商家只能动自己店的订单
    if (order.getStatus() != from) throw new BusinessException("订单状态已变更，请刷新");
    order.setStatus(to);
    ordersMapper.updateById(order);
    pushStatus(order.getUserId(), orderId, to, msg);   // 只推给下单用户
}
```

### 2.2 为什么状态机要"带上前置状态校验"

```java
if (order.getStatus() != from) throw new BusinessException("订单状态已变更，请刷新");
```

- 防**重复点击**：商家连点两次"接单"，第二次因为状态已变成 3 而被拒；
- 防**乱序操作**：还没接单就点"完成"会被拒；
- 更严谨的做法是 `UPDATE ... WHERE id=? AND status=?` 的 CAS 更新（受影响行数=0 即失败），本项目用"读-判-写"配合单机事务，多实例下建议改 CAS（见手册④）。

### 2.3 下单：库存扣减与购物车

```java
@Transactional(rollbackFor = Exception.class)
public OrderVO create(Long userId, OrderCreateDTO dto) {
    Shop shop = shopMapper.selectById(dto.getShopId());
    if (shop == null) throw new BusinessException("店铺不存在");
    // ★ 三端新增：店铺未过审 / 休息中，用户端直接不能下单
    if (!RoleConstants.visibleToUser(shop)) throw new BusinessException("该店铺当前休息中或未通过审核，暂不接单");

    // 第一遍：校验商品归属与在售状态 + 算金额（纯内存，不加锁）
    // 第二遍：条件扣减库存 WHERE stock >= n（原子 SQL，防超卖）+ 写明细快照 + 清购物车对应项
}
```

两个关键设计：

1. **条件更新防超卖**：`UPDATE tb_product SET stock = stock - #{count}, sales = sales + #{count} WHERE id = #{id} AND stock >= #{count} AND status = 1`，受影响行数 0 → 抛"库存不足"并整体回滚。
2. **两遍遍历**：第一遍只校验与计算，避免"边校验边扣减"导致部分商品已扣、后面失败难回滚（虽然事务能兜，但少做事更清晰）。

购物车用 Redis Hash（`cart:{userId}`，field=productId，value=数量），下单成功后 `redis.opsForHash().delete(cartKey, productId)` 逐项清理。

### 2.4 三端在订单链路里的分工

| 动作 | 用户端 | 商家端 | 管理端 |
|---|---|---|---|
| 下单 | ✅ `/order/create` | — | — |
| 支付 | ✅ `/order/{id}/pay` | — | — |
| 接单/配送/完成 | — | ✅ `/merchant/order/{id}/accept\|deliver\|finish` | ✅ 兜底（客服介入） |
| 取消 | ✅ 仅待支付 | ✅ 待支付/已支付 | ✅ 兜底 |
| 查看 | ✅ 仅自己的（`/order/mine`） | ✅ 仅本店（`/merchant/order/page`） | ✅ 全平台（`/admin/order/page`） |

## 模块三：多端 WebSocket 实时推送

### 3.1 会话管理：按角色与店铺分桶

```java
// ws/WsSessionManager.java
private final Map<Long, Set<WebSocketSession>> userSessions     = new ConcurrentHashMap<>();  // userId → 会话
private final Map<Long, Set<WebSocketSession>> merchantSessions = new ConcurrentHashMap<>();  // merchantId → 会话
private final Set<WebSocketSession>            adminSessions    = new CopyOnWriteArraySet<>();

public void register(LoginUser user, WebSocketSession session) {
    if (user.isAdmin())          adminSessions.add(session);
    else if (user.isMerchant())  merchantSessions.computeIfAbsent(user.getId(), k -> new CopyOnWriteArraySet<>()).add(session);
    else                         userSessions.computeIfAbsent(user.getId(),  k -> new CopyOnWriteArraySet<>()).add(session);
}
```

为什么用 `ConcurrentHashMap<Long, Set>` + `CopyOnWriteArraySet`：多端登录（同一账号多标签页）+ 并发注册/断开，读写比极高（连接建立是低频、广播是高频）。

### 3.2 消息类型与路由

| 类型 | 生产者 | 消费者 | 触发点 |
|---|---|---|---|
| `NEW_ORDER` | 用户支付成功 | **该订单所属店铺的商家** | `OrderService.pay()` |
| `ORDER_STATUS` | 订单状态流转 | **下单用户** | `transit()` / `cancelAndRestore()` |
| `SECKILL_RESULT` | MQ 消费者 | **抢券用户** | `SeckillOrderConsumer` |

```java
// OrderService.pay() —— 新订单只推给这家店的商家
Shop shop = shopMapper.selectById(order.getShopId());
data.put("merchantId", shop == null ? null : shop.getMerchantId());
MessagePusher.pusher().newOrderToMerchant(shop == null ? null : shop.getMerchantId(), data);
```

```java
// MessagePusher
public void newOrderToMerchant(Long merchantId, Map<String, Object> data) {
    if (merchantId == null) return;
    sessionManager.sendToMerchant(merchantId, wrap(TYPE_NEW_ORDER, data));
}
```

> 对比改造前：`broadcastToMerchant()` 把新单推给**所有**管理端连接。店铺一多，A 店老板被 B 店订单刷屏，管理端更是噪音爆炸。这是三端改造中最直观的一处收益。

### 3.3 握手鉴权（浏览器 WebSocket 不能自定义 Header）

```javascript
// 前端 frontend/src/utils/ws.js
socket = new WebSocket(`${proto}://${window.location.host}/api/ws?token=${encodeURIComponent(user.token)}`)
```

```java
// 后端 WsHandshakeInterceptor：从 query 里取 token 校验，成功则放入 attributes
LoginUser user = jwtUtil.parse(value);
if (user != null) { attributes.put("user", user); return true; }
return false;
```

三个细节：

1. `HandshakeInterceptor` 只负责握手鉴权，`WebSocketHandler` 从 `session.getAttributes().get("user")` 取身份；
2. 前端心跳每 30s 发一次 `ping`，防止中间层（Nginx/云 SLB）空闲断连；
3. Nginx 必须配置 `Upgrade`/`Connection` 头与长 `proxy_read_timeout 3600s`，否则握手失败或 60s 被切断（见 `frontend/nginx.conf`）。

### 3.4 前端按角色消费

```javascript
// utils/ws.js dispatch()
if (type === 'ORDER_STATUS')  { if (user.isUser)     ElNotification(...); bus.emit('ORDER_STATUS', data) }
if (type === 'NEW_ORDER')     { if (user.isMerchant) ElNotification({title:'🔔 新订单提醒', ...}); bus.emit('NEW_ORDER', data) }
if (type === 'SECKILL_RESULT'){ if (user.isUser)     ElNotification(...); bus.emit('SECKILL_RESULT', data) }
```

商家端 `MerchantLayout` 监听 `NEW_ORDER` → 若当前在订单页，`bus.emit('MERCHANT_RELOAD_ORDERS')` 让列表自动刷新，体验上像"实时工单"。

### 3.5 代价与更优方案

| 现状 | 代价 | 更优 |
|---|---|---|
| 单实例内存存会话 | 多实例部署时，A 实例推不到连在 B 实例上的用户 | Redis Pub/Sub 或 MQ 广播 + 各实例本地投递；或网关层做粘性会话 |
| 无离线消息 | 用户不在线时状态变更丢失 | 前端拉取兜底（本项目列表页刷新即可）+ 生产可加离线消息表 |
| 明文 ws:// | 无域名场景下可接受 | 接域名后上 wss://（前端已按 `location.protocol` 自动切换） |

## 模块四：优惠券领取与核销（三端职责划分）

### 4.1 普通券领取：Redisson 分布式锁

```java
public void grabNormal(Long userId, Long voucherId) {
    RLock lock = redisson.getLock(NORMAL_LOCK_PREFIX + voucherId);
    lock.lock();
    try {
        voucherOrderService.createVoucherOrderTx(userId, voucherId);   // DB 条件扣减 + 唯一索引
    } finally { lock.unlock(); }
}
```

为什么普通券不像秒杀券那样上 Lua + MQ：**流量级别不同**。普通券是"随时可领、库存充足（99999）"，用分布式锁互斥足够；秒杀券是瞬时高并发，才需要 Lua 预扣 + MQ 削峰。**按流量分级选方案**是很好的面试答法。

### 4.2 券订单的三个视角

| 视角 | 接口 | 数据范围 |
|---|---|---|
| 用户 | `GET /voucher/order/my` | `WHERE user_id = 我` |
| 商家 | `GET /merchant/voucher/order/page` | `WHERE shop_id = 我的店`（并返回领券人昵称，便于到店对账） |
| 平台 | 暂无独立接口 | 通过审计日志与店铺治理覆盖 |

商家核销：

```java
public void merchantUse(Long shopId, Long orderId) {
    VoucherOrder order = voucherOrderMapper.selectById(orderId);
    if (order == null || !shopId.equals(order.getShopId()))
        throw new BusinessException("该券不属于您的店铺");     // ★ 归属校验
    if (order.getStatus() != VoucherOrder.STATUS_UNUSED)
        throw new BusinessException("该券已被使用或已过期");
    order.setStatus(VoucherOrder.STATUS_USED);
    order.setUseTime(LocalDateTime.now());
    voucherOrderMapper.updateById(order);
}
```

前端 `views/merchant/Redeem.vue`：待核销列表 + 二次确认弹窗 + 核销统计卡（累计发放/已核销/待核销）。

> 注意用户端的 `useVoucher(orderId, userId)` 是"演示自助核销"，真实业务必须由商家核销（否则用户自己就能把券用掉，商家对不上账）。这正是三端改造要修正的**业务流程错误**——现在两端都有核销能力，但商家的才是业务正确的路径。

```java
// service/ChatService.java —— 未读数走 idx_to_read (to_id, read_flag) 联合索引
// 前端 UserLayout 每 6s 轮询 /chat/contacts 汇总未读数（导航红点）
```

为什么轮询而不是 WebSocket：私信是**低频、弱实时**场景，6s 轮询实现成本极低；WebSocket 已用于订单这类强实时链路。真要做 IM 需要"会话表 + 消息表 + 已读位点 + 推送"，成本陡增（见手册④）。
