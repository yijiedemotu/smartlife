# 智联生活 · 项目学习手册 ④ 技术选型：为什么 & 更优方案（大表）

> 这一篇是"从会做到会讲"的关键：面试官真正想听的不是"我用了 Redis"，而是
> **"你为什么用它 / 它的代价是什么 / 如果换个场景你会怎么选"**。
>
> 表格读法：先看「本项目做法」，再看「为什么」讲收益，再看「代价/局限」准备被追问，最后用「更优/演进方案」展示技术视野。
> 三端改造相关的条目集中在 A、B、H、I 四节——这是本项目区别于其它教学项目的部分。

## A. 三端身份、权限与数据隔离（本项目特色）

| 主题 | 本项目做法 | 为什么 | 代价/局限 | 更优/演进方案 |
|---|---|---|---|---|
| 角色模型 | 单表 `tb_user.role`：1用户 / 2商家 / 3管理员 + `status` 封禁位 | 三端账号体系一致，登录/找回/封禁只需一套逻辑 | 角色硬编码，无法表达"一个账号既是买家又是卖家" | RBAC：`tb_role` + `tb_user_role` + `tb_permission`，支持多角色与细粒度权限点 |
| 商家↔店铺 | `tb_shop.merchant_id` **UNIQUE**，一商家一店 | 唯一索引把业务不变量固化进 schema，天然防并发重复建店 | 无法支持连锁（一商家多店） | `tb_merchant_shop` 关联表 + 商家端"店铺切换器"；`uk_merchant` 降级为普通索引 |
| 端侧鉴权 | 拦截器按**路径前缀**粗粒度分端 | 集中一处、新增接口只要遵守前缀约定就自动受保护 | 依赖命名约定，`/merchantx/**` 这类畸形路径会绕过判断 | 注解式 `@RequireRole(ADMIN)` + AOP；或 Spring Security 的 `antMatchers`/`@PreAuthorize` |
| 二次校验 | Service 层 `RoleGuard.requireXxx()` | 拦截器不懂业务语义；内部/定时任务调用也能得到清晰报错 | 需要在每个 Service 方法手写一行 | 自定义注解 + 拦截器统一处理（`@RequireRole`），减少样板代码 |
| **数据隔离** | `resolveOperateShop/resolveQueryShop` + `assertShopOwnership` + **服务端强制重写 shopId** | 前端传什么都不可信；即使伪造 shopId 也被改回自己的店 | 商家端所有写方法都要接入这套校验，漏一处就是越权 | MyBatis-Plus 多租户插件（`TenantLineInnerInterceptor`）自动给 SQL 拼 `merchant_id = ?`，从框架层根治 |
| 管理员代管 | 管理员进商家端需显式传 `shopId`，不传则报"请先选择店铺" | 防止管理员误操作到全平台；代管行为显式可审计 | 需要前端一个店铺选择器 + 每个接口多一个可选参数 | 独立的"代管会话"（Redis 记录 `adminId → actingShopId`），过期自动失效，更接近"sudo 模式" |
| 入驻审核 | `tb_merchant_apply` 申请单 + `/admin/apply/{id}/audit` | 审核留痕、可驳回重提、状态可追溯 | 单表存全部资质字段，字段会随业务膨胀 | 拆 `tb_merchant_profile`（资质档案）+ `tb_audit_task`（通用审批流），支持多级审批 |
| 审核幂等 | `if (apply.getStatus() != PENDING) throw` | 防重复点击/重复消息导致重复开店 | 单机事务内判重，多实例并发仍可能双开（有唯一索引兜底） | `UPDATE ... WHERE id=? AND status=0` CAS + 乐观锁版本号；或状态机引擎 |
| 审计留痕 | `tb_audit_log`（actor/action/target/detail）+ 写失败不影响主流程 | 治理行为可追责；审计是旁路，不该回滚业务 | 同库同表会与业务争抢资源；日志量大后查询慢 | 异步 MQ 落独立库/ClickHouse；或接入 ELK / 阿里云 SLS |
| 前端路由守卫 | 三端路由 + `pathRole()` 校验 + 后端下发 `homePath` | 防手滑跳错端，规则只写在后端一处 | **易被误解为安全边界**（实际可被绕过） | 保持"守卫只做体验、后端才是防线"的定位；把权限点集中在前端 store 供菜单渲染 |
| 密码存储 | 随机盐 + `sha256hex(password+salt)`，存 `salt:hash` | 防彩虹表；实现简单无依赖 | SHA-256 是**快速哈希**，GPU 爆破成本低 | BCrypt / scrypt / Argon2（自适应成本因子）；或接入统一认证（OAuth2/OIDC） |
| 会话方案 | JWT 无状态 + 双拦截器滑动续期 | 多实例零共享；续期对前端透明 | **无法主动踢人**：封禁后旧 token 在有效期内仍可用 | Redis 存会话/黑名单 + jti 撤销表；或改短 token + refresh token 双令牌 |
| 注册防提权 | 角色由接口决定（`/auth/register`→1、`/auth/register/merchant`→2），**不接受前端传 role** | 杜绝"注册成管理员"的经典漏洞 | 商家/用户注册逻辑略有重复 | 统一注册 + 服务端策略表（按注册渠道映射角色） |

## B. 平台治理与业务边界

| 主题 | 本项目做法 | 为什么 | 代价/局限 | 更优/演进方案 |
|---|---|---|---|---|
| 店铺双状态 | `audit_status`（平台）+ `open_status`（商家）分列 | 两种权限主体各管一个维度，互不覆盖 | 可见性判断要看两个字段，容易漏 | 抽 `ShopVisibilityPolicy` 策略类 + 单测覆盖所有组合 |
| 可见性口径 | `RoleConstants.visibleToUser(shop)` 单一方法，4 处复用 | 防止"用户端能搜到但点进去 404"这类口径漂移 | 静态方法，无法按场景扩展（如灰度可见） | 策略模式 + 配置开关（按用户分群可见） |
| 经营 vs 治理 | 商家端管"日常经营"（商品/券/订单），管理端管"治理与兜底" | 边界清晰，权限矩阵一眼可懂 | 平台缺少"代商家操作"以外的手段（如批量下架） | 平台侧增加批量治理工具与风控规则引擎（自动下架违规券） |
| 违规券处理 | `tb_voucher.audit_status` 平台置 0 + 清缓存 | 秒级对用户端生效，且不影响商家自己的 `status` | 两个状态列含义相近，容易混淆 | 统一为 `tb_content_status` 通用审核表，支持商品/券/评价 |
| 类目字典 | `tb_shop_type` 仅管理端可改，12h 缓存 | 平台级主数据，商家只能选不能改 | 改类目要手动清缓存（当前 `saveType` 已做） | 字典服务 + 本地缓存 + 配置中心推送失效 |

## C. 缓存与高并发读

| 主题 | 本项目做法 | 为什么 | 代价/局限 | 更优/演进方案 |
|---|---|---|---|---|
| 店铺详情 | L1 Caffeine(5s) → L2 Redis(随机TTL 20~40min) → DB | 热点数据本地命中，Redis 兜底，DB 只扛未命中 | 多实例 L1 最长 5s 不一致 | Redis Pub/Sub 广播失效；或本地只读热点 + 定时全量刷新 |
| 缓存穿透 | 布隆过滤器 + 空值标记（不存在 5min / 不可见 2min） | 拦住恶意遍历不存在的 id | 布隆不能删除；空值标记占内存 | Cuckoo Filter（可删）；或参数校验 + 限流前置 |
| 缓存击穿 | 互斥锁重建 + 双重检查 + 未抢到锁自旋 | 保证只有一个线程回源 | 自旋占用线程；锁释放要校验 token | 逻辑过期（返回旧值 + 异步重建），请求不阻塞 |
| 缓存雪崩 | TTL 随机 1200~2400s | 错峰过期 | 仍有极小概率同时失效 | 逻辑过期 + 多级缓存兜底 + 限流降级 |
| 写后一致 | `saveShop` 统一收口：失效 L1 + 删 Redis + 改 GEO + 清热点 | 所有写路径共用一处，避免遗漏 | 依赖"所有写操作都调它"的纪律 | 领域事件 + 订阅 binlog（Canal）驱动缓存失效 |
| 秒杀库存 | Redis 独立计数键 + Lua 原子操作 | 内存级并发能力，DB 不参与抢购 | 与 DB 双写，存在不一致窗口 | 库存分片（把 100 张拆成 10 个键）+ 本地库存批量扣减 |
| 分布式锁 | Redisson（看门狗续期） | 实现简单，防误删、可重入、自动续期 | 单点 Redis 失效则锁失效 | RedLock（多节点）或 etcd/ZooKeeper；业务侧仍要幂等兜底 |
| 签到 | BitMap，`sign:{userId}:{yyyyMM}`，offset=当月第几天 | 46 字节/人/年，极致省内存 | 只能存布尔；跨月连续签到要跨键查询 | 连续签到用 Redis Stream/ZSet 记录日期；或 ClickHouse 存事件流 |
| UV | HyperLogLog（`uv:{date}:{page}`） | 12KB 固定内存，0.81% 误差可接受 | 不能判单个元素、不能精确 | 精确 UV 用 BitMap（userId 为 offset）或 ClickHouse bitmap 函数 |
| 店铺类型 | Redis 缓存 12h + 写时删键 | 读多写极少，长 TTL 收益最大 | 变更后最长 12h（本项目写时已删，实际立即生效） | 配置中心 + 本地缓存 + 事件推送 |

## D. 消息队列与异步

| 主题 | 本项目做法 | 为什么 | 代价/局限 | 更优/演进方案 |
|---|---|---|---|---|
| 秒杀削峰 | RabbitMQ 主队列 + 手动 ack + `prefetch=1` + 死信队列 | 把瞬时写请求变成匀速消费，DB 压力可控 | 用户要等异步结果（前端靠 WebSocket 回执） | Kafka（更高吞吐、可回放）；或本地消息表 + 定时补偿（不依赖 MQ 可用性） |
| 消费幂等 | DB 唯一索引 + `countByUserAndVoucher` | 消息可能重复投递，必须幂等 | 依赖业务唯一键存在 | 消息去重表 + 消息 id；或 Redis SETNX 消费标记 |
| 失败补偿 | 死信队列消费者回补 Redis 库存与已购标记 | 保证"预扣成功但下单失败"不吞库存 | 补偿逻辑要幂等，且 Redis 键可能已过期 | 对账任务（定期比对 Redis 与 DB 库存）+ 告警 |
| 可靠性 | 手动 ack，异常不 ack 进死信 | 不丢消息 | 需要处理重复消费 | 生产端确认（publisher confirm）+ 消息持久化 + 镜像队列/Quorum 队列 |
| 消息内容 | 只传 `{userId, voucherId}`（`SeckillMessage`） | 消息轻量，避免与 DB 数据不一致 | 消费时要回查 DB | 传必要快照 + 版本号；或事件溯源 |

## E. 数据库与 ORM

| 主题 | 本项目做法 | 为什么 | 代价/局限 | 更优/演进方案 |
|---|---|---|---|---|
| ORM | MyBatis-Plus，`LambdaQueryWrapper` 类型安全查询 | 写 CRUD 快，SQL 可控（复杂统计用 `@Select` 手写） | 复杂动态 SQL 仍要 XML/注解；`last("LIMIT ...")` 有注入风险（本项目参数为 Integer，安全） | MyBatis-Plus 分页插件替手写 LIMIT；JOOQ 类型安全更强 |
| 金额 | `INT` 存分 | 杜绝浮点误差 | 需要前后端约定换算 | `DECIMAL(18,2)` 或 BigDecimal（Java 侧统一） |
| 库存扣减 | `UPDATE ... SET stock = stock - n WHERE stock >= n` | 单条原子 SQL，DB 层防超卖 | 高并发下会行锁竞争 | Redis 预扣 + DB 最终一致（本项目秒杀已这么做）；或库存分片 |
| 一人一单 | `UNIQUE KEY (user_id, voucher_id)` | 数据库层最终防线，任何绕过应用的写入也无效 | 与"可重复购买"业务冲突 | 加 `batch_no` 到唯一键（支持周期性重复领取） |
| 索引设计 | `idx_type_score(type_id, popularity)`、`idx_shop_status(shop_id, status)`、`idx_to_read(to_id, read_flag)` | 覆盖高频查询的过滤+排序 | 索引多了写变慢 | 用慢查询日志持续验证；必要时覆盖索引减少回表 |
| 订单快照 | 明细表存 `product_name/price` 快照 | 商品改价/改名不影响历史订单 | 数据冗余 | 事件溯源；或订单快照独立归档表 |
| 分页 | `LIMIT (page-1)*size, size` | 简单直接 | 深分页性能差（`LIMIT 100000,10` 要扫 10 万行） | 游标分页（`WHERE id < lastId ORDER BY id DESC LIMIT n`）；或搜索引擎承担列表 |
| 迁移 | `sql/init.sql`（新建）+ `sql/manual/upgrade_v2_three_end.sql`（幂等升级，动态 ALTER） | 手工可控，部署简单 | 无版本记录，容易漏执行 | Flyway / Liquibase 版本化迁移，与 CI 集成 |
| 多租户隔离 | 应用层强制 shopId（服务端重写） | 无需改 SQL，边界清晰 | 漏写一处即越权 | MyBatis-Plus 租户插件 + 拦截器自动注入；或按店铺分库分表 |

## F. 接口与规范

| 主题 | 本项目做法 | 为什么 | 代价/局限 | 更优/演进方案 |
|---|---|---|---|---|
| 响应结构 | `{code, msg, data}`，`code=1` 成功 | 前端拦截器统一处理，业务层不用关心 HTTP 状态 | HTTP 状态码与业务码混用（401/403 走 body） | RFC 7807 problem+json；或规范化业务错误码枚举 |
| 异常处理 | `@RestControllerAdvice` 统一兜底，业务异常 warn、系统异常 error + 堆栈 | 不把堆栈泄露给前端，日志留全 | 兜底文案"服务器繁忙"不利于排查（需查日志） | 加 traceId 返回给前端，与日志关联（MDC + Sleuth/SkyWalking） |
| 参数校验 | JSR-303 注解落在 DTO，`@Valid` 触发 | 声明式，Controller 无需手写 if | 复杂跨字段校验要自定义 | 自定义 ConstraintValidator + 校验分组 |
| 接口文档 | Knife4j(OpenAPI)，生产环境可开关 | 调试方便，可当接口契约 | 注解侵入代码；OpenAPI 2 (Swagger2) 略旧 | SpringDoc OpenAPI 3；或 contract-first（OpenAPI 文件生成代码） |
| 认证续期 | 响应头 `X-Auth-Refresh` 下发新 token | 前端拦截器自动刷新，用户无感 | 每个响应都要检查头 | 双令牌（access + refresh）+ 静默续期 |

## G. 前端

| 主题 | 本项目做法 | 为什么 | 代价/局限 | 更优/演进方案 |
|---|---|---|---|---|
| 应用形态 | 单仓库单应用，三套布局 + 路由守卫 | 一套依赖、一个镜像、一次构建；部署最简单 | 主包偏大（Element Plus + ECharts 全量） | 微前端（qiankun）拆分三端；或按端做多入口（Vite multi-page） |
| 路由 | Vue Router history 模式 + Nginx 回退 | URL 干净 | 需要服务端配置回退（已配） | 保持 |
| 状态管理 | Pinia，`sl_user` 持久化到 localStorage，state 全键显式声明 | 轻量、TS 友好；显式声明避免"赋值不生效"的坑 | localStorage 可被篡改（但后端才是权限边界） | 关键状态放内存 + 刷新时向后端校验角色（`/user/me/role`） |
| 请求封装 | Axios 拦截器：`code=401` 跳登录、`code=403` 回自己端、续期头刷新 | 三端统一错误处理 | 403 直接跳转略粗暴 | 细化 403 处理（提示 + 提供"申请权限"入口） |
| 实时消息 | 单 WebSocket 连接，按角色消费；心跳 30s；断线 3s 重连 | 三端共用一条连接，实现简单 | 断线期间消息丢失 | 指数退避重连 + 消息序号 + 拉取补偿 |
| 图表 | ECharts 全量引入 | 开箱即用 | 打包体积大（index chunk > 1MB） | 按需引入（`echarts/core` + 具体图表）或用 unplugin 自动按需 |
| 构建 | Vite 5 | 冷启动/HRM 快，构建快 | 生产产物仍需 gzip（已在 Nginx 配置） | 加 CDN + 长效缓存 + 预压缩（brotli） |

## H. 部署与运维

| 主题 | 本项目做法 | 为什么 | 代价/局限 | 更优/演进方案 |
|---|---|---|---|---|
| 部署形态 | 单机 docker compose 五容器 | 空服务器一条命令起全站，成本最低 | 单点故障；升级有秒级中断 | K8s / 阿里云 ACK + 多副本；或至少 `docker compose` 多机 + 云数据库 |
| 后端构建 | 镜像内 Maven 多阶段构建 | 服务器无需 JDK/Maven；产物与源码一致 | 首次构建 5~15 分钟 | CI 构建镜像推到 ACR，服务器只 pull |
| 数据库 | 容器内 MySQL + 命名卷 | 一体化，无外部依赖 | 备份/扩容靠自己；容器故障有风险 | 阿里云 RDS（自动备份/只读实例/高可用） |
| 缓存 | 容器内 Redis + AOF + `requirepass` | 有持久化有密码，够用 | 单点；`noeviction` 下内存满是写失败 | 阿里云 Tair/Redis 集群版 |
| MQ | 容器内 RabbitMQ | 秒杀削峰够用 | 单点，无镜像队列 | 阿里云 RabbitMQ/云消息队列 RocketMQ |
| 端口暴露 | 仅 frontend 暴露 80，其余绑 `127.0.0.1` | 攻击面最小 | 本机运维要 SSH 隧道 | 保持；生产再加跳板机/堡垒机 |
| 密钥管理 | `.env.prod`（`chmod 600`，git 忽略） | 简单直观 | 明文落盘，同机泄露风险 | 阿里云 KMS / Secrets Manager + 启动注入 |
| HTTPS | 无域名先用 HTTP，文档给出接域名步骤 | 空服务器可立即验收 | 明文传输 | 接入域名 + 免费证书 + 80 跳转 443（文档已写） |
| 可观测 | 文件日志 + `docker stats` + 平台看板 | 轻量够用 | 无链路追踪、无告警 | Prometheus + Grafana + Actuator/Micrometer；ELK 收日志；云监控告警 |
| 备份 | `backup-db.sh` + cron，保留 14 天 | 成本极低 | 与库同机，机器挂了备份也没了 | OSS 异地备份（脚本已留 `ossutil` 钩子）+ 定期做恢复演练 |
| 定时任务 | Spring Scheduler + Redisson 锁 | 单机/多机都安全 | 任务与 Web 应用同进程，扩容时任务也跟着扩 | 独立调度服务（XXL-JOB / SchedulerX） |

## I. 秒杀方案对比（面试高频，可量化）

| 维度 | 纯 DB（悲观锁/条件更新） | Redisson 分布式锁 | **Redis Lua + MQ（本项目默认）** |
|---|---|---|---|
| 原子性保证 | DB 行锁 | 锁互斥 | Lua 脚本在 Redis 单线程内原子执行 |
| 单次抢购开销 | 1 次 DB 往返 + 行锁等待 | 抢锁 + 业务 + 解锁（含网络往返、看门狗续期） | **1 次 Redis 往返**（EVALSHA） |
| 一人一单 | 唯一索引 | 锁内查 + 唯一索引 | Lua 内 SISMEMBER + 唯一索引 |
| 削峰能力 | 无（同步写库） | 无（同步写库） | **有**（MQ 匀速消费） |
| 前端体验 | 同步返回结果 | 同步返回结果 | 异步（需 WebSocket/轮询回执） |
| 复杂度 | 低 | 中 | 高（Lua + MQ + 死信 + 幂等） |
| 适用流量 | 低（< 100 QPS） | 中（数百 QPS） | **高（数千~数万 QPS）** |
| 本项目验证方式 | `SECKILL_LUA_ENABLED=false` 前的基线 | `SECKILL_LUA_ENABLED=false` | `SECKILL_LUA_ENABLED=true`（默认） |

> 面试话术："我没有直接说 Lua 一定更好，而是在同一套代码里留了开关，用 JMeter 对比了两种方案在同一库存（100 张）同一并发（2000 线程）下的吞吐与平均耗时，Lua 版本因为把'检查+扣减'压缩成一次 Redis 往返、并且把落库变成异步，吞吐明显更高；代价是前端要处理异步结果。具体数字我本地实测是 xxx。"

## J. 一句话取舍总结（背下来就能用）

1. **权限**：前端守卫管体验，后端三级校验管安全；能放数据库的约束（唯一索引）不要放应用层。
2. **隔离**：服务端强制重写归属字段，永远不相信前端传的 id。
3. **缓存**：本地 + Redis + DB 三层，穿透用布隆、击穿用互斥、雪崩用随机 TTL；写操作统一收口做失效。
4. **秒杀**：Redis 保性能、DB 保正确、MQ 保吞吐、唯一索引保底线。
5. **消息**：按角色与业务归属分桶推送，不做无差别广播。
6. **治理**：审核走状态机、操作留审计、双状态分权限主体。
7. **部署**：端口收敛到 1 个、密钥走环境变量、数据必须能备份能恢复。
