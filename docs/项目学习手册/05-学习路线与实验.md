## 2. 动手实验（每个都有明确预期结果）

### 实验 0：验证种子密码哈希算法（10 分钟，读 SQL 前必做）

`PasswordUtil.matches` 用的是 **`sha256hex(rawPassword + salt)`（密码在前、盐在后）**，与常见写法相反，所以手工造种子 SQL 极易搞错。

```bash
# 方式一：用 java 单文件快速验证（JDK 11+）
cat > HashTest.java <<'EOF'
import java.security.MessageDigest;
public class HashTest {
  static String hex(byte[] b){ StringBuilder sb=new StringBuilder();
    for(byte x:b) sb.append(Character.forDigit((x>>4)&0xF,16)).append(Character.forDigit(x&0xF,16));
    return sb.toString(); }
  static String sha(String s) throws Exception {
    return hex(MessageDigest.getInstance("SHA-256").digest(s.getBytes("UTF-8"))); }
  public static void main(String[] a) throws Exception {
    System.out.println("admin123   => seed:" + sha("admin123seed"));
    System.out.println("merchant123=> seed:" + sha("merchant123seed"));
    System.out.println("123456     => seed:" + sha("123456seed"));
  }
}
EOF
java HashTest.java
```

**预期**（应与 `sql/init.sql` 中的值完全一致）：

| 明文 | 哈希（拼接 `seed:` 前缀后写入 SQL） |
|---|---|
| `admin123` | `e61ea5c0115e9dc541c26b898ebb7ea8a9beab428a3e6180a10a4df35cc14080` |
| `merchant123` | `6969d4663175762598ee07b6216b3e1d007e150e6cc0e2bfd2523ff4fd3a9f37` |
| `123456` | `5f7ddeeb7625016332e4d62f529ba782312294e62c531a5b67ffd93ef04b2042` |

> 如果按常见写法 `sha256(salt + password)` 算，得到的是另一串（例如 `123456` 会得到 `7e4d2581...`），用它写种子会导致**登录失败**。

## 3. 面试题库

### 3.1 三端/多角色专题（本项目最强差异化）

**Q1：你这个项目从双端改成三端，具体改了什么？为什么必须改？**

【答】原设计里 `role=2` 的"管理员"同时是商家和平台，导致三个业务问题：① 没有店铺归属，任何管理员能改任意店铺；② 开店无门槛，没有资质审核；③ 治理动作无留痕，出问题无法追责。
改造分四层：
- **数据层**：`tb_user.role` 重定义为 1用户/2商家/3管理员 + `status` 封禁位；`tb_shop` 增加 `merchant_id`（唯一索引）与 `audit_status`/`open_status` 双状态；新增 `tb_merchant_apply`（入驻申请）与 `tb_audit_log`（操作审计）；`tb_voucher` 增加 `audit_status` 让平台能强制下架。
- **接口层**：新增 `/merchant/**`（经营）与 `/admin/**`（治理）两套接口体系，原来的 `/admin/product|voucher|order` 里"经营"的部分下沉到商家端。
- **权限层**：拦截器按路径前缀分端 + Service 层 RoleGuard + 店铺归属校验 + 服务端强制重写 shopId，四道防线。
- **消息层**：WebSocket 会话按角色和 merchantId 分桶，新订单只推给对应店铺。
【追问准备】旧数据怎么办？→ 提供幂等的 `sql/manual/upgrade_v2_three_end.sql`：先把原 role=2 提升为 3，再补列补索引，最后为历史店铺补建商家账号并绑定归属。

---

**Q2：多角色系统怎么保证权限"不走样"？**

【答】我把权限分成三层，每层解决不同问题：
1. **路径级（AuthInterceptor）**：`/merchant/**` 要 role 2 或 3，`/admin/**` 必须 role 3，`/cart /mate /chat /sign` 是用户端专属。解决"不该进来的别进来"，集中管理、新增接口只要遵守前缀约定就自动受保护。
2. **业务级（RoleGuard）**：拦截器不认识业务语义，所以 Service 里用 `RoleGuard.requireMerchant()/requireAdmin()` 再声明一次调用方身份。好处是无 Web 上下文的场景（定时任务、内部调用）会得到明确报错，而不是 NPE 或静默越权。
3. **数据级（MerchantService）**：`assertShopOwnership(shopId, merchantId)` 保证商家只能碰自己的店；写操作还**强制把 shopId 重写成自己的店铺**，所以前端伪造 shopId 也无效。
另外前端路由守卫只做体验（防手滑跳错端），我在文档里明确写了"它**不是**安全边界"——真正的权限永远在后端。

---

**Q3：商家伪造 shopId 改别人的商品，你怎么防？**

【答】三步：
```java
Shop shop = merchantService.resolveOperateShop(user, product.getShopId(), true);  // 商家分支忽略传入的 shopId
product.setShopId(shop.getId());                                                  // 强制重写归属
if (product.getId() != null) {                                                    // 改已有商品还要验原归属
    merchantService.assertShopOwnership(productService.getById(product.getId()).getShopId(),
                                        user.isAdmin() ? null : user.getId());
}
```
第一句保证"新建时只能建在自己店"，第二句保证"改不了别人的商品"。冒烟测试里有一条断言专门测这个：传 `shopId=2` 保存，商品最终落在自己的店铺 1。

---

**Q4：一个商家一个店铺，为什么要用唯一索引而不是代码判重？**

【答】代码判重有并发窗口：两个请求同时查到"该商家没有店铺"，然后各插一条，就出现了两个店铺，后续按 merchantId 查会不确定。`uk_merchant (merchant_id) UNIQUE` 是数据库层的最终防线，任何写入路径（包括将来别人绕过 Service 直连 DB）都破坏不了这个不变量。
代价我也清楚：这样无法支持"一个商家多店（连锁）"，那时需要改成 `tb_merchant_shop` 关联表，把唯一索引降级为普通索引，前端加店铺切换器。这是一次明确的重构点，不是意外。

---

**Q5：管理员要帮商家处理订单，这个"代管"怎么设计才安全？**

【答】三点：
1. **必须显式指定店铺**：管理员调商家端接口时如果没传 `shopId`，`resolveOperateShop` 直接抛"请先选择要管理的店铺"，避免误操作到全平台（这是一个很容易踩的坑，因为"不传=全部"在查询场景是合理的，在写场景是危险的）。
2. **前端有明确的代管入口**：管理端店铺列表点"代管经营"，把选中店铺写入 Pinia 再跳商家端；商家端布局顶部有店铺选择器，切换时通过事件总线广播给所有子页面。
3. **代管行为仍走同一套 Service**：`currentMerchantScope()` 对管理员返回 `null`（不限制归属），对商家返回自己的 userId，`transit()` 里 `assertOwnership(order, null)` 直接放行——一套代码同时服务商家和平台代管，没有重复实现，也就没有"代管路径漏校验"的风险。

---

**Q6：店铺为什么要有"审核状态"和"营业状态"两个字段？**

【答】因为这两个维度的**权限主体不同**：`audit_status`（0待审/1通过/2驳回/3停业）由平台控制，`open_status`（1营业/0休息）由商家控制。
- 商家临时打烊不该走平台审批（否则每次歇业都要等审核）；
- 平台停业整顿也不能让商家自己改回来；
- 用户端可见性 = 两者同时满足，我把它收敛成 `RoleConstants.visibleToUser(shop)` 一个方法，在详情缓存重建、分页查询、热点列表、启动索引重建四处复用，防止口径漂移（比如"列表里有但点进去 404"）。

---

**Q7：审核通过后自动开店，怎么保证不重复开？**

【答】三层：
1. 申请单状态判断：`if (apply.getStatus() != PENDING) throw "该申请单已处理"`；
2. 商家侧提交侧：存在待审核单时 `submitApply` 直接拒绝，从源头减少重复；
3. `tb_shop.uk_merchant` 唯一索引兜底：即使并发双开，第二条插入也会被数据库拒绝。
在单机事务下这三层足够；多实例高并发更严谨的做法是把状态更新改成 CAS（`UPDATE tb_merchant_apply SET status=1 WHERE id=? AND status=0`，受影响行数=0 就说明别人已处理），这样连"两个管理员同时点通过"也能精确只有一个成功。

---

**Q8：平台下架一张违规优惠券，怎么保证用户端立刻买不到？**

【答】`VoucherService.changeAuditStatus()` 把 `audit_status` 置 0 后调用 `evictCache(shopId)` 清掉店铺券列表缓存和秒杀场次列表缓存。同时**所有读取路径都加了 `audit_status=1` 过滤**：店铺券列表、秒杀场次列表、秒杀抢购前置校验、券订单创建校验。所以即使缓存没清干净，DB 查询和业务校验也会拦住。
这是"缓存失效 + 查询条件"双保险的思路——缓存是第一道性能优化，查询条件才是正确性保证。

---

**Q9：商户数据和用户数据放一个库，怎么防止商家看到用户隐私？**

【答】几点：
1. 商家端能看到的用户信息是**最小必要**：券核销列表只给昵称（用于到店对账），订单列表给昵称，不给手机号、地址等（`UserService.toVO(user, withPhone)` 控制，`withPhone=false` 时手机号脱敏）；
2. 商家端所有查询强制带 `shop_id = 自己的店`，天然拿不到其他店铺的订单/券；
3. 平台端查账号列表也走脱敏 VO，不返回密码，手机号脱敏；
4. 数据库账号层面目前是单一账号（简化部署），生产更严的做法是给商家端用独立只读账号 + 视图，或用 MyBatis 多租户插件从 SQL 层强制隔离。

---

**Q10：如果要做"一个商家多个店铺"（连锁品牌），你怎么改？**

【答】
- **数据层**：新增 `tb_merchant_shop(merchant_id, shop_id)` 关联表，去掉 `tb_shop.uk_merchant` 唯一索引；`tb_shop.merchant_id` 可保留为"主店"或直接删除。
- **权限层**：`resolveQueryShop/resolveOperateShop` 从"取唯一店铺"改成"校验 shopId 属于当前商家"（一次 exists 查询，可缓存）。
- **接口层**：商家端所有接口的 `shopId` 从"可选（管理员专用）"变成"必填（所有角色）"。
- **前端**：商家端顶部店铺选择器对所有角色可见（现在只有管理员能看到）。
- **治理层**：入驻审核的粒度从"商家"变成"商家+店铺"，`tb_merchant_apply` 增加"是否为新店"标识。
大概影响 5~8 个文件，属于可预期的重构。

### 3.2 高并发与缓存（经典高频）

**Q11：缓存穿透、击穿、雪崩的区别与各自解决方案？**
【答】穿透是查**不存在**的数据（恶意遍历 id），对策：布隆过滤器前置 + 空值缓存；击穿是**热点 key 恰好过期**，瞬时全打到 DB，对策：互斥锁重建或逻辑过期；雪崩是**大量 key 同时过期**，对策：TTL 随机化 + 多级缓存兜底 + 熔断限流。
【易错】别说"布隆过滤器防击穿"，它是防穿透。本项目的组合在 `ShopService.queryById`：布隆 → 空值标记 → 互斥锁 → 随机 TTL。

**Q12：缓存与数据库一致性怎么保证？**
【答】Cache Aside：读未命中查库回填；写先更新 DB 再**删缓存**（不是更新缓存，避免并发写时旧值覆盖新值）。本项目在 `ShopService.saveShop` 里统一收口做失效（L1 invalidate + 删 Redis + 改 GEO + 清热点列表）。
更严格可用延迟双删或订阅 binlog（Canal）。要承认强一致做不到，只做最终一致并缩短不一致窗口。

**Q13：为什么本地缓存只有 5s？**
【答】L1 的收益是省掉一次 Redis 网络往返，代价是多实例不一致。5s 是"收益明显 + 不一致窗口可接受"的折中。三端改造后这个窗口变得更敏感（平台停业要求秒级生效），所以我在 `saveShop` 里加了 `localCache.invalidate(id)` 主动失效，不靠 TTL 兜。

**Q14：互斥锁重建为什么需要双重检查？**
【答】抢到锁的线程在查 DB 前要再看一次缓存：可能在它"抢锁成功"和"开始查 DB"之间，另一个线程已经释放锁并写好了缓存。没有双重检查就会重复查库。另外释放锁要校验 token（`if (token.equals(redis.get(lockKey))) delete`），防止误删别人的锁。

**Q15：BitMap 和 HyperLogLog 分别适合什么场景？**
【答】BitMap 适合"低基数、布尔、需要判断单个位"的场景（签到：一年 46 字节/人）；HyperLogLog 适合"高基数、只需基数估计"的场景（UV：12KB 固定内存，0.81% 误差）。反过来用都不行：BitMap 做 UV 需要 userId 当 offset，稀疏时内存爆炸；HLL 做签到无法判断"今天签了没"。

### 3.3 秒杀与消息队列

**Q16：秒杀怎么防超卖？**
【答】四层：① Redis Lua 原子预扣（内存层挡住并发）；② Redis Set 一人一单；③ DB `UPDATE ... WHERE stock >= n` 条件扣减；④ `uk_user_voucher` 唯一索引。原则是"Redis 保性能、DB 保正确"，任一层失效都不会资损。

**Q17：为什么要用 RabbitMQ？不用行不行？**
【答】不用也能保证不超卖（Lua + DB 足够），但用户请求要同步等 DB 写入，QPS 上不去、前端容易超时。MQ 把"抢到名额"和"落库"解耦：用户被快速告知"抢单成功，正在创建订单"，落库按消费者能力匀速进行（`prefetch=1`、`concurrency=2~8`），这就是削峰。代价是前端要处理异步结果（本项目用 WebSocket 回执）。

**Q18：消息消费失败了怎么办？**
【答】手动 ack + 死信队列：消费者抛异常不 ack，消息进 DLX，`SeckillDeadConsumer` 回补 Redis 库存和用户标记（幂等：先判断库存键是否存在）。同时 DB 唯一索引保证即使重复消费也不会重复下单。

**Q19：你保留了 Redisson 锁方案，为什么？**
【答】为了做对照实验。同一套代码用 `SECKILL_LUA_ENABLED` 开关切换，可以在相同库存和并发下对比两种实现的吞吐与耗时，这比空谈"Lua 更快"有说服力。另外它也是降级预案：如果 Lua 脚本环境出问题，可以临时切回锁方案。

---

### 3.4 订单与实时推送

**Q20：订单状态机为什么要校验前置状态？**
【答】防重复点击和乱序操作：商家连点两次接单，第二次因为状态已是 3 而被拒。更严谨的是 CAS 更新（`UPDATE ... WHERE id=? AND status=?`，受影响行数 0 即失败），本项目"读-判-写"在单机事务下够用，多实例建议改 CAS。

**Q21：新订单为什么不能广播给所有商家？**
【答】广播是改造前的行为：所有管理员/商家连接都收到，店铺一多就是噪音（A 店老板被 B 店订单刷屏）。现在 `WsSessionManager` 按 merchantId 分桶，`newOrderToMerchant(shop.getMerchantId(), data)` 只推给该店铺的商家。实测方式是同时开两个不同商家的商家端，只有对应那家弹提醒。

**Q22：WebSocket 在浏览器里怎么带 token？**
【答】浏览器 WebSocket API 不支持自定义 Header，所以用 query 参数：`ws://host/api/ws?token=xxx`，后端在 `WsHandshakeInterceptor.beforeHandshake` 里解析校验，成功才放行并把用户放进 session attributes。Nginx 侧必须透传 `Upgrade`/`Connection` 头并放大 `proxy_read_timeout`（本项目设 3600s），否则 60s 就被切断。

### 3.5 工程化与部署

**Q23：服务器上要装 JDK 和 Maven 吗？**
【答】不需要。后端 Dockerfile 用多阶段构建：`maven:3.9-eclipse-temurin-17` 阶段编译打包，`eclipse-temurin:17-jre` 阶段只跑 jar。服务器只需要 Docker，构建产物与源码一致，也避免"服务器环境不一致"的经典问题。

**Q24：为什么只暴露 80 端口？**
【答】因为只有前端 Nginx 需要面向公网，后端和三个中间件都在 Docker 内网，端口绑定到 `127.0.0.1`，安全组也只放行 80（和 22）。运维需要连数据库时用 SSH 隧道（`ssh -L 3306:127.0.0.1:3306`）。这样攻击面最小，也不需要为每个中间件单独做防火墙规则。

**Q25：MySQL 容器重启后数据会丢吗？初始化脚本会不会重复执行？**
【答】不会丢：数据在命名卷 `smartlife-mysql-data` 里。`sql/init.sql` 只在**数据目录为空时**由 MySQL 官方镜像的 entrypoint 执行一次，之后重启/重部署都不会重复执行（`docker compose down` 不删卷，`down -v` 才会）。要彻底重置需显式 `docker volume rm smartlife-mysql-data`。

**Q26：怎么保证发版不丢数据？**
【答】`scripts/backup-db.sh` 用 `mysqldump --single-transaction` 做一致性快照（不锁表），可挂 cron 每日执行并自动清理 14 天前备份；恢复用 `restore-db.sh`（先停后端写入再还原）。升级前先备份是硬性习惯，回滚时 `git checkout` 上一个提交 + 还原备份。

### 3.6 开放题

**Q27：这个项目如果上线真实运营，你觉得最大的三个风险是什么？**
【答】
1. **单点部署**：所有中间件和后端都在一台机器上，机器故障即全站不可用。应优先把 MySQL 换成 RDS、Redis 换 Tair，后端多副本 + SLB。
2. **无支付与对账**：现在是"模拟支付"，真实业务需要接支付网关 + 回调验签 + 幂等 + 每日对账，这部分的复杂度远高于下单本身。
3. **无风控与限流**：秒杀只靠 Redis 原子性和一人一单，缺少 IP/设备维度的限流、验证码、黄牛防控。真实秒杀必须有网关层限流和风控前置。

**Q28：如果让你给这个项目加一个功能，你会加什么？为什么？**
【答】我会加**商家侧的结算与对账**（因为它是三端闭环里唯一缺失的钱流环节）：每笔已完成订单生成结算流水（金额/平台佣金/商家应收），商家端有结算单和提现申请，管理端有审核与打款记录。技术上要引入状态机 + 幂等 + 事务，并且复用现成的 `tb_audit_log` 做审核留痕，能验证我对"多角色资金流"的完整设计能力。
