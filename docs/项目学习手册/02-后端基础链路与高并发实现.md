## 模块一：三端认证与权限体系

### 1.1 怎么做的：一次三端请求的完整链路

```
浏览器每次请求（除 /auth/login、/auth/register*、/ws、doc 等白名单）
   │  Header: Authorization: Bearer <JWT>
   ▼
AuthInterceptor.preHandle（一级拦截器）
   ① resolveToken：从 Header 取 Bearer token
   ② jwtUtil.parse 校验 HS256 签名与过期时间 → LoginUser{id, role, nickname}
   ③ 剥离 context-path 得到业务路径，按前缀做端侧鉴权：
        /merchant/**                 → 需要 role=2 或 role=3（管理员可代管）
        /admin/**                    → 需要 role=3
        /cart /mate /chat /sign      → 用户端专属，role=3 不可调
   ④ UserContext.set(loginUser)     ← ThreadLocal 线程隔离
   ▼
TokenRefreshInterceptor（二级拦截器）
   剩余有效期 < 30min → 重新签发并写入响应头 X-Auth-Refresh
   ▼
RoleGuard.requireXxx()（Service 层）
   再声明一次"本方法允许谁调用"，与拦截器形成双保险
   ▼
MerchantService.resolveXxxShop()（数据层）
   商家只能碰自己的店铺；管理员需显式指定 shopId
   ▼
afterCompletion → UserContext.clear()   ← 必须清理
```

### 1.2 为什么这么做

| 问题 | 朴素做法 | 问题所在 | 本项目 |
|---|---|---|---|
| 三端权限 | 每个 Controller 里写 `if (role != 3) throw` | 散落、易漏、新增接口容易忘 | 拦截器按路径前缀集中鉴权 + RoleGuard 二次声明 |
| 用户身份传递 | 每个方法都传 `userId/role` 参数 | 签名臃肿、Service 与 Web 层耦合 | ThreadLocal（`UserContext`），请求结束清理 |
| 前端越权跳转 | 只靠前端路由守卫 | 手改 localStorage 就能进管理端页面 | 后端拦截器才是真正防线，前端守卫只做体验 |
| 商家越权改他人数据 | 只校验路径 | 商家能调 `/merchant/product/save` 但传别人的 shopId | 归属校验 + **服务端强制重写 shopId** |

### 1.3 代价与坑

| 坑 | 后果 | 本项目如何规避 |
|---|---|---|
| ThreadLocal 未清理 | Tomcat 线程复用导致**身份串号**（A 用户读到 B 用户身份） | `afterCompletion` 里 `UserContext.clear()`；手册①§2.1 有完整链路 |
| `getRequestURI()` 含 context-path | 前缀匹配错误、鉴权失效 | 先 `substring(getContextPath().length())` |
| 拦截器无法识别"业务归属" | 商家能操作他人订单/商品 | Service 层 `assertShopOwnership()` 兜底 |
| 角色写死在多处 | 改角色编码要全局搜 | 统一 `LoginUser.ROLE_*` + `RoleConstants` |
| JWT 无法主动踢人 | 封禁后 token 仍有效 | 登录时校验 `tb_user.status`；封禁后**下次登录**被拒（进阶方案见手册④） |

| 功能 | 文件 |
|---|---|
| 一级拦截器（三端路径鉴权 + ThreadLocal） | `security/AuthInterceptor.java` |
| 二级拦截器（Token 滑动续期） | `security/TokenRefreshInterceptor.java` |
| Service 层角色守卫 | `security/RoleGuard.java` |

## 模块二：多级缓存治理（穿透 / 击穿 / 雪崩）

### 2.1 怎么做的

```
ShopService.queryById(id)  —— 店铺详情，全项目 QPS 最高的读接口
    │
    ├─ L1 Caffeine 本地缓存（maximumSize=5000，expireAfterWrite=5s）  → 命中直接返回
    ├─ 布隆过滤器 mightContain(id)？ 否 → 直接返回 null（拦住恶意遍历不存在的 id）
    ├─ L2 Redis cache:shop:{id}
    │      · 命中 "EMPTY" 标记 → 返回 null（空值缓存，防穿透）
    │      · 命中 JSON        → 回填 L1 并返回
    └─ 未命中 → 互斥锁重建 rebuildByMutex(id, key)
           ① SETNX lock:shop:{id} token EX 10
           ② 抢到锁：双重检查 Redis → 查 DB → 不可见写 EMPTY(2min) / 可见写详情(随机 TTL 20~40min)
           ③ finally 比对 token 再删锁（防误删他人锁）
           ④ 没抢到锁：自旋 10×30ms 等他人重建；超时兜底查库（保证最终一致）
```

四个经典问题的对应手段：

| 问题 | 触发场景 | 手段 |
|---|---|---|
| 缓存穿透 | 查**不存在**的数据（恶意遍历 id） | 布隆过滤器前置拦截 + 空值标记（5min / 不可见 2min） |
| 缓存击穿 | **热点 key 恰好过期**，瞬时全打到 DB | 互斥锁重建 + 双重检查 |
| 缓存雪崩 | **大量 key 同时过期** | TTL 随机化 1200~2400s |
| 缓存一致性 | 商家改价/平台停业后读到旧值 | 写后失效：`localCache.invalidate` + 删 Redis + 重建 |

### 2.2 三端改造带来的新问题（重点）

"平台停业一家店"这件事，在双端时代不存在（管理员就是商家）。三端之后必须保证**状态变化立刻对用户端生效**：

```java
// ShopService.saveShop：所有店铺写路径的唯一收口
localCache.invalidate(shop.getId());                       // L1 立即失效（不能只靠 5s TTL）
if (RoleConstants.visibleToUser(shop)) {
    writeDetail(shop); addToGeo(shop); bloom.put(shop.getId());
} else {
    redis.delete(RedisConstants.shopCacheKey(shop.getId()));   // 删详情缓存
    redis.opsForGeo().remove(RedisConstants.shopGeoKey(0L), String.valueOf(shop.getId()));
    if (shop.getTypeId() != null)
        redis.opsForGeo().remove(RedisConstants.shopGeoKey(shop.getTypeId()), String.valueOf(shop.getId()));
}
redis.delete(RedisConstants.HOT_SHOP_KEY);                 // 热点列表作废
```

并且在**缓存重建时也要判可见性**（否则每次请求都会重新查到这家不可见的店并回填缓存）：

```java
if (!RoleConstants.visibleToUser(db)) {
    redis.opsForValue().set(key, MARKER, 2, TimeUnit.MINUTES);   // 不可见 → 空值标记 2 分钟
    return null;
}
```

> 实测：冒烟测试第 6 节"用户端店铺列表仅返回营业中店铺"通过；把某店铺 `audit_status` 改成 3 后，`/shop/list` 与 `/shop/{id}` 立刻不可见（GEO 也同步移除）。

### 2.3 代价与更优方案

| 手段 | 代价 | 更优方案 |
|---|---|---|
| L1 Caffeine 5s | 多实例间不一致最长 5s | 用 Redis Pub/Sub 广播失效；或本地缓存改为只读热点 + 消息驱动 |
| 互斥锁重建 | 未抢到锁的请求自旋等待（占线程） | 逻辑过期 + 异步重建（返回旧值，后台刷新），避免请求阻塞 |
| 随机 TTL | 仍有极小概率同时过期 | 逻辑过期方案彻底解耦"过期"与"重建" |
| 布隆过滤器不能删 | 删除店铺后过滤器仍说"可能存在" | 定期重建（本项目启动时全量重建）；或换 Cuckoo Filter（支持删除） |
| 每层都手写 | 代码重复 | 抽成通用注解 `@MultiLevelCache`（AOP） |

## 模块三：Redis GEO 附近店铺

### 3.1 怎么做的

```
写入：ShopService.addToGeo(shop)
   GEOADD shop:geo:0          lon lat shopId     ← 全量索引
   GEOADD shop:geo:{typeId}   lon lat shopId     ← 分类索引（按类目查附近）

查询：GET /shop/nearby?lon&lat&typeId&radiusKm
   GEORADIUS shop:geo:{typeId} lon lat {radius} km ASC COUNT 20 WITHDIST
   → 拿到 shopId + 距离 → 逐个走 queryById（命中多级缓存）→ 组装 ShopNearVO(shop, distanceM)
```

启动时 `DataInitRunner` → `rebuildIndexes(shopService.listVisible())`：清空旧 GEO 键 → 只把**可展示**的店铺写入全量与分类索引 → 同时装载布隆过滤器与类型缓存。

### 3.2 为什么用 GEO 而不是 MySQL 距离计算

| 方案 | 10 万店铺 5km 查询 | 说明 |
|---|---|---|
| `WHERE sqrt(pow(lon-?,2)+pow(lat-?,2)) < ?` | 全表扫描，无法用索引 | 数学上还对（小范围近似），工程上不可用 |
| 经纬度 + 矩形范围 + 索引 | 需要 4 个索引列 + 二次精算 | 可行但代码复杂 |
| **Redis GEO**（底层 zset + geohash） | O(log N + M) | 一条命令搞定，天然支持排序与距离 |

### 3.3 代价与坑

| 坑 | 说明 | 处理 |
|---|---|---|
| Redis 版本要求 | GEO 需要 Redis ≥ 3.2 | compose 固定 `redis:7-alpine` |
| 经纬度写反 | `lon=lat` 导致搜不到 | 前端/表单标注清楚，`addToGeo` 前判空 |
| 删除/停业未清索引 | 用户端仍能在附近列表看到 | `saveShop`/`removeShop` 双键移除 |
| 不存在的店铺 | `queryById` 返回 null | `nearby()` 里 skip（布隆过滤器已提前拦截） |
| 分页 | GEORADIUS 用 COUNT 限制而非分页 | 附近场景只取 TopN（本项目 20），符合业务 |

## 模块四：BitMap 签到

### 4.1 怎么做的

```java
// service/SignService.java
// key: sign:{userId}:{yyyyMM}   offset: 当月第几天-1   value: 1
redis.opsForValue().setBit(key, dayOfMonth - 1, true);

// 本月签到次数：BITCOUNT
Long count = redis.execute("BITCOUNT", key);  // 或 redis.opsForValue().bitCount

// 连续签到天数：从今天往前逐位判断，遇到 0 停止
```

### 4.2 为什么用 BitMap

| 存储方案 | 1 万用户 × 1 年 | 说明 |
|---|---|---|
| MySQL 一行一次签到 | 365 万行（约 200MB+） | 查询连续天数需要 SQL 窗口函数或应用层遍历 |
| Redis Set（存日期字符串） | 每用户每年 365 个 member，约 30KB | 1 万用户 ≈ 300MB |
| **BitMap** | 每用户每年 365 bit ≈ **46 字节** | 1 万用户 ≈ 450KB |

46 字节 vs 30KB —— 差 650 倍。这就是"数据密度极低的布尔序列用位图"的经典应用。

### 4.3 代价与坑

| 坑 | 说明 |
|---|---|
| 只能表示"是/否" | 签到送积分等需要额外 Hash 存储 |
| 月键设计 | 本方案按 `yyyyMM` 分键，跨月连续签到需要连着查上个月的键（本项目只统计当月连续） |
| 大 offset 稀疏写入 | 如果 offset 直接用时间戳（如 `userId` 前 32 位做 key），会造成大量空洞浪费内存 —— 所以要按用户分键 + 月内天数做 offset |

## 模块五：HyperLogLog UV 统计

### 5.1 怎么做的

```java
// 店铺详情接口里顺手打点
String uvKey = RedisConstants.uvKey(LocalDate.now(), "shop:" + id);   // uv:2026-09-12:shop:1
redis.opsForHyperLogLog().add(uvKey, String.valueOf(id));

// 平台看板读取今日 UV
uvService.sumToday();   // PFCOUNT 各页面键，或 PFMERGE 后 PFCOUNT
```

平台看板 `overview.uvToday` 就来自这里，与"在线连接数"（WebSocket 会话数）形成"今日访问量 vs 实时在线"的对照。

### 5.2 为什么不用 Set / 精确计数

| 方案 | 100 万 UV 内存 | 误差 |
|---|---|---|
| Set 存 userId | 约 50MB+ | 0 |
| **HyperLogLog** | **固定 12KB** | 0.81% 标准误差 |

UV 是"给运营看趋势"的指标，0.81% 误差完全可接受，而内存差 4000 倍。

### 5.3 代价

- 不能取单个元素是否访问过（没有 `SISMEMBER`）；
- 不能精确计数（面试如果问"如何精确统计 UV"→ BitMap（userId 为 offset）或 ClickHouse + 位图函数）。

## 模块六：饭搭子匹配（编辑距离 + TopN 优先队列）

### 6.1 怎么做的

```java
// service/MateService.java
// ① 中文标签转拼音首字母，把"川菜"和"窗台"这种字面不同、读音相同的差异降维（Levenshtein 之前做归一化）
// ② 用编辑距离度量兴趣标签相似度
// ③ 用容量为 N 的小顶堆（优先队列）维护 TopN，内存 O(N) 而不是 O(全部用户)
// ④ 结果缓存 Redis 10 分钟：cache:mate:recommend:{userId}
```

`util/Levenshtein.java` 是标准 DP 实现（滚动数组，空间 O(min(m,n))）。

### 6.2 为什么用优先队列而不是全排序

| 方案 | 10 万用户 Top 20 | 复杂度 |
|---|---|---|
| 全量算分 + 排序 | 需要保存 10 万条结果再排序 | O(N log N) 时间 + O(N) 内存 |
| **容量 N 小顶堆** | 只需维护 20 个元素 | O(N log N) 时间 + **O(N) → O(1) 额外内存**（堆大小固定） |

在候选人多的场景，内存才是瓶颈（每个候选对象含用户信息）。

### 6.3 更优方案

| 方案 | 适用 |
|---|---|
| 倒排索引：`tag → userIds`，取"共同标签最多"的候选集再精算编辑距离 | 用户量大（百万级），先用倒排把候选集从 10 万降到几百 |
| 向量化 + 近似最近邻（Faiss / Milvus） | 标签变成 embedding，语义匹配（"爱撸串" ≈ "爱烧烤"） |
| 离线计算 + 缓存 | 匹配结果不要求实时，可离线预计算（本项目已加 10min 缓存，是简化版） |

## 模块七：定时任务与分布式锁

### 7.1 三个定时任务

| 任务 | 频率 | 职责 | 并发保护 |
|---|---|---|---|
| `OrderTimeoutTask` | 每 30s | 超时 15 分钟未支付订单自动取消并**回补库存** | Redisson `tryLock(0, 5, SECONDS)` |
| `CachePreheatTask` | 每 30min | 预热热点店铺（写列表 + 详情缓存）、巡检秒杀库存缓存 | Redisson `tryLock(0, 10, SECONDS)` |
| `DataInitRunner` | 启动一次 | GEO 全量重建 + 布隆过滤器装载 + 秒杀库存回填 | 启动天然单实例 |

### 7.2 为什么必须加分布式锁

多实例部署时，三个实例的 `@Scheduled` 会**同时**触发：

- 超时订单取消：同一笔订单被取消三次 → 库存回补三次（**少卖**）
- 缓存预热：三倍无谓的 DB 压力（雪崩式预热的自伤）

`Redisson.tryLock(0, 5, TimeUnit.SECONDS)` 语义 = 不等待、拿不到就直接返回，天然适合定时任务打擂台。

```java
RLock lock = redisson.getLock("smartlife:task:timeout-order");
boolean locked = false;
try { locked = lock.tryLock(0, 5, TimeUnit.SECONDS); }
catch (InterruptedException e) { Thread.currentThread().interrupt(); return; }
try {
    if (!locked) return;              // 其它节点正在执行
    // ... 业务
} finally {
    if (locked) lock.unlock();        // 只有持锁者才解锁
}
```

### 7.3 与三端相关的点

- 超时取消订单要 `pushStatus(...)` 推送给**下单用户**（用户端），但不打扰商家（商家端只看自己订单列表）；
- 平台停业店铺后，`OrderTimeoutTask` 仍会正常取消其超时订单（状态机不依赖店铺可见性）；
- `CachePreheatTask` 预热时只预热可见店铺（`hotShops()` 内部已按 `visibleToUser` 过滤），避免把停业店铺重新灌进缓存。

## 模块八：统一响应、异常与参数校验

```java
// common/Result.java —— code=1 成功；0 业务失败；401 未登录/过期；403 端侧越权
public static <T> Result<T> ok(T data)          // {code:1,msg:"ok",data}
public static <T> Result<T> fail(String msg)    // {code:0,msg}

// common/GlobalExceptionHandler.java
BusinessException        → {code:0, msg:业务提示}          （日志 warn）
MethodArgumentNotValidException → {code:0, msg:首个校验错误} （@Valid 触发）
Exception                → {code:0, msg:"服务器繁忙，请稍后再试"}（日志 error + 堆栈）
```

参数校验用 JSR-303 注解（`@NotBlank/@Pattern/@Size/@Min/@Max`）落在 DTO 上，例如：
- `RegisterDTO`：手机号 `^1\d{10}$`、密码 6~20 位
- `MerchantRegisterDTO`：额外要求店铺名称必填（入驻注册必须带店铺资料）
- `OrderCreateDTO.items`：`@NotEmpty` + `@Valid` 嵌套校验 `CartItemDTO`（count 1~99）

> 注意：三端改造后**RegisterDTO 不再允许前端指定角色**（原实现从前端读 role，是提权漏洞）。角色由服务端根据调用的接口决定：`/auth/register` → role=1，`/auth/register/merchant` → role=2，管理员账号只能由已有管理员/DB 创建。这是本次改造顺带修掉的一个安全问题。
