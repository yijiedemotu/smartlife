## 1. 项目定位

**智联生活 = 三端一体的本地生活与社交聚合平台**：
`浏览(附近搜索) → 点餐 → 秒杀 → 找饭搭子 → 实时履约 → 平台治理`

它把四个经典教学项目的核心能力**合并到一个三端业务闭环**里，并且补上了教学项目普遍缺失的一环——**平台治理**：

| 能力来源 | 吸收到本项目的点 |
|---|---|
| 苍穹外卖 | 订单状态机、商家接单→配送→完成、WebSocket 实时推送、定时任务、经营看板 |
| 黑马点评 | 多级缓存治理（穿透/击穿/雪崩）、Redis Lua 秒杀、GEO 附近、BitMap 签到、HyperLogLog UV、Redisson 分布式锁 |
| 黑马商城 | 秒杀削峰：Redis 预扣 + RabbitMQ 异步下单 + 死信兜底 |
| 伙伴匹配 | 编辑距离 + 容量 N 优先队列 TopN 推荐 |
| **本项目新增** | **三端角色与数据隔离、商家入驻审核、平台治理闭环、操作审计留痕** |

### 1.1 为什么要从"双端"改成"三端"

改造前：`role=1 用户 / role=2 管理员`，管理员账号同时承担"商家"和"平台"两种身份——所有店铺数据混在一起，没有归属概念，没有审核，没有留痕。
这在真实业务里是不成立的：

| 教学项目的做法 | 真实业务的要求 | 本项目的改造 |
|---|---|---|
| 管理员想改哪个店就改哪个店 | 商家只能碰自己的店 | `tb_shop.merchant_id` 唯一归属 + 每次写操作前置归属校验 |
| 谁都能开店，店铺直接可卖 | 平台要审核资质 | `tb_merchant_apply` 申请单 + `/admin/apply/{id}/audit` 审核 |
| 管理员就是最高权限，随便改 | 关键操作要留痕、可追责 | `tb_audit_log` 记录 actor/action/target/detail |
| 新订单广播给所有"管理端" | 新单只能给对应店铺 | WebSocket 会话按角色 + merchantId 分桶 |
| 前端按 role 跳不同页面 | 后端也要能拦住越权 | 拦截器按路径前缀鉴权 + Service 层 RoleGuard 二次校验 |

> **面试价值**：多角色系统的难点从来不是"给页面分个菜单"，而是**权限不走样**（前端能跳不代表后端能调）、**数据不串店**（A 商家改不到 B 商家的商品）、**治理可追溯**（谁在什么时候批了谁）。这三件事在本项目都有代码落点，见 §4。

### 2.1 一次请求的完整生命周期（以"商家接单"为例）

```
商家端点击"接单"
  → POST /api/merchant/order/123/accept   Header: Bearer <JWT(role=2, id=11)>
  → Nginx  /api/ → http://backend:8080/api/
  → AuthInterceptor.preHandle
       ① 无 token？ → 写回 {code:401} 终止
       ② jwtUtil.parse 校验签名/过期 → 得到 LoginUser{id=11, role=2}
       ③ path=/merchant/order/... 以 /merchant/ 开头
          user.canOperateShop() ?  (role=2 或 3) → true 放行
       ④ UserContext.set(loginUser)   ← ThreadLocal 线程隔离
  → MerchantController.accept(orderId, currentMerchantScope())
       currentMerchantScope()：商家返回自己的 userId(11)，管理员返回 null(代管不限制)
  → OrderService.accept(orderId, merchantId=11)
       transit() →
         assertOwnership(order, 11)：
           查出 order.shopId → shop.merchantId == 11 ? 放行 : 抛"无权操作其它店铺的订单"
         状态机校验：当前必须是 2(已支付/待接单)，否则抛"订单状态已变更，请刷新"
         update status=3
         WebSocket 推送给下单用户（ORDER_STATUS）
  → 返回 {code:1,msg:"ok"}
  → AuthInterceptor.afterCompletion → UserContext.clear()  ← 必须清理，防线程池复用串号
```

注意三个细节，面试很容易被追问：

1. **为什么路径判断要先剥离 context-path**：`request.getRequestURI()` 返回 `/api/merchant/...`，而 `getContextPath()` 是 `/api`，不剥离就会匹配错。
2. **为什么 ThreadLocal 必须在 afterCompletion 清理**：Tomcat 线程池复用线程，不清理会导致下一个请求读到上一个用户的身份（越权事故）。
3. **为什么拦截器之外还要 RoleGuard**：拦截器只认路径，认不出"这个订单是不是你的"。路径级 + 数据级两道校验缺一不可。

## 3. 数据模型（三端）

### 3.1 角色与归属：先看整体关系

```
                    ┌──────────────────────────┐
                    │  tb_user                 │
                    │  role: 1用户 2商家 3管理员 │
                    │  status: 1正常 0封禁      │
                    └───┬──────────────┬───────┘
        role=1 用户 ─────┘              └───── role=2 商家
             │                                    │
             │ user_id                    merchant_id（UNIQUE 唯一索引！）
             ▼                                    ▼
     ┌───────────────┐  shop_id        ┌────────────────────┐
     │  tb_orders    │◄────────────────│  tb_shop           │
     │  tb_voucher_  │                 │  audit_status 0/1/2/3
     │  order        │                 │  open_status  1营业/0休息
     │  tb_message   │                 └──┬─────────────────┘
     └───────────────┘                    │ shop_id
                                          ▼
                              ┌───────────────────────┐
                              │ tb_product / tb_voucher│
                              └───────────────────────┘

     ┌──────────────────────┐        ┌──────────────────────┐
     │ tb_merchant_apply    │        │ tb_audit_log         │
     │ 入驻/变更申请单       │        │ 平台操作审计留痕       │
     │ merchant_id,status   │        │ actor/action/target   │
     └──────────────────────┘        └──────────────────────┘
```

**核心约束**：`tb_shop.uk_merchant (merchant_id) UNIQUE` —— "一个商家一个店铺"由数据库唯一索引保证，而不是靠应用层 `if (shop != null) throw`。

> 面试追问：为什么要用唯一索引？
> 答：应用层判重存在并发窗口（两个请求同时查到"没有店铺"然后各插一条），唯一索引是最终防线；同时它把"一个商家一个店铺"这条业务不变量固化进 schema，任何绕过 Service 的写入路径也破坏不了。代价是将来要支持"一个商家多店（连锁）"必须改成关联表 `tb_merchant_shop`，这是一次明确的重构点（见手册④）。

### 3.2 表清单与关键字段

| 表 | 关键字段 | 设计要点 |
|---|---|---|
| `tb_user` | `phone`(唯一)、`password`(salt:sha256)、`role`、`status`、`tags`(JSON) | 三端统一账号；`tags` 用 JSON 数组支撑饭搭子匹配 |
| `tb_shop_type` | `name`、`icon`、`sort` | 平台级字典，只有管理端能改；12h 缓存 |
| `tb_shop` | `merchant_id`(**UNIQUE**)、`type_id`、`lon/lat`、`score`、`popularity`、`audit_status`、`audit_remark`、`audit_time`、`open_status`、`phone`、`description` | 商家经营主体；`lon/lat` 支撑 Redis GEO；审核与营业状态分离（平台管审核、商家管营业） |
| `tb_merchant_apply` | `merchant_id`、`type`(1入驻/2变更)、`shop_id`(通过后回填)、`license_no`、`license_img`、`status`、`auditor_id`、`audit_remark`、`audit_time` | 一次提交=一张单，审核留痕；同一商家存在待审核单时禁止重复提交 |
| `tb_audit_log` | `actor_id`、`actor_role`、`action`、`target_type`、`target_id`、`detail` | 平台治理可追溯 |
| `tb_product` | `shop_id`(索引)、`price`(**分**)、`stock`、`sales`、`status` | 金额一律用分存 INT，避免浮点误差 |
| `tb_voucher` | `shop_id`、`type`(1代金/2秒杀)、`status`(商家上下架)、`audit_status`(平台治理)、`stock`、`sold`、`begin_time`、`end_time` | **两个状态列分别代表两种权限主体**，这是三端设计的典型体现 |
| `tb_voucher_order` | `user_id + voucher_id`(**UNIQUE**)、`status`、`use_time` | 一人一单的最终防线；`shop_id` 索引支撑商家端核销 |
| `tb_orders` | `number`(唯一)、`user_id`、`shop_id`、`amount`、`status`、快照字段 | 状态机 1待支付→2已支付/待接单→3已接单→4配送中→5已完成 / 6已取消 |
| `tb_order_item` | `order_id`、`product_id`、`price`(下单快照) | 明细存快照，商品改价不影响历史订单 |
| `tb_message` | `from_id`、`to_id`、`read_flag`、`idx_to_read` | 私信未读查询走联合索引 |

### 3.3 为什么"审核状态"和"营业状态"要分两列

```java
// tb_shop.audit_status  0待审核 1已通过 2已驳回 3已停业   ← 平台说了算
// tb_shop.open_status   1营业   0休息                    ← 商家说了算
```

- 商家临时打烊，不应该走平台审核（否则每次歇业都要审批）；
- 平台停业整顿，也不能被商家自己改回来；
- 用户端可见性 = 两个条件同时满足：

```java
// common/RoleConstants.java
public static boolean visibleToUser(Shop shop) {
    return shop != null
        && shop.getAuditStatus() != null && shop.getAuditStatus() == SHOP_AUDIT_APPROVED
        && shop.getOpenStatus()  != null && shop.getOpenStatus()  == SHOP_OPEN;
}
```

这个方法被用在 4 个地方，形成一致的可见性口径：

1. `ShopService.queryById` —— 缓存重建时不可见就当"不存在"（写空值标记）
2. `ShopService.pageShops` —— 用户端分页过滤
3. `ShopService.hotShops` —— 热点列表过滤
4. `ShopService.rebuildIndexes` —— 启动时只把可见店铺放进 GEO 与布隆过滤器

> **设计要点**：把"什么算可见"收敛成一个静态方法，而不是在 4 个查询里各写一遍 `if`。这是防止口径漂移的常用手法。

### 3.4 金额与状态编码约定（全项目统一）

| 约定 | 取值 | 原因 |
|---|---|---|
| 金额单位 | `INT` 分 | 避免 `double` 精度问题；展示层 `/100` 保留 2 位 |
| 用户角色 | 1用户 / 2商家 / 3管理员 | **v2 变更点**：v1 的 2=管理员已迁移为 3，新增 2=商家 |
| 店铺审核 | 0待审 / 1通过 / 2驳回 / 3停业 | 与申请单 `status`(0/1/2) 有意区分：店铺多一个"停业"终态 |
| 订单状态 | 1待支付 2待接单 3已接单 4配送中 5已完成 6已取消 | 状态机流转，非法跃迁直接拒绝 |
| 券类型 | 1代金券 / 2秒杀券 | 秒杀券才有时间窗与 Redis 库存 |
| 券双状态 | `status`(商家) / `audit_status`(平台) | 见 §3.3 |

## 4. 三端隔离的四道防线（重点章节）

### 4.1 第一道：路径前缀鉴权（AuthInterceptor）

```java
String path = request.getRequestURI().substring(request.getContextPath().length());

// 商家端：商家本人 + 平台管理员（管理员具备平台级代管能力）
if (path.startsWith("/merchant/") && !user.canOperateShop()) { 403 }

// 管理端：仅平台管理员
if (path.startsWith("/admin/") && !user.isAdmin()) { 403 }

// 用户端专属：购物车/找搭子/私信/签到（管理员没有用户购物车语义）
if (isUserOnlyPath(path) && user.isAdmin()) { 403 }
```

返回的是 **HTTP 200 + body `{code:403}`**（由 `ResponseUtil` 统一写出），前端 `request.js` 拦截 `code=403` 时提示并跳回自己角色的首页。

### 4.2 第二道：Service 层角色守卫（RoleGuard）

拦截器不认识业务语义，所以 Service 里再显式声明一次"这个方法谁能调"：

```java
// security/RoleGuard.java
requireMerchant()       // 必须是商家本人（管理员不通过，用于仅商家自己的敏感操作）
requireShopOperator()   // 商家或管理员
requireAdmin()          // 必须是平台管理员
```

使用示例（`MerchantController`）：

```java
@GetMapping("/dashboard/overview")
public Result<Map<String, Object>> overview(@RequestParam(required = false) Long shopId) {
    LoginUser user = RoleGuard.requireShopOperator();
    Shop shop = merchantService.resolveQueryShop(user, shopId);   // 第三道防线
    ...
}
```

好处：即使将来有人新增了 `/merchant/xxx` 却没在拦截器里想清楚，读到 RoleGuard 也能立刻明白调用方身份要求；同时定时任务/内部调用这类没有 Web 上下文的场景会得到清晰报错（"未登录"）而不是 NPE。

### 4.3 第三道：店铺归属校验 + 服务端强制重写 shopId（真正防越权）

这是三端改造里最关键的一段代码，解决"商家 A 传了 shopId=2 想改商家 B 的商品"：

```java
@PostMapping("/product/save")
public Result<Void> productSave(@RequestBody Product product) {
    LoginUser user = RoleGuard.requireShopOperator();
    // 经营类写操作：必须已有"过审"店铺
    Shop shop = merchantService.resolveOperateShop(user, product.getShopId(), true);
    // ★ 强制归属到自己的店铺，忽略前端伪造的 shopId
    product.setShopId(shop.getId());
    if (product.getId() != null) {
        // 改已有商品时，还要校验这个商品原本就属于自己
        merchantService.assertShopOwnership(productService.getById(product.getId()).getShopId(),
                                            user.isAdmin() ? null : user.getId());
    }
    productService.save(product);
}
```

`resolveOperateShop` 的语义（`MerchantService`）：

| 调用者 | 传 shopId | 结果 |
|---|---|---|
| 商家 | 不传 | 返回自己的店铺（`mustActive=true` 时要求已过审） |
| 商家 | 传了别人的 | 商家分支忽略入参，仍返回自己的店铺（配合后面的强制重写，伪造无效） |
| 管理员 | 不传 | 抛"请先选择要管理的店铺"（避免管理员误操作到全平台） |
| 管理员 | 传了 shopId | 返回该店铺（平台代管能力） |

而**查询**类接口用的是 `resolveQueryShop`：商家传别人的 shopId 会直接抛"无权查看其它店铺的数据"，管理员传 null 表示全平台口径。

> 实测证据：`scripts/smoke-test.ps1` 第 3 节断言"伪造 shopId=2 保存商品会被强制归属到本店(shopId=1)"，通过。

### 4.4 第四道（消息层）：WebSocket 会话按角色与店铺分桶

```java
// ws/WsSessionManager.java
userSessions     : Map<userId,     Set<Session>>   // 用户端
merchantSessions : Map<merchantId, Set<Session>>   // 商家端，按商家 id 隔离
adminSessions    : Set<Session>                    // 平台管理员

// 新订单只推给订单所属店铺的商家
MessagePusher.pusher().newOrderToMerchant(shop.getMerchantId(), data);
```

对比改造前：`broadcastToMerchant()` 会把新单推给所有"管理端"连接——店铺多了以后就是噪音灾难。现在 A 店的新单不会打扰 B 店，管理端也不再被新单刷屏。

## 5. 平台治理闭环（本项目的差异化亮点）

### 5.1 入驻审核状态机

```
商家注册(/auth/register/merchant)
   │  创建 tb_user(role=2) + tb_merchant_apply(status=0)
   ▼
登录商家端 → 看到"店铺尚未开通经营权限"（shop=null）
   │  此时：不能新增商品/券、不能接单（resolveOperateShop(mustActive=true) 直接拒绝）
   ▼
管理员在 /admin/apply/page 看到待审核单
   │  查看资质（营业执照号/图片/联系人/地址/经纬度）
   ▼
POST /admin/apply/{id}/audit {approved:true, remark:"资质齐全"}
   │  ① 申请单 status→1，写入 auditor_id / audit_time / audit_remark
   │  ② 首次入驻且无店铺 → 创建 tb_shop（audit_status=1, open_status=1）并回填 apply.shop_id
   │  ③ 清 MerchantService 归属缓存（否则商家端 60s 内仍读不到店铺）
   │  ④ 写 tb_audit_log（action=APPLY_APPROVE）
   ▼
商家下次登录：登录响应带上 shopId + shopAuditStatus=1 → 商家端解锁全部经营能力
```

驳回分支（`approved:false`）：申请单 `status→2` 并记录原因；**不创建店铺**，商家可补充资料后重新提交。

**幂等保护**：同一张申请单重复审核会被拒 —— `if (apply.getStatus() != APPLY_PENDING) throw new BusinessException("该申请单已处理，请勿重复审核")`。
**重复提交保护**：商家存在待审核单时 `submitApply` 直接拒绝。

### 5.2 审计留痕

所有平台级关键动作统一走 `MerchantService.writeAuditLog(...)`，且**审计失败不影响主流程**（try-catch 只记 warn）：

| action | 触发点 |
|---|---|
| `APPLY_APPROVE` / `APPLY_REJECT` | 入驻审核 |
| `SHOP_CLOSE` / `SHOP_REOPEN` / `SHOP_DELETE` | 店铺治理 |
| `USER_BAN` / `USER_UNBAN` | 账号治理 |
| `PRODUCT_UP` / `PRODUCT_DOWN` / `PRODUCT_DELETE` | 商品巡检 |
| `VOUCHER_BAN` / `VOUCHER_RESTORE` / `VOUCHER_DELETE` | 优惠券治理 |
| `TYPE_SAVE` / `TYPE_DELETE` | 类目字典 |

> 为什么写日志要吞异常？审计是"旁路"，不应因为日志表写失败就把用户的审核操作回滚。真实业务里更稳的做法是异步消息 + 独立存储（见手册④）。

### 5.3 平台与商家的职责边界（面试常问）

| 能力 | 商家端 | 管理端 |
|---|---|---|
| 店铺审核状态 | 只读（看审核意见） | 审核 / 停业 / 恢复 / 删除 |
| 店铺资料 | 改地址/经纬度/图片/电话；营业开关 | 改审核状态与处置原因 |
| 商品 | **增删改查、上下架** | 只读巡检 + 强制下架/恢复 + 删除 |
| 优惠券 | **创建、上下架、设秒杀时间窗** | 只读巡检 + 强制下架/恢复 + 删除 |
| 订单 | **接单/配送/完成/取消** | 全平台巡检 + 客服兜底处置 |
| 账号 | 只改自己的资料与密码 | 封禁/解封全平台账号（管理员账号受保护） |
| 类目字典 | 只读 | 增删改 |

这个边界就是 `/merchant/**` 与 `/admin/**` 的划分依据：**"日常经营"归商家，"治理与兜底"归平台**。

## 6. 缓存与索引在"治理"场景下的正确性

三端改造给缓存治理加了一个新问题：**店铺状态变了，缓存必须跟着失效**，否则会出现"平台已停业，用户端还能下单"。

```java
// ShopService.saveShop：所有店铺写操作（商家改资料、平台停业、审核开店）的唯一入口
public void saveShop(Shop shop) {
    if (shop.getId() == null) shopMapper.insert(shop); else shopMapper.updateById(shop);

    localCache.invalidate(shop.getId());          // ① L1 本地缓存立即失效

    if (RoleConstants.visibleToUser(shop)) {      // ② 可见：回填 Redis + GEO + 布隆
        writeDetail(shop);
        addToGeo(shop);
        bloom.put(shop.getId());
    } else {                                      // ③ 不可见：清 Redis + 移出 GEO
        redis.delete(RedisConstants.shopCacheKey(shop.getId()));
        redis.opsForGeo().remove(RedisConstants.shopGeoKey(0L), String.valueOf(shop.getId()));
        if (shop.getTypeId() != null) {
            redis.opsForGeo().remove(RedisConstants.shopGeoKey(shop.getTypeId()), String.valueOf(shop.getId()));
        }
    }
    redis.delete(RedisConstants.HOT_SHOP_KEY);    // ④ 热点列表作废
    if (shop.getTypeId() != null) redis.delete(RedisConstants.SHOP_TYPE_KEY);
}
```

三个容易踩的坑：

1. **L1 本地缓存必须显式 `invalidate`**：Caffeine 有 5s TTL，但商家改了价格后 5s 内用户端仍看到旧值是事故，所以要主动失效。
2. **GEO 索引要按 typeId 分键移除**：`shop:geo:0` 是全量键，`shop:geo:{typeId}` 是分类键，两个都要清。
3. **不可见的店铺不能只删缓存**：下次请求还会重建缓存，所以 `rebuildByMutex` 里也要判断可见性（写 2 分钟空值标记），否则会反复打 DB。

`MerchantService` 自己还有一层**归属缓存**（60s，`Map<merchantId, CacheEntry>`）：审核通过/驳回、资料变更、营业开关后必须 `evictCache(merchantId)`，否则商家端最长 60s 看不到变化。

> 面试可以这样讲取舍：本地缓存 + 短 TTL 是"用 60s 不一致换掉每次请求两次 DB 查询"；审核这种低频高价值动作必须主动清，不能靠 TTL 兜。

### 7.1 路由守卫（双重校验）

```js
router.beforeEach((to) => {
  const user = readUser(); const role = Number(user.role); const logged = !!user.token && !!role;
  if (to.meta.public) return logged && to.path === '/login' ? homePathOf(role) : true;
  if (!logged) return { path: '/login', query: { redirect: to.fullPath } };

  const target = pathRole(to.path);                     // /merchant→2  /admin→3  其余→1
  if (target === ROLE.ADMIN    && role !== ROLE.ADMIN)  return homePathOf(role);
  if (target === ROLE.MERCHANT && role !== ROLE.MERCHANT
                               && role !== ROLE.ADMIN)  return homePathOf(role);
  if (target === ROLE.USER     && role !== ROLE.USER)   return homePathOf(role);
  return true;
});
```

要点：

- **`role` 只是前端路由便利，不是权限**。守卫只防"手滑跳错页面"，真正的权限在后端（写代码时务必有这个意识）。
- 登录接口返回 `homePath`，前端不硬编码"role=2 去 /merchant"这类规则，避免前后端规则各写一份、改一处漏一处。
- 允许管理员进入 `/merchant/**`（代管），此时 `MerchantLayout` 顶部出现**店铺选择器**，选中的 shopId 通过 props 传给子页面并写入 store。

### 7.2 管理员代管的交互设计

```
AdminLayout 侧边栏「进入商家端代管」或 Shops 页「代管经营」按钮
   → user.setShop({id, name, auditStatus})  写入 Pinia + localStorage
   → 跳 /merchant/dashboard
   → MerchantLayout onMounted 调 /merchant/shop/mine
        返回 {admin:true, shops:[...]}  → 顶部渲染店铺下拉框
        切换店铺 → user.setShop(target) + bus.emit('MERCHANT_SHOP_CHANGED', id)
   → 子页面 watch(props.shopId) 重新拉数据，请求自动带 ?shopId=xxx
```

后端对应逻辑：`MerchantController` 的每个查询/写接口都接收可选 `shopId`，管理员传了才生效（`resolveQueryShop` / `resolveOperateShop`）。

1. **后端镜像内构建**：服务器无需装 JDK/Maven，`maven:3.9-eclipse-temurin-17` 阶段编译，`eclipse-temurin:17-jre` 阶段运行，镜像既小又自洽。
2. **密钥全部走 `.env.prod`**：compose 里只有 `${VAR}` 引用，没有明文；`deploy.sh` 会先检查是否残留 `CHANGE_ME`。
3. **端口收敛 + 健康检查**：中间件只绑 `127.0.0.1`（安全组也只放 80），`backend` 用 `depends_on: condition: service_healthy` 等待三个中间件，避免启动竞态。

## 9. 旧库升级（v1 双端 → v2 三端）

`sql/manual/upgrade_v2_three_end.sql`，幂等，可重复执行（用 `information_schema` 判断后再动态 `ALTER`，因为 MySQL 8 的 `ADD COLUMN` 不支持 `IF NOT EXISTS`）：

```sql
DROP PROCEDURE IF EXISTS sl_add_column;
DELIMITER $$
CREATE PROCEDURE sl_add_column(IN p_table VARCHAR(64), IN p_column VARCHAR(64), IN p_ddl VARCHAR(500))
BEGIN
    IF NOT EXISTS (SELECT 1 FROM information_schema.COLUMNS
                   WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = p_table AND COLUMN_NAME = p_column) THEN
        SET @ddl = CONCAT('ALTER TABLE `', p_table, '` ADD COLUMN ', p_ddl);
        PREPARE stmt FROM @ddl; EXECUTE stmt; DEALLOCATE PREPARE stmt;
    END IF;
END$$
DELIMITER ;
```

升级顺序（**顺序很重要**）：

1. `UPDATE tb_user SET role = 3 WHERE role = 2;` —— 先把 v1 管理员提升为平台管理员，否则后面插入 role=2 的商家账号会和新角色语义冲突。
2. 补列：`tb_user.status`；`tb_shop.merchant_id/phone/description/audit_status/audit_remark/audit_time/open_status`；`tb_voucher.audit_status`。
3. 补索引：`uk_merchant`、`idx_audit`、`idx_shop_status`、`idx_role_status`。
4. 建表：`tb_merchant_apply`、`tb_audit_log`。
5. 为历史店铺补建商家账号（`13700000001~10 / merchant123`，哈希为 `sha256('merchant123'+'seed')`）并 `UPDATE tb_shop SET merchant_id=...`——`merchant_id IS NULL` 作为幂等条件。
6. 为已绑定店铺补建"已通过"的申请单，让管理端审核记录完整。

> 注意种子密码哈希的算法：`PasswordUtil.matches` 用的是 `sha256hex(rawPassword + salt)`（**密码在前、盐在后**），与常见写法相反，写种子 SQL 时容易搞错。可用手册⑤的实验 0 快速验证。
