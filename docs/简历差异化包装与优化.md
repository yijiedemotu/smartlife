> 目的：既然"苍穹外卖/黑马点评/黑马商城/伙伴匹配"人人都会写，那就**别按教程的壳写**——

## 0. 为什么你的简历会"撞车"（先认清病灶）

| 撞车来源 | 典型症状 | 解法 |
|---|---|---|
| 同模板 | "项目描述/核心亮点/难点解决"三段式 + 一模一样的技术清单 | 换成**"业务命题 → 我的第一性拆解 → 取舍 → 验证"**叙事 |
| 同话术 | "使用 Redis 解决缓存穿透/击穿/雪崩""Lua+MQ 抗百万流量" | 每个结论前加**你自己的取舍与代价**（见§3 对照表） |
| 同数字 | "耗时降低 200ms""百万级并发" | 换成本项目**可现场复现**的口径（§2 指标包） |
| 同角色 | 只写"用户端 + 商家端"，管理端一律被说成"商家端兼职"，role 数字一个都没讲 | 换成**三端角色体系 + 平台治理闭环**（§4 第 11~14 条），把"多角色设计能力"讲成主线 |
| 同视角 | 站在"功能实现者" | 换到**"产品与系统双视角"**：为谁设计、指标是什么 |

**一条铁律：教程项目是"原材料"，你的增量设计才是"简历"。** 增量 = 代码里别人四个原型没有、而你想清楚的部分（§4 给你 14 个现成的）。

## 1. 差异化项目定位（选一个当标题，别再用"高并发本地生活平台"这种大词）

写法不是"我做了个外卖+秒杀+匹配"，而是给评审一个**记忆点**：

- **定位 A（业务闭环向）**：
  > "从'附近有什么'到'跟谁一起吃'再到'怎么买最划算'的本地生活一体化产品，单仓**三端**（用户端 role=1 / 商家经营端 role=2 / 平台治理端 role=3）"
- **定位 B（系统设计向，推荐技术岗）**：
  > "一个把**热点数据分层**、**秒杀一致性**、**三端实时协作**、**多角色权限与数据隔离**四个课题放在同一业务闭环里验证的个人系统"
- **定位 C（产品数据向，适合全栈/产品感）**：
  > "围绕**商家经营**（券/订单/看板）、**平台治理**（入驻审核/店铺与账号处置/审计留痕）与**用户增长**（秒杀/签到/搭子社交）三组指标设计的一体化平台"

一句话示例（替换烂大街首行）：
> 智联生活：单体架构下同时验证"读热点治理、写一致性、实时触达、多端权限不走样"四组技术命题的本地生活系统，用户端/商家端/管理端同源同库，演示数据/压测/部署全部可复现。

把简历里的"量化"从玄学改成**证据**：

| 我写进简历的口径 | 现场怎么证明 | 在项目里的依据 |
|---|---|---|

| "秒杀 stock=100、2000 并发压测 → 订单表恰好 100 行、零超卖" | 压完跑 `SELECT COUNT(*)` 对比 sold=100 | 文档⑤ 实验2（数字跑完再填） |

| "失败订单自动回补库存并告知用户" | 停库/改坏券后观察 WS 通知 + 库存回归 | 死信消费者+restoreStock |
| "签到一年约 46 字节/用户" | `redis-cli` 数 BITCOUNT 推导 | BitMap 原理 |
| "会话消息 2.5s 级可达，全程零长连接" | DevTools 看轮询请求间隔 | Chat 页 afterId 轮询 |
| "新订单只到达该店铺商家，不跨店打扰" | 开两个商家端窗口 + 一个用户端下单，只有对应店铺响铃 | `WsSessionManager` 按角色分桶 + `MessagePusher.newOrderToMerchant` |
| "商家无法读写他人店铺数据（伪造 shopId 无效）" | 用商家 token 调 `/merchant/product/save` 传别人 shopId，商品仍落到自己店里 | `MerchantController.productSave` 服务端重写 shopId |
| "入驻审核通过后自动开店，全过程可追溯" | 待审核商家登录看到"等待平台审核"→ 管理端审核通过 → 商家端出现店铺；审计日志出现 `APPLY_APPROVE` | `MerchantService.auditApply` + `tb_audit_log` |

|---|---|
| "使用 Redis 缓存解决了缓存穿透/击穿/雪崩" | "为热点店铺详情设计 L1 本地(5s)+L2 Redis(随机TTL)两级缓存；穿透用**布隆前置+空值缓存**双保险，击穿用**互斥锁单飞重建+自旋兜底**——选互斥而非逻辑过期，因为业务读多写少、实现简单可解释；代价是热点过期瞬间有毫秒级等待，我接受这个取舍" |
| "用 Lua+MQ 实现高并发秒杀，解决超卖" | "秒杀拆成'原子预扣(Lua)'与'慢动作落库(MQ)'两段：Lua 把判重+扣减压成一次原子 RTT；落库靠 **DB 条件更新(stock>0)+唯一索引** 双兜底，MQ 只负责削峰；还保留 Redisson 锁实现做**同场景对照**，用数据说服自己选 Lua" |
| "WebSocket 实现订单实时推送" | "只有强实时才用长连接（订单履约），弱实时的搭子私信**故意用 REST+afterId 增量轮询**（2.5s 级），因为私信无连接态、部署与排查成本最低——同一个平台里两种实时方案按场景取舍" |
| "基于编辑距离+优先队列实现 TopN 推荐" | "匹配要支持'川菜≈川味'的近似，选编辑距离而非字面集合相似；候选遍历用容量 N 的堆把内存压到 O(N)；并诚实说明：百万用户该换成倒排索引/向量召回——我先解决'算法对'，再解决'规模对'" |
| "使用 JWT 做登录鉴权" | "JWT 无状态是双刃剑：换来多实例零共享，代价是无法主动踢人；所以补了**二级拦截器滑动续期**(剩30min自动签发新 token，前端无感)，需要下线时再引 Redis 黑名单；账号级封禁则走 `tb_user.status`，登录时直接拒绝——这是我能讲清权衡的选择" |
| "设计了 XX 表 XX 字段" | "金额一律**存分**、订单写**快照列**、券单加 **(user,voucher) 唯一索引**——这三条是我从'测试数据对不上账/重复支付'这类真实事故里归纳出的规约" |
| "系统支持用户端和商家端，管理员也能进商家端" | "用**一个 role 字段(1用户/2商家/3管理员) + 路径前缀鉴权**把三端拆开：拦截器只管'能不能进这个端'，店铺归属校验全部下沉到 Service（`assertShopOwnership/resolveOperateShop`），并且**商品与券保存时服务端强制把 shopId 重写为自己店铺**——所以管理员能代管但必须显式选店铺，商家伪造 shopId 也越不了权" |
| "商家入驻就是插一条店铺数据" | "入驻拆成**申请单（tb_merchant_apply）+ 审核动作**：提交时校验'已有待审单不许重复提交'，审核时校验'单据状态必须是待审'，通过才在**同一事务**里创建并开通店铺并回写 shop_id；驳回只记原因不产生店铺——把'审批'建模成一张有状态机的单据，而不是一个布尔开关" |

## 4. 只有你代码里有的"谈资清单"（差异化弹药库，逐条对应源码）

这些**不是**教程原样，是你在本项目里做的增量/决策，面试官基本没听过同款：

1. **双方案可切换秒杀**：`smartlife.seckill.lua-enabled` 一条配置切换 Lua/Redisson 两版，附对比实验（别人通常只交一版）
2. **三层一致性防线方法论**：Redis 预扣(快) → DB 条件更新(权威) → 唯一索引(幂等) + 失败回补(最终一致)，可画成自己的"库存一致性分层模型"
3. **缓存写路径联动**：店铺 CRUD 时同步维护 缓存/GEO/布隆 三份索引 + 启动全量重建——把"缓存一致性"做成闭环而非散点
4. **聊天不用 WS 的决策**：同平台订单用 WS、私信用轮询，能答"为什么这么分"
5. **afterId 增量轮询**：自增 id 当游标，无时钟漂移不漏消息（比时间戳轮询严谨）
6. **会话聚合 SQL**：`LEAST/GREATEST(from,to)+MAX(id)` 归组取末条——小而巧
7. **JSON_CONTAINS vs LIKE 选型**：标签精确到数组元素不误命中（能展开"为什么不用 LIKE"）
8. **订单状态机 + 非法流转拒绝**：`transit(from,to)` 把流程变成可测试的规则
9. **定时任务分布式锁**：tryLock 抢执行权防多实例重复 + 可演进到 XXL-Job 的判断
10. **压测/验收脚本化**：`sql/more_seed_data.sql`、`docs/项目学习手册/05` 实验清单 = 你重视"可复现交付"
11. **三端权限三层防线**：拦截器（`AuthInterceptor` 按 `/merchant/**`、`/admin/**`、用户端专属路径分端）→ Service 守卫（`security/RoleGuard` 的 requireMerchant/requireShopOperator/requireAdmin）→ 数据归属收敛（`MerchantService` 的 shopOfMerchant/requireActiveShop/assertShopOwnership/resolveOperateShop）。**三层各司其职，拦截器只做粗粒度，越权校验绝不外包给前端**
12. **归属即数据库不变量**：`tb_shop.merchant_id` 唯一索引 `uk_merchant` 表达"一个商家一个店铺"，把业务约束下沉；应用层判重只能算第二道防线（并发下唯一索引才是最终裁判）
13. **申请单驱动治理闭环**：`tb_merchant_apply`（type 1首次入驻/2资料变更，status 0/1/2）+ 审核通过自动开店 + 驳回留原因 + 已处理单拒绝重复审核 + `tb_audit_log` 记录 APPLY_APPROVE/SHOP_CLOSE/USER_BAN/VOUCHER_BAN 等
14. **管理员代管的显式化设计**：管理员可进商家端（`LoginUser.canOperateShop()`），但商家端接口在 admin 场景**必须带 shopId**（`resolveOperateShop` 未传就报"请先选择要管理的店铺"），前端用 `MerchantLayout` 的店铺下拉 + `bus` 广播给子页面——把"平台代管"和"商家自助"用同一套接口面表达而不牺牲安全

> 用法：别全写进简历（太长），选 2~3 个与岗位最相关的作为"项目亮点"下的小标题，其余放进面试谈资。**投后端/系统设计岗，优先选 11~14（多角色设计能力最稀缺）**。

## 5. 岗位化变体（同一个项目，三段不同侧重）

### A. Java 后端校招/社招（主推）
> **技术栈**：Java17 · Spring Boot · MyBatis-Plus · MySQL · Redis · Lua · Redisson · RabbitMQ · WebSocket · Vue3
> **职责**：独立设计并实现…（定位B）
> 1) 店铺详情高并发读：两级缓存(本地5s+Redis随机TTL) + 布隆/空值/互斥锁四防线，压测 DB 查询趋近于零；
> 2) 秒杀一致性：Lua 原子预扣 → RabbitMQ 异步削峰 → DB 条件更新+唯一索引双兜底，stock=100/2000并发实测零超卖；保留 Redisson 锁版同场景对照；
> 3) 三端履约：6态订单状态机 + WebSocket **按角色分桶、新订单精确推送到所属店铺商家**，超时单分布式锁定时取消并回补库存；
> 4) **多角色与治理**：role 1/2/3 三端鉴权（拦截器 + RoleGuard 双层）、商家数据隔离（归属校验 + 服务端 shopId 重写）、入驻申请单审核后自动开店、关键操作审计留痕；
> 5) 工程规约：金额存分、订单快照、ThreadLocal 清理、JWT 滑动续期、统一 Result/异常、全容器化 Docker Compose 一键部署。

### B. 中间件/并发方向（把缓存/消息放大）
> 标题可写："热点分层 + 最终一致性"实践者。
> 1) 讲**缓存四防线如何组合而非堆名词**；
> 2) 讲**秒杀的三层一致性模型**与两方案对照实验；
> 3) 讲**RabbitMQ 死信/手动ACK/唯一索引幂等**的可靠性闭环；
> 4) 主动提一句"单体也能用全套中间件，分布式只是把边界切开；本项目连'一个商家一个店铺'这种业务不变量都用数据库唯一索引落地，而不是靠应用层 if"。

### C. 全栈/后端兼前端
> 强调 Vue3 **三端工程**（`/user` `/merchant` `/admin` 三套布局与路由 + 守卫双重校验）、Pinia 状态持久化的坑(JWT store 未声明字段失效)与修法、**管理员代管商家端的店铺选择联动**、ECharts 看板（商家单店口径 vs 平台全平台口径）、轮询资源分级(2.5s/5s/6s)。

## 6. 结构排版建议（让它不像批量生产）

1. **标题行给数字钩子**：把最硬的一条证据放最前（如"压测零超卖""DB读趋近0""伪造 shopId 写不进别人店"）
2. **亮点写成"取舍句"而非"功能句"**：功能句=做了X；取舍句=为什么不用Y而用X，代价是Z
3. **给"细节名词"建立人设**：比如自称"对边界情况敏感"就用 ThreadLocal 清理/金额存分/快照列/归属唯一索引来佐证，而不是自夸
4. **多角色能力要单独成行**：招聘方对"三端/多角色/平台治理"的关键词识别度极高，别把它塞在"其他"里
5. **附一条可验证链接/二维码**：GitHub 或本地 README（若可以脱敏公开）
6. **长度**：项目段 8~12 行为佳；更细的留在作品集页面

## 7. 诚实红线（面试能扛住才算优化）

- 别写"独立开发全部功能"之外还加上"团队协作"的套话，保持真实一致

## 8. 一版可直接抄的"项目经历"最终稿

> **智联生活 · 本地生活与社交聚合平台（个人全栈，三端一体化：用户端 role=1 / 商家端 role=2 / 管理端 role=3）**
> 业务闭环：附近找店 → 点外卖 → 抢秒杀券 → 匹配饭搭子 → 实时履约 → 平台治理；三端同库同源、共用一套账号体系与后端。
>
> **关键决策与验证**
> ① **读热点治理**：店铺详情两级缓存(本地Caffeine 5s + Redis 随机TTL)，以布隆+空值缓存拦穿透、SETNX 互斥锁单飞重建打击穿；写路径联动更新 缓存/GEO/布隆，启动全量重建——压测中 200 次热点请求 DB 查询趋近于零。
> ② **秒杀一致性**：拆"原子预扣(Lua：判重+扣减一次 RTT)"与"异步落库(MQ)"，DB 条件更新(stock>0)+ (user,voucher) 唯一索引做双兜底，失败消息死信回补；另实现 Redisson 锁版做同场景对照。stock=100、2000 并发实测 0 超卖(数字待本机复测)。
> ③ **实时方案按场景取舍**：订单履约(强实时)用 WebSocket **按角色分桶推送**（该店铺商家收新单响铃、下单用户收进度）；搭子私信(弱实时)用 REST + afterId 增量轮询(2.5s 级)并配分级轮询降耗——同一平台两套方案并存的理由可完整阐述。
> ④ **平台治理闭环（差异化重点）**：商家提交入驻/资料变更**申请单** → 管理员审核 → **通过自动创建并开通店铺**（驳回留原因、已处理单拒绝重复审核）；`tb_shop.merchant_id` **唯一索引**把"一个商家一个店铺"落成数据库不变量；商家数据隔离靠 Service 层归属校验 `assertShopOwnership/resolveOperateShop`，**商品与券保存时服务端强制重写 shopId 防伪造越权**；管理员可进入商家端代管但必须显式选择店铺；审核/停业/封禁/下架等关键操作写 `tb_audit_log` 留痕。
> ⑤ **工程规约**：金额一律存分、订单明细快照防改价追溯、6 态状态机拒非法流转、超时单由分布式锁定时任务取消并回补库存、JWT 二级拦截器滑动续期 + ThreadLocal 严格清理、RabbitMQ 手动 ACK/死信、全容器化 Docker Compose（MySQL8+Redis7+RabbitMQ3.12+后端+Nginx）一键部署。
