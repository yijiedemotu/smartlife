# 一、高频考点（1–16）

**1. 缓存穿透 / 击穿 / 雪崩的区别与各自解决方案？（考点：Redis 缓存三大经典问题）**
【答】穿透=查**不存在**的数据，请求直达 DB；对策=布隆过滤器前置拦截 + 空值短缓存。击穿=**热点 key 恰好过期**，一瞬间全打到 DB；对策=互斥锁单飞重建 / 逻辑过期。雪崩=**大量 key 同时过期**；对策=TTL 随机化 + 多级缓存兜底。
【解析】得分点：能先区分"对象是谁"——穿透是"数据不存在"，击穿是"单个热点过期"，雪崩是"批量同时过期"；再各给方案。易错：把布隆说成防击穿。追问：本项目把四者做成组合（`ShopService.queryById`：布隆→空值→互斥锁→随机TTL），要能报出代码位置。★建议配合文档⑤实验1验证"DB查询趋近0"。

**2. 缓存与数据库一致性怎么保证？（考点：缓存写一致性）**
【答】主流是 **Cache Aside（旁路）**：读未命中→查库→写缓存；写→先更新 DB 再删缓存。本项目：更新 DB 后**同步重建该店铺缓存**并删除热点列表缓存（写后更新）。更严格可"延迟双删"或用 binlog（Canal）订阅变更刷缓存。
【解析】得分点：承认"强一致做不到，只做最终一致+降低不一致窗口"；说出"为什么删缓存比更新缓存好"（并发写时更新旧值会污染）。追问：删除失败怎么办（消息队列重试/订阅 binlog）。易错：吹"强一致"。

**3. 布隆过滤器原理？误判怎么处理？为什么不能删除？**
【答】用 k 个哈希函数把元素映射到位数组的 k 位并置 1；查询时 k 位全 1 才"可能存在"。特点：**不漏报（不在的一定不在），会误报（在的可能说在）**。误判=多查一次 DB/缓存，可配空值缓存兜底；不能删除是因为删一位可能影响其它元素，本项目靠**启动时全量重建**。
【解析】得分点：讲清"宁可错放、不可错杀"及 fpp 参数（本项目 0.01、预期 1 万）。追问：误判率怎么算/数据量增长怎么办（扩容重建）。

**4. Redis 过期删除策略与内存淘汰策略？**
【答】过期删除：**惰性删除**（读时发现过期才删）+ **定期删除**（周期抽查）。内存满时按 **maxmemory-policy** 淘汰：allkeys-lru / volatile-lru / allkeys-random / noeviction 等；生产常用 allkeys-lru。
【解析】得分点：能解释"为什么要两种配合"（惰性有垃圾残留、定期有开销）；秒杀库存这类**不能淘汰**的 key 要意识到风险（本项目库存常驻 + 启动/巡检回填兜底）。

**5. 秒杀怎么防超卖？给出你的完整方案演进。（★核心题）**
【答】演进：①DB 同步"查+插"→必然超卖；②乐观更新 `UPDATE ... SET stock=stock-1 WHERE stock>0` 防超卖但仍慢；③本项目最终：**Redis Lua 原子预扣**（判重+扣减一次 RTT）→ **RabbitMQ 异步落库削峰** → 消费者事务内再做 DB 条件更新 + `(user,voucher)` **唯一索引**双兜底；失败消息**死信队列回补库存**。另保留 Redisson 锁版本可配置切换做对照。
【解析】得分点：讲清"三层防线各防什么"（Lua 防 Redis 侧超卖与一人一单；DB 条件更新是权威兜底；唯一索引=幂等+最终防线；回补=最终一致）。易错：只说"用 Redis 减库存"但没讲 DB 兜底。追问：Redis 与 DB 库存不一致怎么办（对账/巡检/回补）——见文档③模块一。

**6. Redis Lua 为什么原子？和 MULTI 事务有什么区别？**
【答】Redis 单线程执行 Lua 整段脚本，执行期间不穿插其它命令→**天然原子**。MULTI 只是"命令打包按序执行"，**不支持回滚中间失败**、不能做条件分支；Lua 可以在脚本内"读→判断→写"（本项目判重+扣减），MULTI 做不到这种"先读后写的一致性"。
【解析】得分点：举例本项目 `seckill.lua` 里 sismember→decr→sadd。追问：Lua 脚本超时/慢脚本危害（阻塞 Redis）；KEYS/ARGV 与集群槽位限制。

**7. MQ 削峰原理？RabbitMQ 消息可能丢在哪、怎么保证不丢？**
【答】MQ 把"请求瞬间的写洪峰"转成队列积压，消费者按自己的速率消费→**削峰填谷**（本项目秒杀请求秒回、DB 匀速落单）。不丢消息三端：①生产者 **confirm** 确认；②MQ 本身 **持久化**（durable 交换机/队列 + delivery-mode=2）；③消费者**手动 ACK**，处理成功才 ack。
【解析】得分点：分"生产-存储-消费"三段讲，缺一不可；本项目做了持久化+手动ACK，confirm 属于"生产加固点"（要能说"我清楚该加但演示环境未开"）。追问：积压怎么办（扩容消费者/临时转储）。

**8. 消息重复消费怎么办？**
【答】靠**消费幂等**：本项目 `(user_id,voucher_id)` 唯一索引——重复插入直接 DuplicateKey，消费者 catch 后 ACK 视为已处理；一般化方案还有：业务主键去重、幂等表（请求流水号）、状态机前置校验（先查状态再更新）。
【解析】得分点：先说"MQ 重复是常态（网络/重投/消费超时重发）"，再说"幂等设计在业务侧"。追问：为什么唯一索引能同时解决"一人一单"和"消息幂等"两件事（同一个约束）。易错：在消费者里 try 吞异常后 ack。

**9. SETNX 分布式锁和 Redisson 有什么区别？看门狗是什么？**
【答】SETNX+过期时间：非原子设置/误删他人锁/业务超时锁提前释放都要自己处理。Redisson：`lock()` 默认 30s 且**看门狗每 10s 自动续期**（业务没跑完锁不释放）、**可重入**、支持公平锁/红锁；`tryLock(wait,lease)` 可控制等待与手动租期。本项目定时任务用 `tryLock` 抢执行权，秒杀降级方案用 `lock()`。
【解析】得分点：能答"为什么不能只 SETNX"的 3 个坑（加锁非原子→用 SETNX EX；释放误删→存唯一值比对；超时释放→看门狗）。追问：看门狗在 leaseTime 手动指定后还生效吗（不生效）。红锁与 CAP 的取舍要有概念。

**10. JWT 无状态有什么优缺点？怎么续期？怎么踢人？**
【答】优点：服务端不存 Session、多实例天然共享、可跨端。缺点：签发后无法主动失效=**不能踢人/不能防窃用**；payload 可读需注意不放敏感信息。续期：本项目**二级拦截器滑动续期**——剩余 <30min 的任意请求自动签新 token 走响应头 `X-Auth-Refresh`；下线：Redis 黑名单/白名单、token 版本号、短期 token+refresh token 双 token。
【解析】得分点：主动说出"无状态是把双刃剑"，体现权衡；能讲清滑动续期与双 token 两种流派差异。追问：token 放哪（localStorage vs httpOnly cookie + CSRF 取舍）。

**11. ThreadLocal 原理？为什么可能内存泄漏？**
【答】ThreadLocal 值存在**当前线程的 ThreadLocalMap** 里，key 是弱引用；若线程长期存活（线程池）且 value 仍被强引用链持有，Map 会一直变大→泄漏。解决：**用完后 remove()**——本项目 `UserContext.clear()` 放在拦截器 afterCompletion。
【解析】得分点：讲清"线程池复用 + 强引用 value"两个条件；本项目场景（每请求存 LoginUser、请求结束必须清，否则下个请求读到别人的用户=串号）。追问：父子线程/异步线程怎么传（InheritableThreadLocal/TransmittableThreadLocal）。

**12. 为什么订单存快照？金额为什么要用分？**
【答】快照（shop_name/address/product 名称/单价）保证商品改价改名后**历史订单可追溯可对账**；金额服务端按 DB 单价重算防前端篡改。金额用**整数分**避免 double/float 浮点误差（0.1+0.2 问题），BigDecimal 也只用在高精度计算或展示换算场景。
【解析】得分点：细节题很拉好感——能说出"快照=历史事实；分=精度与存储"，并可补充数据库 DECIMAL 与分两种流派（本项目选分+前端 /100）。

**13. Redis 为什么快？单线程为什么反而好？**
【答】①纯内存；②IO 多路复用（单线程处理 epoll 事件）免线程切换与锁竞争；③数据结构高效。单线程好处：无并发竞争、实现简单；坏处：单个慢命令（KEYS/大 key）会阻塞全部——所以本项目用 SCAN/按类型 key 而不是一把梭。
【解析】得分点：别说"单线程所以快"要答 IO 模型；能接"那为什么 6.0 引入多线程"（只用于网络读写，命令执行仍单线程）。追问：本项目有哪些"慢命令风险"（keys 重建 GEO 时用 keys 但只在启动执行，可接受）。

**14. 本项目 Redis 用了哪些数据结构？各自场景？**
【答】String：店铺缓存 JSON/秒杀库存/UV 的 key 前缀；Hash：购物车（field=商品）；Set：一人一单标记/用户在线会话集合（CopyOnWrite 场景）；ZSet：GEO 底层（shop:geo 的 score 是 GeoHash）；BitMap：签到；HyperLogLog：UV；另有 Lua/脚本与 Redisson 锁。列表可扩展：ZSet 还常做排行榜/Feed 时间线（黑马点评知识点，本项目未用但要会）。
【解析】得分点：把"数据结构→业务"一一对上，体现不是背命令；追问任意一个的复杂度（如 ZSet 跳表 O(logN)）。

**15. 缓存击穿：互斥锁方案和逻辑过期方案怎么选？（进阶题）**
【答】互斥锁（本项目）：miss 后抢锁线程查库回填，其余线程自旋等待——**一致性最好**，代价是热点期间有短暂阻塞。逻辑过期：缓存里存"过期时间戳"，命中后发现逻辑过期→返回旧值并让**一个线程**异步重建——**不阻塞读**，代价是这段时间读到旧数据（弱一致）+ 额外字段与重建线程管理。
【解析】得分点：能说出"一个保一致性、一个保可用性"，并选型理由（本项目读多写少选互斥锁、实现简单）。追问：逻辑过期下缓存万一重建失败怎么办（旧值+TTL 兜底/降级 DB）。

**16. 接口幂等怎么设计？（考点：幂等总纲）**
【答】分场景：①天然幂等：GET/条件更新（`WHERE stock>0` 只成功一次）；②唯一约束：业务唯一键（本项目 user+voucher 唯一索引、以及 `tb_shop.merchant_id` 唯一索引）——数据库层去重；③前置 token：下单前发"预生成 token"，提交时校验并删除（防重复下单）；④状态机：只允许特定状态流转（订单 2→3 不能 2→4；申请单 status 必须=0 待审才能审核）——**本项目"审核通过自动开店"正是靠③的状态前置校验+事务做幂等**（见第 41 题）。
【解析】得分点：不要只答"用 Redis setnx"；要按"谁能做唯一键"分层；并区分"幂等"与"防重提交"（前者是重复执行结果一致，后者是不允许重复执行）。追问：本项目哪些接口天然幂等（支付/取消有状态前置校验）。

# 二、中频考点（17–36）

**17. 哪些写法会让索引失效？**
【答】常见：对索引列做**函数/运算**（`WHERE YEAR(create_time)=2026`）、隐式类型转换（字符串列传数字）、前导模糊 `LIKE '%xx'`、OR 连接非索引列、`!= / NOT IN`（视优化器）、联合索引不满足最左前缀。
【解析】得分点：报 3~4 个 + 一个反面例子即可；本项目 phone 唯一索引、orders(user) 索引等要能举出"哪个查询能用上"。**三端相关可举例**：`tb_shop.merchant_id` 唯一索引 `uk_merchant` 让 `MerchantService.shopOfMerchant()` 的等值查询走唯一索引（这也是它能加 60s 本地缓存的前提——归属查询本身足够廉价）；`tb_user` 的 `idx_role_status (role, status)` 支撑管理端"按角色+状态筛选账号"的 `adminPage`。追问：怎么验证（EXPLAIN 的 key 列）。

**18. 聚簇索引 / 回表 / 覆盖索引是什么？**
【答】InnoDB 主键即**聚簇索引**，叶子存整行；二级索引叶子存主键值——查二级索引未覆盖的列要按主键**回表**。若查询列都在二级索引里则**覆盖索引**免回表。本项目 `(to_id, read_flag)` 索引可支撑未读统计这类窄查询。
【解析】得分点：能用"叶子节点存什么"讲清三者关系；优化思路=多建覆盖索引/少 `SELECT *`。

**19. 事务隔离级别？MySQL 默认 RR 解决了什么、没解决什么？**
【答】读未提交/读已提交(RC)/可重复读(RR)/串行化。RR 靠 **MVCC + 快照读**解决脏读与不可重复读；**幻读**在 RR 下仅靠快照读不能完全防（需 next-key lock 或串行化）。本项目订单/库存更新都走事务（默认 RR）。
【解析】得分点：能画 MVCC 版本链与 undo log；区分"快照读"与"当前读"（`SELECT ... FOR UPDATE/UPDATE` 是当前读，秒杀条件更新才生效）。追问：RC vs RR 在并发下的差异（间隙锁/主从一致性）。

**20. 乐观锁 vs 悲观锁？CAS 的 ABA 问题？**
【答】悲观锁=先锁后读（DB 行锁/select for update），冲突多时可用；乐观锁=更新时校验版本（`version=version+1 where version=旧值`）或条件更新（本项目 `WHERE stock>=n` 即库存乐观）。CAS 的 ABA：值 A→B→A，用版本号/时间戳解决。
【解析】得分点：说明秒杀用的是"库存乐观条件更新"而非版本号（天然防 ABA）；并发低优先乐观、冲突高可能悲观更稳——要能说取舍。

**21. @Transactional 失效有哪些情况？**
【答】自调用（同类方法内部调用不走代理）、方法非 public、异常被 catch 吞掉、抛出的是检查异常且未 rollbackFor、事务类没被 Spring 管理、数据库引擎不支持（MyISAM）。
【解析】得分点：结合本项目：秒杀下单消费者调 `voucherOrderService.createVoucherOrderTx` 是**跨 bean 调用**所以代理生效；并说明默认只回滚 RuntimeException，业务失败应抛 BusinessException(继承 RuntimeException) 或显式 rollbackFor。追问：事务里发 MQ/调外系统先发还是先提交（先提交后发+重试）。

**22. MyBatis-Plus 分页原理？深分页怎么优化？**
【答】MP 通过**分页插件拦截器**改写 SQL 拼 `LIMIT`（执行 count 与 limit 两次查询）。深分页（offset 百万）慢在"先扫再丢"——优化：游标分页（`WHERE id > lastId LIMIT n`，本项目聊天记录就是游标）、延迟关联、子查询只取主键。
【解析】得分点：能说出本项目聊天用 id 游标即深分页规避；追问：count 慢怎么办（估算/缓存/不 count）。

**23. 慢 SQL 怎么排查？EXPLAIN 重点看什么？**
【答】慢查询日志 → EXPLAIN → 看 type(ALL=全表最差,ref/range 好)、key 是否命中、rows 估算、Extra(Using filesort/temporary 要警惕)、possible_keys。优化：加合适索引/改写 SQL/拆分大查询。
【解析】得分点：给"一个真实项目例子"最加分——例如 `selectConversations` 的 LEAST/GREATEST 分组查询会全表，教学规模可接受，但能主动说"量大会改为会话表冗余 last_msg_id 或定时聚合"。

**24. RDB 和 AOF 怎么选？**
【答】RDB：定时全量快照，恢复快、文件小，但可能丢最后一次快照后的数据；AOF：追加写命令，默认 everysec 最多丢 1s，文件大、恢复慢。生产常**两者都开**（RDB 兜底 + AOF 精细），或 Redis 7 用混合持久化。
【解析】得分点：结合本项目：秒杀库存这类"允许从 DB 回填"的数据对持久化不敏感（有启动/巡检补偿），可顺势说出"不是所有缓存都需要持久化"的思考。

**25. 什么是大 key / 热 key？怎么发现和处理？**
【答】大 key：单个 key 数据巨大（大 hash/大集合），引发慢命令/阻塞/内存不均。热 key：某 key QPS 极高（如明星店铺），单点压力大。处理：拆分（hash 分片/集合分片）、本地缓存兜热 key、读写分离、热点 key 打散（加后缀随机读多副本）。
【解析】得分点：能关联本项目 L1 Caffeine=本地缓存兜热店铺 key；答"不扫 keys，用 scan/redis-cli --bigkeys/热点探测"。

**26. Redis keys 与 SCAN？还有什么命令规范？**
【答】`KEYS *` 会阻塞 Redis（单线程），必须用 **SCAN 游标分批**；本项目启动重建索引时删 `shop:geo:*` 用 keys 属于低频启动场景可接受，运行时用类型化 key 避免扫库；另注意：大 Hash `HGETALL`、大集合、`DEBUG` 类命令、生产禁 flushdb/flushall。
【解析】得分点：强调"key 设计规范决定会不会被迫全扫"（本项目 RedisConstants 集中管理 + 前缀隔离）；追问：scan 能保证不重不漏吗（可能重复、不保证不漏，业务上要容忍重复处理幂等）。

**27. 令牌桶 / 漏桶 / 滑动窗口限流区别？秒杀要加哪种？**
【答】令牌桶：匀速放令牌，**允许突发**（桶内有存量），适合秒杀入口"先放进来一批"；漏桶：恒定速率流出，强削峰，适合保护下游 DB；滑动窗口：按时间窗口精确计数，防"整点突刺"，实现要维护窗口。可组合：令牌桶限用户点击频率 + 漏桶/队列保护 DB。
【解析】得分点：本项目秒杀"MQ 本身就是漏桶/削峰"，应用层限流是**可加项**（文档⑤改造清单）；要能说出"为什么抢购按钮要加幂等/冷却"。

**28. 秒杀压测怎么设计？QPS / RT / 分位数怎么解读？（★）**
【答】JMeter：CSV 准备 N 个不同账号 token → 线程组 2000 并发 → 断言 code=1 → 打完核对 `tb_voucher_order` 行数=stock、无超卖；结果看 TPS/QPS、平均 RT、**P95/P99**（聚合报告）与错误率；对比 Lua 版 vs Redisson 版。DB 侧看队列消费节奏（削峰证据）。
【解析】得分点：强调"业务断言（0 超卖）比吞吐数字更硬"；数字**先本机实测再写简历**；能说出平均 RT 会被长尾污染，要报分位。

**29. 超时未支付订单：定时任务扫 vs 延迟消息 vs 死信 TTL？**
【答】①定时扫（本项目）：每 30s 扫 + 分布式锁，直观可控，但精度分钟级、压力集中在扫描点；②RabbitMQ 延迟插件/延迟交换机：消息到期精准触发，事件驱动；③死信 TTL：消息不消费进死信队列触发，无需插件但队列语义绕。
【解析】得分点：答"生产优先延迟消息、本项目用任务是为了教学直观+可控"，并说明两者的压力模型差异；追问：任务扫描怎么防把大量数据一次性拉爆（本项目 LIMIT 200 分批）。

**30. 多实例定时任务重复执行怎么解决？XXL-Job 架构知道吗？**
【答】本项目：Redisson `tryLock` 抢锁，抢不到直接跳过（执行权唯一）。生产：XXL-Job——调度中心 + 执行器，支持分片广播、失败重试、任务依赖、故障转移；比"自己抢锁"多了可视化与运维。
【解析】得分点：先讲锁方案（自己实现过），再讲"规模化后换 XXL-Job 的理由"；追问：分片是怎么分配任务的（轮询/一致性哈希给执行器）。

**31. 轮询 / 长轮询 / SSE / WebSocket 怎么选？（本项目私信 vs 订单）**
【答】轮询：定时问（简单，有延迟与空转）；长轮询：挂起到有新数据才返回（少空转但连接管理复杂）；SSE：服务端单向推送，基于 HTTP，改动小；WebSocket：全双工长连接。选型=实时性×方向×成本：本项目订单是"服务器主动+强实时"用 WS（并且按角色分桶，新单只推该店铺商家）；私信弱实时用 REST+afterId 轮询 2.5s 级，零长连接运维成本。
【解析】得分点：答"没有银弹，按场景选"并给判据；追问：SSE 升级私信要改什么（服务端保留 lastEventId、前端 EventSource）——会答直接加分。

**32. WebSocket 心跳与断线重连怎么做？多实例部署怎么广播？**
【答】心跳：客户端定时 ping，服务端超时未收到判离线（本项目前端 30s ping、断线 3s 重连）。多实例广播：实例 A 收到事件→发 Redis Pub/Sub 或 MQ fanout→各实例查本地 session 表投递（session 只在本机）。
【解析】得分点：能指出"会话是进程本地的，跨实例必须借助中间件转发"，这是单体升分布式的必考配套题；追问：①用户多端登录（本项目 `WsSessionManager` 用 `userId -> Set<WebSocketSession>` 保留多会话全推）；②**三端消息怎么不串**——会话按角色分桶（`userSessions / merchantSessions / adminSessions`），新订单只推给订单所属店铺的商家（`MessagePusher.newOrderToMerchant(merchantId, data)`），A 店新单不会打扰 B 店，平台管理员不进新单推送范围（避免噪音）；③升级多实例后这个分桶表也要跟着走 Pub/Sub 广播。

**33. Redis GEO 原理？附近的人有什么边界问题？**
【答】GEO 底层 ZSet，元素 score 是 **GeoHash(52bit)**——把经纬度编码成可比较大小的一维值，区间相邻即地理相邻。边界问题：GeoHash 分桶边界上两很近的点可能哈希差很远（桶裂）；大规模还要考虑分片、热区。更重方案：ES geo / PostGIS / 空间网格索引。
【解析】得分点：能讲"为什么用 score 排序就能做半径查询"，并主动提边界与规模演进；本项目按 typeId 分 key + type=0 全量双写也要能讲。

**34. HyperLogLog 原理？什么时候会不准？**
【答】把元素哈希后统计其二进制"最长前导 0 串"长度，多个桶取调和平均做基数估计：**~12KB 内存、标准误差 0.81%**。不准场景：基数极小（用 tiny 修正）或对精度要求高（应改精确 Set/精确计数）。PV 类大流量很适合，UV 精确对账就不合适。
【解析】得分点：答出"以极小的空间换确定性误差"，并能举本项目 uv:{date}:{page} 用法；追问：合并统计（PFMERGE）做跨页 UV。

**35. BitMap 签到：连续签到、月统计怎么实现？一年多少内存？**
【答】key=`sign:{uid}:{yyyyMM}`，第 N 位=当月第 N 天：SETBIT(day-1)；月统计遍历 GETBIT（或 BITCOUNT 计数）；连续天数从今天往前 GETBIT 计数。内存=365bit/年≈**46 字节/人**。进阶：BITFIELD 一次算多天；跨月连续用上月末几天+本月。
【解析】得分点：把"为什么省内存"算给面试官听；追问：百万用户一个月数据量（<50MB）→ 引申"海量二进制状态都可以 BitMap"。

**36. 编辑距离匹配的复杂度？TopN 为什么用堆？数据大了怎么办？**
【答】编辑距离 DP O(m·n)，标签都很短所以可忽略；瓶颈在候选数 M：全量算完再排序 O(MlogM)，用**容量 N 的堆**只留最优 N 个 O(MlogN)，空间 O(N)。量级上来：①标签**倒排索引**先缩候选（同标签优先）；②离线预计算画像相似；③标签向量化 + **ANN(HNSW/FAISS)** 召回。
【解析】得分点：能把"算法对 vs 规模对"分开讲，体现工程分层思考；追问：为什么用编辑距离不是 Jaccard（近似容忍"川菜≈川味"，见文档②）。

# 三、多角色 / 三端专题（37–42 · 本项目差异化重点）

> 这 6 题是"教程项目堆功能"与"真的设计过多角色系统"的分水岭。教程项目通常只有一个 `ADMIN` 常量，role 数字随手写；本项目把**端侧鉴权、店铺归属、入驻审核、审计留痕**做成了体系，这 6 题就是把它讲出来的最短路径。
> 三端接口面貌（背熟，被追问细节时直接报路径）：`/merchant/dashboard/**`（看板）、`/merchant/order/**`（接单→配送→完成）、`/merchant/product/**`、`/merchant/voucher/**` 与 `/merchant/voucher/order/**`（券管理与核销）、`/merchant/shop/mine`、`/merchant/apply/**`；`/admin/apply/**`（入驻审核）、`/admin/shop/**`（停业/恢复/删除）、`/admin/order/**`（全平台巡检与兜底处置）、`/admin/product/**`、`/admin/voucher/**`（治理，不负责日常经营）、`/admin/user/**`（封禁）、`/admin/stats/**`（平台看板）、`/admin/audit/page`（审计日志）、`/admin/type/**`（类目字典）。

**37. 多角色系统的权限怎么做才"不走样"？（考点：端侧鉴权分层）★**
【答】本项目用**三层**，各管一段，谁都不越位：
① **端级（拦截器）**：`security/AuthInterceptor` 按路径前缀做粗粒度分端——`/merchant/**` 仅商家(role=2) 与管理员(role=3)，`/admin/**` 仅管理员(role=3)，`/cart /mate /chat /sign` 是用户端专属（管理员账号调这些直接 403"平台管理员账号不支持用户端操作"）；`/auth/**` 免登录白名单在 `WebMvcConfig.EXCLUDE`。
② **方法级（Service 守卫）**：`security/RoleGuard.requireMerchant()/requireShopOperator()/requireAdmin()` 在 Service 入口再做一次显式身份声明——既让代码可读（一眼看出这个方法谁能调），也能覆盖定时任务/内部调用这类没有 Web 上下文的场景并给出清晰报错。
③ **数据级（归属收敛）**：即使角色对了，"这个 shopId 是不是你的"只有 Service 知道——`MerchantService.assertShopOwnership / resolveOperateShop` 负责，且**商品与券保存时服务端无条件用自己店铺 id 覆盖前端传入的 shopId**。
**再加一道前端**：`/user` `/merchant` `/admin` 三套路由 + 守卫**双重校验**（登录态 + 端侧归属，`utils/roles.js` 的 `pathRole`），但只当体验优化，**绝不当作安全边界**。
【解析】得分点：能说出"拦截器做不了数据级鉴权"这个本质——因为 `/merchant/product/save` 对所有商家都是合法路径，越权只体现在 body 里的 shopId；答"三层 + 前端只做体验"即满分。易错：把前端路由守卫当安全措施（改 localStorage 就绕过）；或只答拦截器不提 Service 二次校验。追问：管理员为什么能过 `/merchant/**`（`LoginUser.canOperateShop()` 允许，代管场景，见第 40 题）。

**38. 商家数据隔离应该放在拦截器还是 Service？（考点：鉴权分层边界）**
【答】**路径级放拦截器，数据归属必须放 Service**。判据是"这个判断需不需要知道业务数据"：拦截器只看得到 URL 和 JWT，它知道"你是商家"，但不知道"这个 shopId 是不是你的店铺"，所以它无法胜任归属校验。本项目 Service 层四个方法各有分工：`shopOfMerchant(merchantId)` 解析归属（带 60s 进程内缓存，扛住高频请求又能感知审核结果变化，变更后 `evictCache` 主动失效）；`requireActiveShop(merchantId)` 要求"已过审且未停业"才允许经营写操作；`assertShopOwnership(shopId, merchantId)` 校验目标店铺归属，传入 `merchantId=null` 表示管理员代管跳过归属；`resolveOperateShop(user, shopId, mustActive)` 统一解析"这次要操作哪个店铺"。
**写入侧还有一条硬保险**：`MerchantController.productSave/voucherSave` 里 `product.setShopId(shop.getId())`——**先解析出合法店铺，再用它覆盖请求体里的 shopId**，所以哪怕前端伪造 shopId 也只会写进自己店里。
【解析】得分点：能讲清"谁掌握什么信息谁负责校验"，并说出"服务端重写 > 服务端校验"（重写让越权在物理上不可能，校验只是拦截）；追问：为什么不用 AOP 注解统一做归属校验（可以，但要拿到 shopId 得解析方法参数/请求体，可读性和灵活性不如显式调用，本项目选了显式 + 可读）。易错：答"用 Spring Security 注解 @PreAuthorize 就够了"——注解同样只能表达角色，表达不了"这条记录属不属于我"。

**39. 为什么"一个商家一个店铺"用唯一索引，而不是应用层判重？原理和代价说清楚。**
【答】因为「一个商家只能有一个店铺」是**业务不变量**，不是一次性的校验动作。应用层判重（先 `selectCount` 再 `insert`）存在**竞态窗口**：两个并发请求（商家双击提交、或者两名管理员同时审核通过同一个商家的两张单）都可能查到"没有"，然后各插一条，得到两个店铺。本项目把约束下沉到 `tb_shop.merchant_id` 的 **唯一索引 `uk_merchant`**，让数据库当最终裁判——并发下必有一方拿到 DuplicateKey，业务侧捕获后按"已有店铺"处理即可，正确性不依赖代码写得多仔细。
代价也要讲：①商铺与商家是强 1:1，未来若要做"连锁多店"就得改模型（去掉唯一索引，改成 `tb_shop.merchant_id` 普通索引 + 一张 `tb_merchant_shop` 关系表）；②唯一索引同时意味着"同一商家同时只能存在一行店铺"，所以平台删除店铺是重操作——本项目 `AdminMerchantController.removeShop` 会先清归属缓存、调用 `ShopService.removeShop` 同步清理缓存与 GEO 索引，再写 `SHOP_DELETE` 审计日志；删除后该商家才能重新走入驻流程建店。
**反面教材坦率讲**：`MerchantService.shopOfMerchant()` 里"已有店铺就走资料变更分支、没有店铺才走首次入驻"、`submitApply` 里"已有待审单不许重复提交"，这两处都只是**体验层防重**；真正防重复的是 `uk_merchant` 唯一索引 + 申请单状态校验。
【解析】得分点：务必说出"并发竞态窗口"这四个字，并承认应用层判重降级为"体验优化"；能主动说出"连锁多店"的模型演进更加分。易错：把唯一索引说成"为了查询快"（它是约束，索引只是副产品）。

**40. 管理员代管商家端接口，怎么设计才安全？**
【答】先明确产品语义：商家端是"经营自己的店"，管理员是"平台代管任意店"，两者操作面几乎一样但**授权来源完全不同**。本项目的设计：
① **入口放行但不算授权**：`AuthInterceptor` 允许 role=3 进 `/merchant/**`（`LoginUser.canOperateShop()`），这只是"能进这个端"；
② **必须显式指定店铺**：所有商家端查询/写接口都接受可选 `shopId`，`MerchantService.resolveOperateShop(user, shopId, mustActive)` 里——商家走"自己的店铺"（忽略/校验传参），管理员**没传 shopId 直接抛"请先选择要管理的店铺"**。所以代管是"显式选择"而不是"隐式全权"；
③ **前端配合**：`MerchantLayout` 里管理员看到店铺下拉（数据来自 `/merchant/shop/mine` 返回的 `admin=true + shops`），选中后经 `bus` 广播，`Dashboard/Orders/Products/Vouchers` 等子页面把它作为 `shopId` 参数带上；
④ **权限差异显式化**：确实"只有商家本人能做"的敏感自助动作（改店铺资料 `/merchant/shop/profile`、营业开关 `/merchant/shop/open`、提交申请 `/merchant/apply/submit`）用 `RoleGuard.requireMerchant()`——**管理员一律不通过**；平台要改这些必须走管理端自己的治理接口（`/admin/shop/{shopId}/audit`），而且会写审计日志；
⑤ **写操作双重把关**：改别人的商品/券时除了角色校验还要 `assertShopOwnership(exists.getShopId(), user.isAdmin() ? null : user.getId())`，管理员靠传 null 跳过归属但仍留下审计记录。
【解析】得分点：说出"放行 ≠ 授权""代管必须显式选店""管理员不能替商家自助改资料，只能走治理接口"这三条即可满分；能补充"管理员操作全部落 `tb_audit_log`（APPLY_APPROVE/SHOP_CLOSE/USER_BAN…）可追责"更佳。追问：管理员误操作了怎么办（审计日志 + 店铺状态可恢复/驳回原因留痕）。

**41. 审核通过后自动开店，怎么保证幂等？并发下会不会开出两个店？**
【答】整条链路是一个 `@Transactional(rollbackFor = Exception.class)` 的 `MerchantService.auditApply`，幂等靠**三道叠加**：
① **单据状态前置校验**：进入方法先查申请单，`status != APPLY_PENDING(0)` 直接抛"该申请单已处理，请勿重复审核"——重复点击/重复请求在业务上被第一条挡住；
② **事务原子性**：申请单状态更新 + 创建店铺 + 回写 `apply.shopId` 在同一事务里，要么全成要么全不成，不会出现"状态已改为通过但店铺没建出来"；
③ **数据库最终防线**：万一两次审核真的并发了，两个事务都创建 `tb_shop` 时会撞上 `uk_merchant` 唯一索引——一方 DuplicateKey，事务回滚，不会留下两家店。
另外分支语义也要清楚：**首次入驻**（`apply.shopId == null`）才 `new Shop()` 并直接 `audit_status=1 / open_status=1` 开通；**资料变更**（`type=2`）走的是更新已有店铺并复营业；**驳回**只更新单据状态与驳回原因，首次入驻不产生店铺。最后 `evictCache(merchantId)` 清掉归属缓存（否则商家端 60s 内还看不到新店），并写 `APPLY_APPROVE/APPLY_REJECT` 审计日志。
【解析】得分点：能按"状态机 → 事务 → 唯一索引"三层报出防线，并说清"哪一层防的是什么"（状态防重复提交、事务防半成品、唯一索引防真并发）；主动提"缓存要在事务提交后失效"是加分项。易错：只说"加个分布式锁"——锁能防同一管理员重复点击，但防不了"数据本来就重复"这类问题，而且引入额外依赖，本项目优先用状态+约束解决。

**42. role 重新定义（1用户/2商家/3管理员）之后，历史数据怎么升级才不出事故？**
【答】本项目给了两条路径：
① **全新初始化**：`sql/init.sql`（表 `CREATE TABLE IF NOT EXISTS` + 种子 `INSERT IGNORE` 固定主键，可重复执行），种子规模为 **1 管理员 + 11 商家 + 9 用户 + 10 店铺 + 2 张入驻申请单**（其中 `13700000002/merchant123` 是"待审核未开店"商家，专门用来演示"提交入驻 → 平台审核 → 自动开店"）。
② **旧库平滑升级**：`sql/manual/upgrade_v2_three_end.sql`，**幂等**是要点——MySQL 8 的 `ADD COLUMN` 不支持 `IF NOT EXISTS`，脚本用**存储过程 + `information_schema` 判断**后再动态 `ALTER`（`sl_add_column` / `sl_add_index`），已存在的列/索引/表自动跳过；执行顺序上**先把 `role=2` 的管理员统一提升为 `role=3`**（`UPDATE tb_user SET role = 3 WHERE role = 2`），再为历史店铺补建商家账号（`13700000001~10 / merchant123`，用 `NOT EXISTS` 防重复插入）并按顺序绑定 `tb_shop.merchant_id`，同时补建"已通过"的入驻申请单让管理端审核记录完整；最后 `ALTER ... MODIFY COLUMN role ... COMMENT '1用户 2商家 3平台管理员'` 修正注释并输出 `SELECT role, COUNT(*)` 做校验。
**顺序为什么关键**：如果先建商家账号（role=2）再把 role=2 提升为 role=3，商家账号会被误升级成管理员——这是最容易踩的坑。
【解析】得分点：讲清"幂等怎么实现（information_schema 判断 + 动态 DDL）"与"DDL/DML 顺序依赖"；能说出"为什么不直接重跑 init.sql"（会丢数据，且种子是 INSERT IGNORE 不会覆盖已有业务数据）更佳。追问：线上执行升级脚本要注意什么（备份 `scripts/backup-db.sh`、低峰执行、DDL 会锁表、先灰度验证）。

# 四、低频考点（43–56）

**43. 脏读 / 不可重复读 / 幻读分别指什么？（一句话区分）**
【答】脏读=读到**未提交**数据；不可重复读=同一行两次读值不同（被改/被删）；幻读=同一范围两次查询**行数变化**（被插）。隔离级别逐级解决：RC 防脏读，RR 防脏读+不可重复读，串行化全防。
【解析】得分点：结合秒杀想一下"为什么条件更新+唯一索引不怕幻读"（唯一索引天然防同键并发插入）。

**44. SQL 注入原理？MyBatis #{} 和 ${} 区别？**
【答】注入=把用户输入拼进 SQL 改变语义。`#{}` 预编译占位符（安全）；`${}` 直接拼接（有注入风险，仅用于表名/排序字段等且必须白名单）。本项目手写 SQL 全用 `#{}`/`@Param`。
【解析】得分点：说清"预编译为什么能防"（参数不进 SQL 解析）；追问：LIKE/IN/ORDER BY 动态场景怎么安全处理（拼接前白名单校验）。

**45. 订单号/分布式 ID 怎么生成？雪花算法了解吗？**
【答】本项目订单号：时间戳+随机（单机够用）；生产：**雪花算法**（时间戳+机器位+序列号，趋势递增）、号段模式（数据库发号/Leaf）或 UUID（无序、索引差）。要满足：唯一、尽量趋势递增利于索引、可含业务位。
【解析】得分点：说出"为什么不用 UUID 当主键"（无序导致页分裂）；追问：雪花时钟回拨怎么办（拒绝/等待/备用序列）。

**46. 统一返回 Result 和全局异常的设计思路？**
【答】统一 `{code,msg,data}`：code=1 成功，业务失败/401/403 走约定码；`@RestControllerAdvice` 集中处理 BusinessException→业务提示、MethodArgumentNotValidException→参数提示、Exception→"服务器繁忙"+日志。避免 Controller 到处 try-catch、也避免把堆栈吐给前端。
【解析】得分点：讲"异常分类"（业务异常=提示用户；系统异常=记日志）；追问：如何区分 4xx/5xx 与 HTTP 状态（可约定 HTTP 200+业务码或语义化，本项目前者；**三端相关的 401/403 走 `security/AuthInterceptor` 里 `ResponseUtil.write(response, 403, ...)` 直接写响应体，业务异常交给全局处理器**——两条通道要能分清）。

**47. MyBatis-Plus 自动填充、逻辑删除、乐观锁插件知道吗？**
【答】MetaObjectHandler 自动填充 create_time/update_time（本项目用它统一时间）；逻辑删除=@TableLogic 只 update is_deleted；乐观锁=@Version 插件自动拼 version 条件。本项目用自动填充+少量手写乐观条件更新。
【解析】得分点：能说"工具帮什么、我什么时候自己写 SQL"；追问：逻辑删除对唯一索引的影响（易踩坑）。

**48. 项目里事务都用在哪些方法？传播/隔离怎么设？**
【答】下单、秒杀落库、取消订单回补、券的创建：都要求"要么全成要么全不成"→默认 REQUIRED 即可；秒杀消费事务里"先条件扣库存再插订单，失败整体回滚"。**三端治理侧同样重事务**：入驻审核 `MerchantService.auditApply` 里"改申请单状态 + 建/改店铺 + 回写 shopId"必须同事务，否则会出现"审核显示已通过但店铺不存在"的脏数据。隔离用默认（数据库层条件更新+唯一索引兜并发，不靠隔离级别硬扛）。
【解析】得分点：答出"业务并发控制靠条件更新与唯一约束，而不是靠把隔离级别调到串行化"——体现设计判断；追问：事务里调用 Redis/MQ 的副作用（不是事务资源，需补偿/最终一致；本项目的做法是把 `evictCache` 放在业务方法末尾而非依赖回滚）。

**49. Spring AOP 在你项目里体现在哪？**
【答】事务（@Transactional 代理）、异常处理（@RestControllerAdvice 本质也是 AOP 思想）、日志切面可加（记录入参耗时）；秒杀/统计若加"耗时打点"用切面最合适。**需要注意本项目端侧鉴权没用 AOP/注解，而是拦截器 + Service 显式 `RoleGuard` 调用**——因为归属校验（"这个 shopId 是不是我的"）需要业务数据，注解表达不了，强行用切面反而要在切面里解析方法参数，可读性更差（呼应第 37/38 题）。
【解析】得分点：能讲清动态代理（JDK 接口代理 vs CGLIB）与自调用失效（呼应第21题）即达标。

**50. Docker 部署注意什么？Nginx history 路由和 WS 反代怎么配？**
【答】前端镜像：多阶段（node 构建→nginx 托管）；后端镜像瘦身（temurin-jre + 可执行 jar，本项目 `docker-compose.prod.yml` 更进一步——**镜像内用 Maven 多阶段构建**，服务器无需装 JDK）。Nginx：history 路由 `try_files $uri /index.html`；WebSocket 要 `proxy_set_header Upgrade/Connection` 且 `proxy_read_timeout` 拉长。编排上 **MySQL8 + Redis7 + RabbitMQ3.12 + 后端 + Nginx 全容器化，对外只暴露 80/443**（3306/6379/5672/15672/8080 都只绑 `127.0.0.1` 供本机运维；443 走 HTTPS：无域名、免 ICP 备案时用 Let's Encrypt 的 IP 证书 + acme.sh 定时续签，有域名后一条命令换 90 天证书），密钥经 `.env.prod` 注入（compose 里用 `${VAR:?请在 .env.prod 中设置 …}` 强制校验，缺密钥直接启动失败），`scripts/deploy.sh` 一键部署/升级并带健康检查（前端探活 + 用管理员账号打 `/api/auth/login` 探后端），`scripts/backup-db.sh` 备份。
【解析】得分点：说"容器只给进程、数据放 volume、配置用环境变量"（本项目 yml 全环境变量化 MYSQL_*/REDIS_*/RABBIT_*）+ "敏感项默认不暴露公网"；追问：健康检查与启动顺序（`depends_on: condition: service_healthy` + healthcheck + 脚本轮询重试）。

**51. 启动预热 Runner 和定时预热在防什么？**
【答】DataInitRunner 启动时重建 GEO 索引、装载布隆、回填秒杀库存、预热类型缓存——解决**冷启动后第一波请求全 miss**；CachePreheatTask 定期把热点店铺写进缓存——把"击穿窗口"提前消化，配合随机 TTL 错峰。
【解析】得分点：把"预热"放进"缓存治理体系"讲而不是孤立功能；追问：预热任务挂了怎么办（有 DB 兜底降级，接口仍可用只是慢一点）。

**52. DO / DTO / VO 分层为什么有必要？Controller 应多薄？**
【答】DO(entity) 对表、DTO 对入参（校验注解）、VO 对出参（脱敏 phone、展开 tags、拼接 shopName）——防把密码/内部字段漏出去、防表结构变化污染接口。Controller 只做参数绑定与结果包装，业务在 Service。
【解析】得分点：举本项目 UserVO 隐藏 password/phone 脱敏的例子最有力——`UserService.toVO(user, withPhone)` 在 `withPhone=true` 时也只写**脱敏**手机号（`138****0000`），`withPhone=false` 则整个字段不返回，**password/salt 永不进 VO**；**三端场景下这一条更值钱**：同一个 `UserVO` 服务用户端（自己的资料）、饭搭子（他人公开资料）、管理端账号治理三种口径，靠 VO 收口而不是靠"前端别显示"；追问：字段多了要不要只返回需要字段（是，省流量+安全）。

**53. 前端 token 续期和 401 是怎么串起来的？**
【答】axios 请求拦截器带 `Authorization`；响应拦截器：收到 `X-Auth-Refresh` 就更新存储的 token；body.code=401 时清登录态跳登录页。后端续期见第10题——前端无感替换。
【解析】得分点：能画"请求→后端判快过期→响应头新 token→前端自动替换下一次请求"闭环；追问：并发多个请求同时拿到刷新头会不会乱（幂等覆盖即可，本项目直接覆盖）。

**54. XSS / CSRF / 越权是什么？本项目做了哪些？**
【答】XSS=注入脚本窃取/伪造；CSRF=借已登录身份发请求（表单/图片）；越权=水平(改别人 id)或垂直(普通用户调管理员接口)。本项目：①后端不信任前端数据（金额服务端重算、userId 一律从 UserContext 取而非请求参数、**商品/券的 shopId 服务端强制重写**）；②垂直越权靠 `AuthInterceptor` 按端分路径（`/admin/**` 仅 role=3、`/merchant/**` 仅 role=2/3）+ `RoleGuard` 二次校验；③**水平越权靠 Service 层归属校验**（`MerchantService.assertShopOwnership` 与订单侧 `OrderService.assertOwnership` 比对 `shop.merchant_id`，管理员代管时传 null 跳过）；④口令加盐（`salt:sha256(password+salt)`）；⑤违规账号可被平台封禁（`tb_user.status=0`，登录即拒）。
【解析】得分点：主动说"水平越权在真实系统要靠资源归属校验，而且必须在服务端"——本项目查询都带当前 userId/自己的 shopId 条件即该思路，且拦截器做不到这类校验（呼应第 37/38 题）；追问：JWT 放 localStorage 的 XSS 风险 vs cookie 方案的 CSRF 风险（要能权衡）。

**55. 这个单体怎么演进成微服务？哪些先拆、基建补什么？**
【答】先按**业务与流量**拆：订单/秒杀(高写)、店铺搜索(高读)、用户/匹配各自独立；补：注册发现与网关(Nacos+Gateway)、配置中心、分布式事务(下单可选本地消息表/事务消息或 Seata AT，秒杀本是 MQ 解耦天然适合)、WS 多实例广播(第 32 题)、定时任务换 XXL-Job、Redis/MySQL 集群与分库分表。**三端治理还要额外考虑**：网关层统一做端侧路由与鉴权（把 `AuthInterceptor` 的路径前缀规则上移到 Gateway），但**店铺归属校验仍必须留在各服务的业务层**（网关同样不知道 shopId 属不属于你）；入驻审核这类跨服务写操作（改单据 + 建店铺）在拆分后正好由"事务消息/本地消息表"承接。
【解析】得分点：核心是"说清哪些套路原样平移、哪些必须换"；本项目中间件技巧(缓存分层/Lua/MQ 削峰/唯一索引幂等)在微服务下完全复用——这就是单体高并发项目的价值；能主动指出"鉴权可以上移、归属校验不能上移"是高分回答。

**56. 讲一个你印象最深的 Bug / 怎么排查的？（行为题但考技术深度）**
【答】示例（真实，二选一讲）：
① **登录后跳回登录页"点了没反应"**——排查：先用无头浏览器复现并抓包确认登录接口 200 返回正常 → 定位到路由守卫读 localStorage 为空 → 深挖是 Pinia store `state: () => load()` 首次返回空对象、**未预声明 token 等字段**导致赋值不生效、save() 存出 `{}` → 修复为显式声明全部字段并做持久化水合；三端化之后这个坑更危险：store 里还多了 `shopId/shopName/shopAuditStatus` 三个商家端上下文键，漏声明会让商家端首屏拿不到店铺。
② **管理员代管时"看错店"**——现象：管理员进商家端默认落在第一个店铺，误以为在看 A 店实际操作了 B 店。排查：管理员没有个人店铺（`shopOfMerchant(adminId)` 返回 null），`/merchant/shop/mine` 返回的是全平台店铺列表，而 `resolveQueryShop` 在管理员不传 shopId 时返回 null（全平台口径），前端又有"自动选中列表第一项"的兜底 → 界面口径与接口口径不一致。修复思路：`resolveOperateShop` 对管理员**强制要求显式 shopId**（未选直接报"请先选择要管理的店铺"），前端把"当前代管店铺"做成显式可见、可切换状态（`MerchantLayout` 下拉 + `bus` 广播），并在写操作接口上再校验一次归属。
【解析】得分点：按"现象→假设→最小复现→抓证据(网络/存储/接口口径)→根因→修复→沉淀"讲；比直接说"我会 Redis"更能证明工程能力。易错：只讲结论不讲排查过程；三端项目的 Bug 往往不是语法错误而是**口径不一致（谁的店铺？哪个端？）**，能这样归纳非常加分。
