## 0. 一句话定位（放简历首行）

> 高并发本地生活与社交聚合平台「智联生活」：围绕"**逛店(附近搜索) → 点外卖 → 抢秒杀券 → 找饭搭子 → 实时履约**"的全链路业务闭环，单体架构整合四大经典电商/社交场景，并在同一工程内落地**用户端(role=1) / 商家端(role=2) / 管理端(role=3) 三端角色体系与平台治理闭环**，重点解决高并发下的**缓存治理、超卖、订单一致性、实时触达、多端权限不走样**五大难题。

## 1. 推荐简历模板（可直接改）

**项目名称**：智联生活 · 高并发本地生活与社交聚合三端平台（个人全栈实战，参考苍穹外卖/黑马点评/黑马商城/伙伴匹配四大项目重构融合）

**技术栈**：Spring Boot · MyBatis-Plus · MySQL · Redis · Lua · Redisson · RabbitMQ · JWT · WebSocket · Spring Scheduler · Docker Compose · Knife4j · Vue3 · ECharts

**项目描述**：
一体化本地生活三端平台：用户端（逛店/外卖/秒杀/饭搭子社交）、商家端（商品券管理、订单履约、经营看板）、管理端（入驻审核、店铺与账号治理、平台看板、审计留痕），三端共用一套账号体系（`tb_user.role` 1/2/3）与一套后端服务。
- 浏览链路：店铺详情构建 **本地 Caffeine + Redis + DB 三级缓存**，配合**布隆过滤器、空值缓存、随机TTL、互斥锁重建**分别拦截穿透/雪崩/击穿；基于 **Redis GEO** 实现附近店铺，**HyperLogLog** 统计页面 UV，**BitMap** 实现每日签到。
- 交易链路：购物车与订单分别落在 Redis Hash 与 MySQL；**下单用条件更新 SQL 原子扣库存**防超卖；支付后经 **WebSocket** 按角色分桶推送——新订单只推给该店铺的商家（`MessagePusher.newOrderToMerchant(merchantId,...)`），履约状态（接单→配送→完成）推给下单用户；并实现超时未支付订单自动取消（分布式锁防多实例重复执行）。
- 秒杀链路：**Redis Lua 脚本原子完成"库存扣减+一人一单校验"**后投递 **RabbitMQ 异步削峰下单**，消费者事务落库+唯一索引幂等，失败消息走**死信队列回补库存**；另提供 Redisson 分布式锁版可一键切换对比。JMeter 压测验证不超卖，接口吞吐显著高于同步直写（数字以本机实测为准）。
- 平台治理链路：商家提交**入驻/资料变更申请单**（`tb_merchant_apply`）→ 管理员在管理端审核 → **通过时自动创建并开通店铺**（一个商家账号绑定一个店铺，`tb_shop.merchant_id` 唯一索引）→ 违规可停业/恢复/删除；关键操作落 `tb_audit_log` 留痕；账号可封禁（`tb_user.status` 1正常/0封禁）。
- 权限与隔离：**按路径前缀的端侧鉴权**（`AuthInterceptor`：`/merchant/**` 仅 role=2/3、`/admin/**` 仅 role=3、`/cart /mate /chat /sign` 为用户端专属）+ **Service 层二次校验**（`security/RoleGuard`）；商家数据隔离靠 `MerchantService.shopOfMerchant / requireActiveShop / assertShopOwnership / resolveOperateShop`，**商品与券保存时服务端强制把 shopId 重写为自己的店铺**，防伪造 shopId 越权。
- 社交链路：用户兴趣标签经**编辑距离**度量相似度，用**容量为 N 的优先队列**取 TopN 推荐饭搭子（内存 O(N)），结果 Redis 缓存 10 分钟。
- 工程化：JWT **二级拦截器链**（登录+三端角色校验 / Token 滑动续期），ThreadLocal 线程隔离；统一异常/响应体；Knife4j 文档；全容器化部署（MySQL8 + Redis7 + RabbitMQ3.12 + 后端 + Nginx，`docker-compose.prod.yml` + `scripts/deploy.sh` 一键部署，仅对外暴露 80 端口，密钥经 `.env.prod` 注入）。

## 2. 亮点拆解（每个都可以被追问到底，均有对应源码）

### 亮点①：多级缓存与高并发流量治理（源自黑马点评）
**讲法**：热点店铺详情页 QPS 极高，直连 DB 会打满连接。
- L1 本地缓存 Caffeine（5s）兜热点；L2 Redis 存 JSON；
- 缓存 key 过期时间 **随机化(20~40min)** → 避免雪崩；
- 详情查询先过**布隆过滤器**，不存在的店铺 id 直接返回 → 避免穿透打库；
- 缓存 miss 时**互斥锁（SETNX）单飞重建 + 双重检查**，其余线程自旋等待后兜底查库 → 避免击穿；
- DB 无记录时写 **5 分钟空值缓存**；布隆/缓存/GEO 在增删改店铺时联动维护。
**源码**：`ShopService.queryById / rebuildByMutex / rebuildIndexes`
**可追问**：布隆过滤器误判/删除问题、为什么 Redis 不做逻辑过期、Caffeine 与 Redis 一致性怎么取舍。

### 亮点②：Redis+Lua+RabbitMQ 秒杀（源自黑马点评+黑马商城）
**讲法**：秒杀本质是"库存扣减 + 一人一单"两个原子约束 + "下单落库"慢操作。
- 两次 DB 读改（校验库存→插订单）会超卖 → 改 **Lua 脚本**（DECR + SISMEMBER/SADD）一次 RTT 原子完成预扣；
- 落库改 **RabbitMQ 异步消费**：同步阻塞转异步削峰，消费者事务里 `UPDATE ... SET stock=stock-1 WHERE stock>0` 做 DB 兜底 + **user_id+voucher_id 唯一索引**做一人一单最终防线（消费天然幂等）；
- 失败补偿：业务异常回补 Redis 库存并解绑用户标记，未知异常 NACK 进**死信队列**兜底回补；WebSocket 把秒杀结果实时推给用户；
- 集群语义：Redisson `lock()` 看门狗自动续期版作为可切换方案（`smartlife.seckill.lua-enabled=false`），方便面试演示两种思路差异。
**源码**：`VoucherService.grabSeckill/luaReserve/lockReserve`、`SeckillOrderConsumer`、`SeckillDeadConsumer`、`resources/lua/seckill.lua`
**可追问**：Lua 为什么原子？MQ 丢消息/重复消费怎么办？Redis 与 DB 库存不一致？死信什么时候触发？

### 亮点③：订单履约一致性 + WebSocket 三端实时化（源自苍穹外卖）
**讲法**：外卖是"跨端协作"业务：用户下单、商家接单、骑手配送、平台巡检。
- 订单用**事务**一次写入主单+明细快照，明细存商品名/价格快照防商品改价影响历史单；
- **条件扣库存 SQL（where stock>=n）**防并发超卖，取消/超时回补库存；
- 订单状态 1→6 状态机：用户支付→(WS 推送**该店铺商家**)新订单响铃→商家接单/开始配送/完成→(WS 推送用户)实时进度；
- 支付后 15 分钟未支付由 **Spring Scheduler 每 30s 扫描取消**，多实例部署时套 **Redisson tryLock** 保证单机执行。
**源码**：`OrderService`、`OrderTimeoutTask`、`ws/WsSessionManager`、`ws/MessagePusher`
**可追问**：为什么订单明细要快照？怎么防超卖？MQ 与定时任务两种超时方案对比？WebSocket 断线重连/多端登录怎么处理？

### 亮点④：编辑距离匹配 + 优先队列 TopN（源自伙伴匹配）
**讲法**：饭搭子=兴趣标签相似的人。
- 相似度 = 我的每个标签与对方标签集合**最小编辑距离之和**，支持中文近似匹配（"川菜/川味"）；
- 候选全量遍历时只维护**容量为 N 的优先队列**（堆顶淘汰最差），内存 O(N) 而非 O(M)；
- 推荐结果按用户 Redis 缓存 10min + 定时预热热标签，冷启动也不穿透；
- 标签搜索用 MySQL `JSON_CONTAINS` 精确匹配，另提供热门标签。
**源码**：`MateService`、`util/Levenshtein`
**可追问**：为什么用编辑距离而不是集合交集/余弦？TopN 为什么用堆？数据量大到百万用户怎么办（索引/向量召回/异步预计算）？

### 亮点⑤：平台治理闭环（入驻审核 + 数据隔离 + 审计留痕）——三端项目最大的差异化
**讲法**：教程项目通常只有"用户端 + 一个兼着商家的管理端"，role 也只有一个管理员常量；本项目的增量是把**平台治理做成一条完整闭环**，这才是"多角色系统设计能力"的证据。

- **入驻/变更审核闭环**：商家提交申请单 `tb_merchant_apply`（`type` 1首次入驻/2资料变更，`status` 0待审/1通过/2驳回）→ 平台在 `/admin/apply/**` 审核 → **审核通过时自动创建并开通店铺**（`audit_status=1`、`open_status=1`）→ 驳回记录原因、首次入驻不产生店铺；同一商家存在待审核单时禁止重复提交，已处理单据再次审核直接报"请勿重复审核"（`MerchantService.submitApply / auditApply`）；商家端 `/merchant/shop/mine` 首屏据此区分"未入驻 / 待审核 / 经营中"。
- **归属模型**：`tb_shop.merchant_id` **唯一索引**（`uk_merchant`）= 一个商家账号绑定一个店铺，把"一个商家一个店铺"这条业务约束下沉成数据库事实，应用层判重只能算第二道防线。
- **数据隔离（防水平越权）**：`AuthInterceptor` 只做**端侧粗粒度**鉴权（`/merchant/**` 仅 role=2 与 3；`/admin/**` 仅 role=3；`/cart /mate /chat /sign` 为用户端专属），真正的店铺归属校验在 Service 层——`MerchantService.shopOfMerchant()/requireActiveShop()/assertShopOwnership()/resolveOperateShop()`，配合 `security/RoleGuard` 的 `requireMerchant/requireShopOperator/requireAdmin`；**商品与券保存时服务端强制用"本次解析出的合法店铺 id"覆盖前端传入的 shopId**（商家恒为自己店铺，管理员代管时为显式选定的店铺），前端伪造 shopId 也写不进别人店里。
- **管理员代管**：管理员允许进入商家端（`LoginUser.canOperateShop()`），但**必须显式选择店铺**（商家端接口带 `shopId` 参数，`resolveOperateShop` 在 admin 未传 shopId 时直接报错"请先选择要管理的店铺"），把"平台级代管"与"商家自助"用同一个接口面区分开。
- **审计留痕（可追责）**：`tb_audit_log` 记录平台关键操作 `APPLY_APPROVE / APPLY_REJECT / SHOP_CLOSE / SHOP_REOPEN / SHOP_DELETE / USER_BAN / VOUCHER_BAN / PRODUCT_DOWN / TYPE_SAVE` 等，管理端 `/admin/audit/page` 可查；写日志失败**不影响主流程**（try/catch 后告警）。
- **消息不串端**：`WsSessionManager` 按角色分桶（`userSessions / merchantSessions / adminSessions`），新订单只推送给订单所属店铺的商家，A 店的新单不会打扰 B 店，平台管理员不进新单推送范围（避免噪音）。
- **平台治理看板**：管理端 `/admin/stats/**` 提供 overview / trend / userTrend / shopAudit（审核状态分布）/ roleDistribution（角色分布）/ orderStatus / shopRank，与商家端 `/merchant/dashboard/**` 的**单店口径**形成对照。

**源码**：`MerchantService`（submitApply/auditApply/changeShopAuditStatus/shopOfMerchant/requireActiveShop/assertShopOwnership/resolveOperateShop/writeAuditLog）、`security/AuthInterceptor`、`security/RoleGuard`、`controller/AdminMerchantController`、`controller/AdminUserController`、`controller/MerchantController`、`ws/WsSessionManager`、`sql/init.sql` + `sql/manual/upgrade_v2_three_end.sql`
**可追问**：为什么隔离放在 Service 而不是只放拦截器？为什么用唯一索引而不是应用层判重？审核通过自动开店怎么保证幂等/并发安全？管理员代管接口怎么设计才不被绕过？老库怎么平滑升级到三端（role=2 管理员变 role=3、给历史店铺补建商家账号）。

### 亮点⑥：工程化与接口规范（苍穹外卖 + 伙伴匹配风格）
- **JWT 二级拦截器链**：一级校验登录态 + **按路径前缀做三端角色校验**并写入 ThreadLocal（afterCompletion 清理防串号），二级检查剩余有效期 <30min 自动签发新 Token（响应头 `X-Auth-Refresh`），前端 axios 拦截器无缝续期；
- **三端路由与守卫**：单仓库单应用，`/user` `/merchant` `/admin` 三套布局与路由，守卫**双重校验**（登录态 + 端侧归属），手改 localStorage 的 role 也跳不进别人的端；后端登录接口直接下发 `homePath`，前端不硬编码业务规则；
- 统一响应体 `Result{code,msg,data}` + 全局异常处理器（业务异常/参数校验）；
- RabbitMQ 声明式交换机/队列/死信；Redis key 常量集中管理；Knife4j 自动文档；
- 全容器化编排 MySQL/Redis/RabbitMQ + 后端 + Nginx 前端（后端镜像在容器内 Maven 多阶段构建，服务器无需装 JDK），生产编排仅对外暴露 80 端口，密钥经 `.env.prod` 注入，`scripts/deploy.sh` 一键部署/升级、`scripts/backup-db.sh` 备份。

## 6. 面试高频问答（20 题速记）

1. **缓存穿透/击穿/雪崩区别与你的解法？** → 穿透=查不存在（布隆+空值缓存）；击穿=热点 key 过期（互斥锁重建+本地缓存兜底）；雪崩=大面积同时过期（随机TTL+多级）。
2. **布隆过滤器误判怎么处理？** → 误判只导致多查一次缓存/DB，可配空值缓存二次兜底；误删问题靠启动重建索引。
3. **为什么 Redis Lua 能保证不超卖？** → 脚本整体原子执行，Redis 单线程模型下无并发交错。
4. **MQ 里消息丢了怎么办？** → 生产 confirm、队列持久化、消费手动 ACK；本项目的唯一索引保证重复消费幂等。
5. **重复消费怎么幂等？** → user_id+voucher_id 唯一索引，DuplicateKey 直接 ACK。
6. **Redis 库存和 DB 库存不一致？** → Redis 是快车道，DB 条件更新是权威兜底；消费失败回补 Redis；重启/巡检任务自动回填；可答"最终一致"。
7. **一人一单在集群下怎么保证？** → Lua SISMEMBER 原子 + 库表唯一索引双保险。
8. **为什么用 Redisson 不用自己 SETNX？** → 看门狗自动续期、可重入、公平锁等，避免业务超时锁自动释放误删他人锁；自己实现需 uuid 比对 + 续期脚本。
9. **下单为什么要异步（MQ）？** → 削峰填谷：秒杀瞬间 DB 事务堆积，MQ 让数据库按自己速率消费。
10. **WebSocket 和轮询区别？断线怎么办？** → 长连接双向实时；前端心跳 + 断线指数退避重连；后端**按角色分桶的会话表**管理、关闭时清理。
11. **订单为什么存明细快照？** → 防商品改名/改价/下架影响历史订单；金额服务端重算防篡改。
12. **三端权限怎么保证不走样？** → 拦截器按路径前缀粗粒度分端 + `RoleGuard` 在 Service 层二次校验 + 数据归属在 Service 内按 shopId 强制收敛（前端伪造 shopId 被服务端重写），三层各管一段。
13. **商家只能看自己的数据，这个隔离做在哪一层？** → 拦截器只管"能不能进这个端"，归属校验必须进 Service：`MerchantService.assertShopOwnership/resolveOperateShop`，因为同一路径下不同 shopId 的越权只有 Service 知道。
14. **为什么一个商家一个店铺用唯一索引？** → 把业务不变量交给数据库：并发注册/审核通过时唯一索引是唯一能挡住重复店铺的防线，应用层判重有竞态窗口。
15. **管理员代管商家端怎么设计才安全？** → 路由允许（`canOperateShop`）但**接口必须显式带 shopId**，Service 里 admin 未传 shopId 直接报错；这样代管是"显式选择"而不是"隐式全权"。
16. **审核通过自动开店怎么保证幂等？** → 申请单状态前置校验（非 0 待审直接拒绝重复审核）+ 整个审核在一个事务里 + 建店后回写 `apply.shop_id`，重复点击只会有一次生效。
17. **编辑距离为什么适合中文标签？** → 支持"近似"而非必须完全相等（川菜≈川味），字符级 DP 复杂度 O(mn)，标签都很短成本可接受。
18. **TopN 为什么用堆？** → 全量排序 O(MlogM)，堆只留 N 个 O(MlogN)，内存 O(N)。
19. **JWT 无状态，怎么踢人/续期？** → 本项目用双拦截器+滑动续期响应头；要强制下线可引入 Redis 黑名单/版本号（可答演进方案）；账号封禁则用 `tb_user.status` 在登录时拦截。
20. **定时任务多实例重复执行？** → Redisson tryLock 抢锁，抢不到直接跳过；锁超时设为略大于任务时长。

## 7. 一句话版本自评（写在"项目亮点"栏）

> 独立设计并实现高并发本地生活**三端平台**：用**多级缓存+布隆/空值/随机TTL/互斥锁**治理热点店铺流量；用 **Lua+Redisson+RabbitMQ(死信)** 打造不超卖秒杀链路；用 **WebSocket 按角色分桶+状态机+定时任务** 打通三端订单履约；用**入驻审核+归属唯一索引+服务端 shopId 重写+审计留痕**构建平台治理闭环；用**编辑距离+优先队列**实现 TopN 饭搭子推荐 —— 既覆盖四套经典高并发难题，又完整落地多角色系统的权限与数据隔离设计，集中到一个可运行、可压测、可部署的工程中。
